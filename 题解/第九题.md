# 第九题题解：可配置的快照隔离与可串行化隔离级别

## 一、题目目标

本题要求在 RMDB 中实现两种可配置的事务隔离级别：

```sql
SET TRANSACTION ISOLATION LEVEL SNAPSHOT ISOLATION;
SET TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

其中：

- `SNAPSHOT ISOLATION`，简称 SI，需要实现基于 MVCC 的事务级快照读；
- `SERIALIZABLE`，简称 SER，需要在 SI 的基础上实现题目规定的 SSI 风格判定；
- 写写冲突或 SSI 危险结构必须使当前语句返回严格的 `abort\n`，并回滚当前事务；
- 普通写语句、`BEGIN`、`COMMIT`、`ROLLBACK` 和隔离级别设置成功时不能返回多余信息；
- `SELECT` 必须保持框架原有的标准表格输出；
- 输出还要按框架原有格式写入数据库目录下的 `output.txt`；
- 第九题的事务修改不能破坏第十题使用的 WAL、提交、回滚和恢复链路。

最终评测结果：

```text
得分：20.00
You have passed all test cases about configurable isolation
```

本地回归测试结果：

```text
PASS all 23 q9 runtime tests
```

---

## 二、核心难点

这道题并不只是增加两个隔离级别关键字。真正困难的部分主要有以下几点。

### 2.1 快照必须固定在事务开始时

事务 `T` 在 `BEGIN` 时获得 `start_ts`。之后所有普通读取都只能看到：

```text
commit_ts <= T.start_ts
```

的最新已提交版本，再叠加 `T` 自己尚未提交的写入。

如果每次 `SELECT` 都读取当前物理页，就会出现不可重复读；如果完全忽略未提交版本，又会破坏“读己之写”。

### 2.2 写操作不能破坏旧快照

若 `UPDATE` 直接覆盖物理记录，或 `DELETE` 立即清除物理槽位，旧事务便无法重建其应看到的版本。

因此必须保存：

- 修改前记录；
- 修改后记录；
- 删除标记；
- 写入事务；
- 提交时间戳；
- 必要的表名和索引更新信息。

### 2.3 SI 必须立即处理写写冲突

题目要求的是 First-Updater-Wins 风格，而不是等待锁：

```text
发现其他活跃事务正在写同一逻辑记录
    -> 当前写语句立即 abort
    -> 回滚当前事务
```

旧快照事务也不能覆盖在其开始后已经提交的新版本。

### 2.4 SER 需要跟踪谓词读

仅记录实际返回的 RID 不够。下面的查询即使返回空集，也可能被之后的插入改变：

```sql
SELECT * FROM account WHERE balance > 1000;
```

因此 SER 事务还必须保存查询条件及列元数据，用于检测：

- 范围读；
- 空结果读；
- 全表扫描；
- UPDATE 前后记录对谓词结果的影响。

### 2.5 输出不匹配不一定真是格式代码错误

评测报告统一显示：

```text
answer mismatches standard answer
```

它既可能是：

- 表格格式错误；
- 多输出了 `failure\n`；
- 少输出或多输出了 `abort\n`；
- 查询结果错误；
- 事务最终状态错误；
- SQL 根本没有被 Parser 接受。

本题最后三个失败点中，真正的最后一处问题就是算术 `UPDATE` 解析失败，服务端因此返回了题目不需要的 `failure\n`。

## 三、总体设计

最终方案将事务处理分为四层：

```mermaid
flowchart LR
    SQL["SET TRANSACTION / BEGIN"] --> SESSION["会话隔离级别"]
    SESSION --> TXN["事务 start_ts 与隔离级别"]
    TXN --> MVCC["MVCC 版本可见性"]
    MVCC --> SI["SI 写写冲突检测"]
    SI --> SSI["SER 读写反依赖与危险结构"]
    SSI --> OUTPUT["空响应 / abort / SELECT 表格"]
```

核心数据结构是：

```text
RecordKey(file_id, RID)
    -> 该逻辑记录的版本序列

txn_id
    -> 事务的快照、读集、写集、谓词、依赖关系和状态
```

版本并不直接依赖物理页是否仍保存当前事务要读取的数据。物理记录只是版本链初始化和最终提交落地的一部分。

## 四、会话级隔离配置

### 4.1 Parser 与执行计划

Parser 将两条语句分别转换为：

```text
SetTransactionIsolation(SnapshotIsolation)
SetTransactionIsolation(Serializable)
```

Optimizer 再生成 `SetTransactionIsolationPlan`。

执行该计划时只更新当前连接的会话状态，不产生客户端输出：

```cpp
*context->session_isolation_ =
    level == SnapshotIsolation
        ? IsolationLevel::SNAPSHOT_ISOLATION
        : IsolationLevel::SERIALIZABLE;
```

### 4.2 会话状态与事务状态分离

每个客户端连接保存：

```cpp
IsolationLevel session_isolation;
```

会话状态表示“以后新事务使用什么隔离级别”。创建事务时才把它复制进 `Transaction`：

```text
会话执行 SET TRANSACTION
    -> 修改 session_isolation

BEGIN 或隐式事务开始
    -> TransactionManager::begin(...)
    -> 保存 isolation_level
    -> 分配 start_ts
```

这样不会在事务执行中途改变其可见性规则。

## 五、MVCC 版本模型

### 5.1 记录标识

使用物理文件标识和 RID 共同标识一条逻辑记录：

```cpp
struct RecordKey {
    uint64_t file_id;
    Rid rid;
};
```

只使用 RID 不够，因为不同表中可能出现相同的页号和槽号。

### 5.2 版本结构

每个版本保存：

```cpp
struct MvccVersion {
    txn_id_t owner;
    timestamp_t commit_ts;

    bool before_deleted;
    vector<char> before;

    bool deleted;
    vector<char> data;

    string table_name;
};
```

字段含义：

| 字段 | 作用 |
| --- | --- |
| `owner` | 创建该版本的事务 |
| `commit_ts` | 提交时间；未提交版本使用 `INVALID_TS` |
| `before` | 写操作前的记录，用于谓词判断、索引更新和恢复 |
| `before_deleted` | 写入前是否不存在该记录 |
| `data` | 写入后的记录 |
| `deleted` | 新版本是否表示删除 |
| `table_name` | 提交时定位表和索引 |

### 5.3 事务状态

SER 还需要额外保存读写信息：

```cpp
struct MvccTxnState {
    IsolationLevel isolation_level;
    timestamp_t start_ts;
    timestamp_t commit_ts;
    bool aborted;

    vector<ReadPredicate> predicates;
    unordered_set<RecordKey> read_records;
    unordered_set<RecordKey> write_records;

    unordered_set<txn_id_t> incoming_rw;
    unordered_set<txn_id_t> outgoing_rw;
};
```

其中：

- `incoming_rw` 表示哪些事务存在 `reader ->rw current`；
- `outgoing_rw` 表示当前事务存在 `current ->rw writer`；
- 已中止事务必须从后续判定中排除。

## 六、快照可见性

### 6.1 时间戳分配

事务开始时：

```text
start_ts = last_commit_ts
```

事务成功提交时：

```text
commit_ts = ++last_commit_ts
```

`last_commit_ts` 单调递增，因此可以直接比较版本是否属于事务快照。

### 6.2 可见版本选择

读取 `(file_id, RID)` 时按以下顺序处理：

1. 若当前事务存在自己的未提交版本，优先返回该版本；
2. 若自己的版本带删除标记，返回不存在；
3. 否则在已提交版本中选择满足 `commit_ts <= start_ts` 的最新版本；
4. 若该版本已删除或不存在可见版本，返回空；
5. 非 SI/SER 事务保持原有物理记录读取方式。

伪代码：

```cpp
for (version : history reverse) {
    if (version.owner == current_txn &&
        version.commit_ts == INVALID_TS) {
        return version.deleted ? nullptr : version.data;
    }
}

visible = max(version.commit_ts)
          where version.commit_ts <= txn.start_ts;

return visible.deleted ? nullptr : visible.data;
```

这同时保证：

- 不读到其他事务的未提交写；
- 同一事务内重复读取结果稳定；
- 当前事务可以读到自己的 INSERT、UPDATE 和 DELETE；
- 旧事务在其他事务提交后仍能读取旧版本。

### 6.3 为什么 MVCC 扫描所有可能槽位

物理 Bitmap 和索引反映的是物理存储状态，不一定等价于某个事务的逻辑快照。例如：

- 当前事务新插入的记录可能尚未提交；
- DELETE 的物理删除被延后；
- UPDATE 的索引键只在提交时更新；
- 旧事务仍可能看到已经被新事务逻辑删除或修改的版本。

因此 SI/SER 顺序扫描使用所有可能的 `(page_no, slot_no)`，再逐个调用 MVCC 可见性判断。这样不会因为当前物理 Bitmap 或新索引键而漏掉旧快照记录。

## 七、三种写操作

### 7.1 INSERT

INSERT 的物理记录和索引项需要立即创建，以获得稳定 RID，并复用框架现有的 WAL 与回滚机制；同时在版本表中登记当前事务的未提交插入版本。

事务内读取时可以看到该版本，其他事务看不到。

若事务回滚：

```text
删除物理记录与索引项
删除该事务的未提交 MVCC 版本
```

### 7.2 UPDATE

SI/SER 下不能立即覆盖物理记录。执行 UPDATE 时：

1. 通过快照读取当前可见旧记录；
2. 生成 `rec_new`；
3. 检查记录级写写冲突；
4. 检查唯一索引冲突；
5. 保存未提交新版本；
6. 保存 WAL 和事务写集；
7. 暂不修改物理记录和索引。

提交时才：

```text
物理记录写入新值
删除旧索引项
插入新索引项
将版本标记为已提交并分配 commit_ts
```

回滚时只需要移除未提交版本，不应再用普通回滚逻辑覆盖物理记录，因为 SI/SER 的 UPDATE 本来没有提前修改物理页。

### 7.3 DELETE

DELETE 与 UPDATE 类似：

1. 保存删除前记录；
2. 创建带 `deleted=true` 的未提交版本；
3. 当前事务读取时视为不存在；
4. 其他事务仍按各自快照读取旧版本；
5. 提交时删除索引项；
6. 保留必要的物理内容用于旧版本重建和恢复。

早期若立即执行物理删除，会使旧快照无法重建被删元组，并导致 `TupleReconstructTest` 失败。

### 7.4 事务内先 INSERT 再 UPDATE

这是一个容易遗漏的组合：

```sql
BEGIN;
INSERT INTO t VALUES (1, 10);
UPDATE t SET id = 2, val = 20 WHERE id = 1;
COMMIT;
```

第一次 INSERT 创建了自己的 pending version。随后 UPDATE 必须更新同一个 pending version，并保留正确的 `before`、`data` 和表名。

提交时不能因为 `before` 为空就跳过物理同步，否则最终物理记录仍然是 `(1, 10)`，而逻辑版本已经变成 `(2, 20)`。

最终实现会在这种情况下保存 INSERT 后的记录作为 UPDATE 的提交前状态，提交时正确更新物理记录和索引。

## 八、SI 写写冲突

### 8.1 活跃写者冲突

如果记录版本链中存在另一个未中止事务的未提交版本：

```text
version.owner != current_txn
version.commit_ts == INVALID_TS
```

当前事务必须立即中止：

```cpp
throw TransactionAbortException(
    txn_id, AbortReason::WRITE_CONFLICT);
```

不能等待另一个事务释放锁，否则交叉更新会形成传统死锁。

### 8.2 旧快照写入冲突

若记录最新提交版本满足：

```text
latest_commit_ts > current_txn.start_ts
```

说明当前事务正基于旧快照写入，必须 abort，防止丢失更新。

典型调度：

```text
T1 BEGIN，读取 val=100
T2 BEGIN，更新为 200 并 COMMIT
T1 再次读取仍为 100
T1 尝试更新为 150
```

T1 的第二次读取应保持 100，但 UPDATE 必须返回 `abort\n`，最终值保持 200。

### 8.3 交叉更新与“死锁”测试

题目中的 Deadlock 测试本质上验证的是“冲突时立即选择受害者”，不是等待图检测：

```text
T1 写记录 A
T2 写记录 B
T1 再写记录 B -> abort T1
T2 再写记录 A -> 成功
```

关键修复是：

- 冲突事务在抛异常前标记为 aborted；
- 其他事务检查版本链时忽略已中止事务留下的 pending version；
- 服务端捕获异常后完成完整回滚并释放事务；
- 不让两个事务在同时交叉更新时都看到对方为有效写者而双双 abort。

这样同时交叉更新时只选择一个受害者，另一个事务能够继续提交。

### 8.4 唯一索引冲突

UPDATE 可能改变唯一索引键。仅检查目标 RID 不够，还要检查新键是否与其他记录的以下版本冲突：

- 其他事务尚未提交的新版本；
- 当前事务快照之后提交的新版本；
- 当前索引中已经存在的其他 RID。

发现有效冲突时按照 SI 写写冲突返回 `abort\n`，而不是普通 `failure\n`。

## 九、SER 与 SSI 判定

### 9.1 记录读与谓词读

SER 的 SELECT 保存两类信息：

```text
read_records：实际读取到的 RecordKey
predicates：表、条件列表和列元数据
```

即使查询结果为空，也必须保存谓词。

### 9.2 SELECT 建立 reader ->rw writer

执行 SELECT 时，除了按快照返回结果，还检查其他 SER 事务已经产生、但当前快照不可见的写入。

若该写入会改变本次查询结果，则建立：

```text
current_reader ->rw writer
```

这一步只记录依赖，不改变 SELECT 的快照结果。

### 9.3 写语句建立 reader ->rw current_writer

执行 INSERT、DELETE 或 UPDATE 时，将受影响记录与其他 SER 事务保存的读信息比较：

- INSERT 检查新记录；
- DELETE 检查删除前记录；
- UPDATE 同时检查更新前和更新后记录；
- 若记录曾被其他事务读取，或新旧记录命中其谓词，则建立：

```text
reader ->rw current_writer
```

### 9.4 UPDATE 为什么检查前后两个版本

假设读事务执行：

```sql
SELECT * FROM t WHERE score >= 60;
```

下面两种 UPDATE 都会改变其查询结果：

```text
50 -> 70：记录进入结果集
70 -> 50：记录离开结果集
```

因此谓词影响判断必须是：

```text
before_matches || after_matches
```

### 9.5 危险结构

题目定义的 SSI 危险结构为连续两条 rw 反依赖：

```text
Tin ->rw Tpivot ->rw Tout
```

相关事务必须存在执行区间重叠，并满足：

```text
Tin == Tout
```

或 `Tout` 的提交顺序早于 `Tin`。

每次新增依赖后立即检查。若新增依赖形成危险结构：

```text
中止新增该依赖的当前语句所在事务
返回 abort\n
清理该事务产生的依赖、读集、谓词和写集
```

这使 SER 能够阻止写偏序，而 SI 仍允许两个事务更新不同记录。

## 十、提交、回滚与第十题兼容

### 10.1 提交

成功提交时：

1. 沿用框架原有 WAL 提交流程；
2. 分配单调递增的 `commit_ts`；
3. 将 UPDATE 的新值写入物理记录；
4. 更新发生变化的索引键；
5. 提交 DELETE 的索引删除；
6. 将本事务 pending version 转换为 committed version；
7. 清理普通事务运行期资源。

### 10.2 回滚

回滚时区分写操作的物理执行方式：

- INSERT 已经物理执行，继续使用框架原有回滚恢复表和索引；
- SI/SER UPDATE 和 DELETE 未提前改动对应物理内容，不能再重复执行物理回滚；
- 删除当前事务所有未提交版本；
- 清理读集、谓词、写集和 rw 依赖；
- 标记事务已中止，使其他事务不再把它视为有效冲突写者。

### 10.3 为什么不能随意绕开 WAL

第十题依赖 INSERT、UPDATE、DELETE、COMMIT 和 ABORT 日志恢复数据库状态。第九题若只在内存版本表中修改数据而不保留原有日志链路，会出现：

```text
第九题运行时测试通过
系统重启后数据丢失或恢复错误
```

因此最终方案保留了原有日志生成、提交刷盘和事务写集，只调整 SI/SER 下物理修改发生的时机。

## 十一、算术 UPDATE 的补全

### 11.1 最终隐藏问题

本地 22 个并发测试全部通过后，官方评测仍固定失败：

```text
si/Deadlock
si/Non_Repeatable_Read_Lost_Update
si/UpdateTest
```

反复核对客户端表格、`abort\n` 和成功空响应后，发现评测使用了类似语句：

```sql
UPDATE account SET balance = balance + 10 WHERE id = 1;
UPDATE account SET balance=balance-5 WHERE id=1;
UPDATE account SET balance = balance * 2 WHERE id = 1;
```

原 Parser 只支持：

```sql
SET column = constant
```

因此语句在进入 MVCC 执行器之前就解析失败，并返回：

```text
failure
```

评测看到的仍是“答案不匹配”，看起来像事务或输出格式错误。

### 11.2 AST 与语义结构

`SetClause` 增加：

```text
rhs_col_name
arithmetic_op
is_arithmetic
```

常量赋值仍使用原路径，算术赋值保存：

```text
目标列 = 源列 运算符 常量
```

### 11.3 语法支持

最终支持：

```sql
col = value
col = col + value
col = col - value
col = col * value
col = col / value
```

同时兼容：

```text
col=col+1
col = col + 1
```

词法器需要显式识别 `+`、`-`、`*`、`/`，并保留原有带符号数值字面量。

### 11.4 执行

执行 UPDATE 时从当前事务可见的旧记录中读取源列，再按类型计算：

```text
INT   -> 整数运算
FLOAT -> 单精度浮点运算
```

结果写入 `rec_new`，之后继续走完全相同的：

```text
冲突检测
唯一索引检测
MVCC pending version
WAL
提交或回滚
```

不能为算术 UPDATE 另写一条绕开事务系统的物理更新路径。

## 十二、输出格式

本题输出要求非常严格。

### 12.1 成功语句

以下语句成功时客户端响应必须为空：

```text
SET TRANSACTION ISOLATION LEVEL ...
BEGIN
COMMIT
ROLLBACK
INSERT
UPDATE
DELETE
```

不能输出：

```text
success
OK
affected rows
事务编号
调试日志
```

### 12.2 冲突

写写冲突或 SSI 危险结构只返回：

```text
abort\n
```

不能返回异常详情，也不能返回 `failure\n`。

服务端同时向 `output.txt` 追加：

```text
abort
```

### 12.3 SELECT

客户端保持框架原有的完整表格：

```text
+------------------+------------------+
|               id |              val |
+------------------+------------------+
|                1 |              100 |
+------------------+------------------+
Total record(s): 1
```

`output.txt` 则继续使用框架原有的紧凑行格式，例如：

```text
| id | val |
| 1 | 100 |
```

不要为了第九题自行改变通用 `RecordPrinter` 或 `output.txt` 格式，否则可能干扰其他题目。

## 十三、中间错误与正确修复

### 13.1 只看官方测试名，误以为全是 MVCC 算法错误

最初得分为：

```text
17.60
```

失败点始终是：

```text
si/Deadlock
si/Non_Repeatable_Read_Lost_Update
si/UpdateTest
```

这些名字确实指向写冲突和 UPDATE，但不能据此断定所有失败都发生在版本可见性代码中。最后证明其中还包含 Parser 不支持算术 UPDATE 的问题。

正确排查方法是逐层验证：

```text
Parser
  -> Analyzer
  -> Planner
  -> Executor
  -> MVCC
  -> 客户端响应
  -> output.txt
  -> 最终物理状态
```

### 13.2 为修复冲突过度修改会话状态

一次错误修改改变了事务异常后的会话与事务重建行为，导致分数从 `17.60` 降到 `16.80`，并新增：

```text
si/TupleReconstructTest
```

问题在于把“事务已经中止”与“会话以后不能继续执行”混在了一起，同时影响了原有恢复和元组读取路径。

最终做法是：

- 冲突时只回滚当前事务；
- 保留会话配置的隔离级别；
- 释放已中止事务对象；
- 后续语句按框架规则创建新事务；
- 不额外向客户端输出状态信息。

### 13.3 DELETE 立即物理删除

早期 DELETE 在 SI/SER 下直接清除 Bitmap 和索引，导致：

- 旧快照无法重建元组；
- 删除冲突最终状态错误；
- TupleReconstruct 失败；
- 可能干扰第十题恢复。

最终改为：

```text
执行 DELETE -> pending tombstone
COMMIT       -> 删除索引并提交删除版本
ROLLBACK     -> 移除 tombstone
```

并保留旧记录内容供快照读取。

### 13.4 UPDATE 提前物理覆盖

若 UPDATE 在语句执行时立即修改物理记录，其他旧事务只能看到新值，即使版本表中保存了旧值，索引和扫描入口也可能已经改变。

最终改为：

```text
语句执行阶段只生成 pending version
提交阶段再更新物理记录和索引
```

### 13.5 INSERT 后 UPDATE 没有同步物理状态

事务内 INSERT 再 UPDATE 时，版本链结果正确，但提交代码只处理“有旧物理版本”的 UPDATE，导致最终物理记录仍是 INSERT 时的值。

正确修复是在合并同一事务 pending version 时保存必要的提交前数据，使 COMMIT 能识别并同步物理记录及索引。

### 13.6 交叉更新导致两个事务都 abort

同时执行交叉 UPDATE 时，两个线程可能都先看到对方的 pending version，最终返回：

```text
['abort\n', 'abort\n']
```

这不符合“选择一个受害者”的预期。

最终解决方式：

1. 冲突事务立即标记为 aborted；
2. 另一个事务扫描版本链时忽略 aborted owner 的 pending version；
3. 后台异常处理继续清理受害事务版本；
4. 存活事务完成其第二次 UPDATE 并提交。

### 13.7 唯一键冲突返回空响应

并发 UPDATE 到相同唯一键时，曾出现冲突没有被转换成 `abort\n`，客户端收到空字符串。

正确做法是在真正修改索引前，对版本表和索引结果统一检查；若冲突来自并发写者或快照之后的新版本，则抛出 `TransactionAbortException`，进入统一 abort 输出路径。

### 13.8 只用本地测试证明正确

本地测试从 11 项逐步扩展到 22 项，全部通过后官方仍然只有 `17.60` 分。

原因是本地测试只覆盖了：

- 常量 UPDATE；
- SI/SER 并发调度；
- 索引变化；
- 删除与插入；
- 元组重建；
- 同时交叉更新。

却没有覆盖：

```sql
SET score = score + 5.5
```

最终增加第 23 项算术 UPDATE 测试，同时在 `test_parser` 中加入带空格和不带空格的表达式。官方评测随后达到 `20.00`。

### 13.9 把所有 answer mismatch 都当成表格空格问题

客户端 SELECT 表格与原始 `RecordPrinter` 一致，成功写语句也确实为空，冲突也严格为 `abort\n`。继续调整列宽或分隔线不会解决 Parser 返回 `failure\n` 的问题，反而可能破坏其他已经通过的测试。

正确做法是先抓取每条 SQL 的原始响应：

```text
repr(response)
```

区分：

```text
''          -> 正确的成功空响应
'abort\n'   -> 正确的冲突响应
'failure\n' -> 解析、分析或普通执行异常
表格文本     -> SELECT 输出
```

## 十四、优化与工程处理

### 14.1 统一版本锁

版本链、事务 MVCC 状态和依赖图由同一把 `mvcc_latch_` 保护，避免并发检查与写入之间出现数据竞争。

在持锁区域内只做内存状态判断；客户端 I/O、表格输出和普通 SQL 执行不持有该锁。

### 14.2 冲突检测前置

UPDATE 先进行：

```text
记录冲突检查
唯一键冲突检查
```

通过后才登记 pending version 和 WAL，避免执行到一半才发现冲突而留下部分状态。

多行 UPDATE 中若后续记录冲突，异常处理会回滚整个事务，而不是只撤销当前一行。

### 14.3 pending version 合并

同一事务多次修改同一记录时，不为每次 UPDATE 无限追加独立未提交版本，而是更新自己的 pending version：

```text
before 保持事务第一次写入前状态
data 保存当前最后结果
deleted 保存当前逻辑删除状态
```

这样可以正确支持：

- UPDATE 后再次 UPDATE；
- INSERT 后 UPDATE；
- UPDATE 后 DELETE；
- 事务内读己之写。

### 14.4 延迟索引更新

SI/SER UPDATE 和 DELETE 的索引变化推迟到 COMMIT：

- 旧事务仍能通过全槽位扫描和版本可见性读取旧值；
- 未提交索引键不会污染其他事务；
- 回滚不需要重复恢复尚未物理修改的索引；
- 唯一键冲突在提交前完成检测。

### 14.5 不用等待锁处理 SI 写冲突

本题要求冲突立即 abort，因此 SI/SER 路径不应先进入传统行锁等待。版本链检查直接选出当前语句为受害者，避免真正的等待死锁和评测超时。

### 14.6 测试按风险逐步扩展

最终本地测试覆盖：

- INSERT 的事务内可见性；
- 脏读；
- UPDATE/DELETE 写写冲突；
- SI 写偏序；
- 顺序和同时交叉更新；
- 不可重复读与丢失更新；
- 索引键变化；
- 唯一键冲突；
- INSERT 后 UPDATE；
- 多行 UPDATE 原子回滚；
- 元组删除重建；
- 隐式事务；
- 类型化 UPDATE；
- 算术 UPDATE；
- SER 重复读、空谓词和写偏序。

这种测试方式比只复现官方三个测试名更容易发现共同根因。

## 十七、最终解决方式

本题最终满分方案可概括为：

```text
会话级隔离配置
+ BEGIN 时固定 start_ts
+ RecordKey -> 版本链
+ 优先读取本事务 pending version
+ 读取 commit_ts <= start_ts 的最新已提交版本
+ UPDATE/DELETE 延迟物理修改
+ INSERT 保留原有物理写入与回滚链路
+ 活跃写者冲突立即 abort
+ 快照后提交版本阻止旧快照写入
+ 唯一索引版本冲突检查
+ SER 记录 RID 读与谓词读
+ 建立 rw 反依赖
+ 新依赖形成危险结构时中止当前事务
+ 中止事务依赖和版本完整清理
+ 严格的空响应、abort\n 和 SELECT 表格
+ 算术 UPDATE Parser、Analyzer 与 Executor 支持
+ 保留 WAL 与第十题恢复兼容性
```

最关键的经验是：并发题的“答案不匹配”不能只盯着锁和版本链。必须从 SQL 是否成功解析开始，一直检查到客户端响应、`output.txt` 和最终物理数据库状态。

本题最后从长期停留的 `17.60` 提升到 `20.00`，并不是再次修改表格列宽，而是补齐了隐藏测试实际使用的算术 UPDATE，使合法语句不再错误地产生 `failure\n`。这也是整个排查过程中最容易被“输出格式问题”表象掩盖的一点。
