## 并发优化01: MVCC \-\> MV2PL

尽管MVCC通过版本快照控制实现了读操作的并发性，但在同一日志上的写操作却无法并发执行，这就迫使第二个事务进行回滚，从而导致较高的回滚率。为了解决这一问题，我们在MVCC的基础上对其进行了升级，提出了MV2PL

- **多版本管理**：系统为每个数据项维护多个版本，每次写操作都会创建一个新的数据版本，而不会覆盖原有数据。这样，读操作可以读取到稳定的快照版本，避免了读写冲突。

- **两阶段锁协议**：MV2PL通过两阶段锁定协议来管理事务的并发性。事务首先获取所需的锁，并在执行过程中保持锁定状态，直到事务完成并释放锁。锁的获取和释放分别遵循“增长阶段”和“收缩阶段”原则，以确保操作的顺序性和一致性。

- **回滚机制**：当发生写冲突（即两个事务试图在同一数据项上进行写操作）时，当前的实现采用以下策略：

    1. **新事务回滚**：如果一个新事务试图修改一个数据项，而该数据项已经被一个较早的事务修改并未提交，则为了防止死锁，新事务会选择回滚。这样避免了事务间的循环等待，并保证了系统的可操作性。

    2. **老事务等待**：如果一个较老的事务试图修改一个数据项，而该数据项已经被一个新事务修改，则该老事务会进入等待状态，直到新事务提交或回滚。这种设计减少了过多的回滚操作，从而提高了系统的并发性和效率。

### 缓存优化01: LUR \-\> LRU\-K

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ZWM1MzZlZDVmNmYwOTk2OGQ3ZjQxMDNmNDlkNGEyYjVfMGExNWNmNWQ0YTEyNDkwNWIzOTA5ZGFlMTM3Yzk2MjFfSUQ6NzUzODM1NzU4OTE2NDg2NzU4N18xNzg2NzMyMDc1OjE3ODY4MTg0NzVfVjM)

在执行`Select`相关语句的时候，我们发现缓存管理器的时间开销很大，于是我们决定优化。

|对比维度|LRU（Least Recently Used）|LRU\-K（Least Recently *K* Times Used）|
|---|---|---|
|**核心思想**|淘汰最近最久未访问的页面（只看最近一次访问时间）|淘汰**第 K 近**一次访问时间最早的页面（考虑最近 K 次访问时间）|
|**优点**|实现简单，O\(1\) 插入和删除|有效过滤一次性访问（One\-time Access），识别“真正热点”|
|**适用场景**|热点稳定、访问模式较均匀|存在大量一次性访问、顺序扫描或热点切换明显的负载|

1. **访问记录**

    - 每个页面维护一个**最多 K 个时间戳**的队列（按访问时间递增）。

    - 每次 `unpin` 表示一次访问，逻辑时钟自增并记录到该页面的时间戳队列中。

2. **集合划分**

    - **History 区**：访问次数 `< K` 的页面，按最近一次访问时间排序（普通 LRU 逻辑）。

    - **Candidates 区**：访问次数 `≥ K` 的页面，按“第 K 近”访问时间排序（LRU\-K 核心）。

3. **淘汰策略**

    - `victim()` 时优先从 **Candidates 区** 中选择 **第 K 近访问时间最早**的页面淘汰。

    - 若 Candidates 区为空，则从 **History 区** 按普通 LRU 淘汰。





## 读写优化01: load\_table

> 我们实现了基于批量插入的`load_table`功能。每次获取表中的一个有空位的内存页时，直接批量获取该页上面所有空闲位置，实现一次性批量插入。对于每一个空页，最多只需要获取一次，大大减少了获取页的开销。
> 
> 



在海量数据装载过程中，逐条插入会频繁触发“找空位→写入→解锁”的流程，形成明显瓶颈。我们采用 **批量插入策略**：

- **一次性发现空位**：扫描页时直接获取所有空槽位置，避免逐条查找。

- **集中写入**：固定（pin）页的整个生命周期内完成多条插入，彻底消除反复 pin/unpin 开销。

- **吞吐量大幅提升**：装载阶段趋近于顺序 I/O，充分利用缓存和内存带宽。
 → 特别适用于 **建表初始数据加载** 或 **大批量导入场景**。



## 读写优化02: Index \- join

在基础的NestedLoopJoin 执行过程中，数据库需要对外表的每一行记录在内表中逐一扫描，从而带来较高的 I/O 开销和 CPU 开销。我们在实现中引入了 **索引连接（Index\-Join）** 优化策略：

- **外表驱动**：首先扫描外表记录，获取连接键值；

- **索引查找**：利用内表上已经建立的索引，快速定位到匹配的记录位置，而无需进行全表扫描；

- **逐条匹配**：对外表的每条记录都能通过索引高效地找到内表的候选集合，大幅降低连接操作的复杂度；

- **减少无效访问**：避免了在内表中大量不必要的顺序扫描，仅在索引路径下访问需要的候选记录；

- **性能提升**：在连接条件匹配性较强、外表行数适中时，该策略能显著减少 I/O 和 CPU 开销，实现近似于索引查找的性能提升。

整体上，Index\-Join 的优化使得连接操作更加接近 “点查找” 的效率，特别适合 **内表建立了索引**、**连接条件选择性较好** 的场景。



## 读写优化03: bitmap优化

在传统bitmap实现中，查找第一个符合条件的bit位通常需要逐位遍历，效率较低。我们提出一种基于字符比较的优化策略：将bitmap按8位一组（1字节）进行组织，通过检测字节值是否全0（查找1时检测0xFF）来快速定位目标区间。

1. 字节级粗筛：通过整字节比较快速定位第一个非零字节（查找1时即首个0xFF字节）

2. 位级精查：在目标字节内部进行逐位检测



## 读写优化04: batch\_rm\_scan \& batch\_ix\_scan

常规扫描器逐次解析页头位图（bitmap）寻找下一个有效槽位，可能导致对同一页的页头频繁解码。我们改进为 **位图批量解析**：

- **整页解析**：一次性提取当前页头 bitmap 中的全部有效 `Rid`。

- **单次访问**：每个页头在一次扫描中仅解码一次，避免了多次重复解析。

- **更少的锁与 I/O**：减少了对缓冲页的重复固定，降低锁竞争。
 → 优化点在于 **扫描器内部机制**，相比于 Seq Scan / Index Scan 的页级优化，这是更贴近存储结构的改进。



## 读写优化05: batch\_seq\_scan

顺序扫描中，传统的逐条记录返回模式存在大量函数调用和上下文切换。我们实现 **页级批处理**：

- **整页搬运**：一次读出页内所有可见记录并缓存，避免行级迭代。

- **CPU 缓存友好**：利用物理连续性提升 cache 命中率和磁盘顺序读效率。

- **算子解耦更轻量**：算子之间交互由“逐行”变为“整页”，显著减少接口调用。
 → 特别适合 **分析型查询** 和 **大表全表扫描**，能显著提高吞吐率。



## 读写优化06: batch\_index\_scan

索引扫描的开销主要来自“索引项分散 → 页随机访问”。我们采用 **索引批量预取 \+ 页聚合** 技术：

- **预取索引范围**：初始化阶段一次性取出所有目标索引项并排序。

- **聚合访问**：将同一页上的多个索引请求合并为一次访问，避免页反复 pin/unpin。

- **I/O 局部性提升**：批量访问遵循索引顺序，使 I/O 更接近顺序访问。
 → 优势体现在 **范围查询、批量点查和索引连接**，相比逐条索引查找，性能提升尤为明显。



## 读写优化07: fast\_count 

FastCount旨在优化不包含`WHERE`条件的单表`COUNT`语句，例如：

```SQL
SELECT COUNT(*) FROM t1
```

我们采用双层结构来进行优化，具体思路如下：首先在记录存储层面进行处理，在记录文件中保存总记录数，并在每个数据页上记录该页的记录数。为了满足可见性约束，我们在记录文件和内存页中都加入了最新修改的时间戳。对于`COUNT`语句的执行，如果查询的时间戳大于记录文件的修改时间戳，则可以直接返回总记录数；如果查询时间戳小于修改时间戳，则需要遍历每个数据页。当查询时间戳大于某页的时间戳时，可以直接加上该页的记录数；否则，需要逐条检查该页的记录可见性，最终计算出准确的`COUNT`结果。

## 读写优化08: fast\_min

FastMin旨在优化带有索引的`MIN()`聚合函数，例如：

```SQL
SELECT MIN(id) FROM t1 WHERE CONDITIONS;
```

当`MIN(value)`中的`value`是与某个索引的前缀匹配时，可以根据此进行优化。具体方法是，根据`WHERE`条件生成的`LowerKey`来确定最小的约束，然后沿着B\+树索引从该约束开始向后查找，找到第一个符合条件且可见的值即可。
