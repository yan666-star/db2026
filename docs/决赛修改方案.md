# 决赛性能修改方案（百倍挑战路线）

更新时间：2026-08-12
正确性基线：`9e657d2907e4928744c6511ddf9ba2280fad9c2e` 对应的 `src/`
配套红线：`docs/正确性门槛关键要求.md`

## 一、目标与结论

正式排行榜取 32 客户端、50 仓库、3 个 150 秒窗口的 NewOrder/min 中位数。当前成功基线为 28 NewOrder/min，已经通过全部功能、持久化、LOAD、在线一致性和 SIGKILL 恢复门禁，但距离高性能实现仍有数量级差距。

本方案把 `28 → 2,800+ NewOrder/min` 设为百倍挑战目标，不承诺某项改动必然达到该数值。百倍提升不可能依靠一两处共享锁替换获得，必须同时消除事务、heap、索引和 WAL 四条主路径上的全局串行化，并把提交改造成短而清晰的持久化发布路径。

最终目标架构：

```text
PREPARE_SET 生成不可变执行模板
        ↓
EXEC_BATCH 仅绑定参数和创建轻量运行态
        ↓
MVCC 快照读取：直接访问物理基线 + 可见版本，不走逐记录全局屏障
        ↓
写入：事务私有版本 + RecordKey 写意向；heap/index 只做并发安全的私有安装
        ↓
COMMIT：冲突校验 → COMMIT WAL → group fsync → 原子发布 commit_ts
        ↓
后台物化、GC、checkpoint：不阻塞普通事务，恢复仍可由 WAL 重建
```

设计原则：

1. 先建立正确提交线性化，再缩短提交临界区；不能以提前可见换吞吐。
2. 优先消除等待和放弃，不先做单行复制、字符串或容器微优化。
3. 热路径按 `RecordKey`、page、index leaf 和 WAL batch 分片，不按表名或事务名特判。
4. 每阶段必须形成可独立回退的提交，并通过 `docs/正确性门槛关键要求.md` 的回归矩阵。

最重要的组合证据是：低 CPU、极高 NewOrder 延迟、高放弃率和大量零提交时间桶同时出现。这更符合“线程被锁、条件变量、同步 I/O 或串行提交链阻塞”，而不是 CPU 算子计算已经饱和。当前第一优先级不是减少几次内存复制，而是把等待链拆开。

不同正式评测的随机数据和运行环境不完全相同，不能把一次平台分数当作精确 A/B。后续必须使用同一数据库快照、同一负载种子和至少三次重复运行做本地单变量实验。

### 2.2 当前源码中的结构性上限

#### A. 每次记录读取经过全局提交屏障

`RmFileHandle::get_record()` 和 `batch_get_records()` 会获取 `commit_apply_latch_` 的共享锁；提交版本发布、GC 和 checkpoint 会获取独占锁。一个 NewOrder 包含多次索引查找和记录读取，32 个连接会不断进入同一个共享锁，独占提交又必须等待此前读者退出。

这会形成闭环：

```text
大量逐记录共享锁
→ 提交独占锁等待
→ 已占有业务资源的事务迟迟不能结束
→ 后续事务冲突或等待
→ 放弃率与尾延迟上升
```

不能简单改成 writer-priority 锁。writer-priority 会在写者出现后阻止所有新读者，容易把局部提交等待放大为整个数据库的读队头阻塞。正确终态是让普通可见性判断不需要这把全局锁。

#### B. `txn_state_latch_` 承担过多全局事务状态

当前 transaction manager 已有 64 个 MVCC shard，但事务表、依赖图、时间戳、部分冲突检查和生命周期仍频繁经过 `txn_state_latch_`。只要锁内发生 heap/index 访问、容器扩容、集合遍历或条件等待，所有事务都会串行。

#### C. heap 的 `insert_latch_` 是整表 DML 互斥

当前 `RmFileHandle` 使用单个 `std::mutex insert_latch_` 保护：

- RID 分配和 free-list；
- INSERT；
- UPDATE；
- DELETE；
- 整数等值缓存构建与维护；
- 全记录槽枚举。

因此同一张 stock、district、orders 或 order_line 表上的不同页面也无法并行修改。TPC-C 大部分写入集中在少数几张表，这直接限制多核利用率。

#### D. 每个 B+ 树索引写独占整棵树

`IxIndexHandle::insert_entry()` 与 `delete_entry()` 在整个操作期间独占 `root_latch_`。不同叶页的插入、删除也串行；split/merge 期间持锁更久。NewOrder 需要插入 orders、new_orders、order_line 并访问 stock 等索引，整树锁会形成第二条全局写队列。

#### E. 提交路径发布过早，且之后仍做物理应用

当前 `commit_mvcc()` 先分配并写入 `commit_ts`，释放 `commit_apply_latch_`，再进行 heap/index Phase 2；外层 `commit()` 最后追加 COMMIT WAL 并 `force_flush_up_to()`。该顺序虽通过本次自动测评，但不应作为合规终态，详见正确性文档。

性能上它同样不理想：每个提交既要管理全局版本发布，又要逐项更新 heap/index；冲突若在物理阶段才暴露，会浪费整个事务的执行工作并触发昂贵回滚。

#### F. 已有 group commit 仍缺少批次证据

`LogManager::force_flush_up_to()` 已有 leader/waiter 和默认 1 ms 聚合窗口，且 waiter 会检查 `durable_lsn`。方向正确，但当前没有以下数据：

- 每秒 WAL append、write、fsync 次数；
- 每次稳定化覆盖多少个 COMMIT；
- leader 等待、write、fsync 和 waiter 唤醒耗时；
- 1 ms 窗口是否在当前机器上过长或过短。

在锁瓶颈没有拆除前，提交到达稀疏，group commit 也无法形成有效批次。

#### G. Prepared 路径仍有可复用空间

PREPARE_SET 已缓存 plan，但每次 `execute_prepared()` 仍会在共享 plan 上执行参数绑定并重新创建 portal/executor 运行态。若绑定直接修改共享 plan，还必须证明不同连接的 plan 实例隔离。优化目标是“不可变模板 + 每次调用的轻量参数槽和执行状态”，而不是跨连接共享可变 AST/plan。

## 三、收益目标分解

百倍目标采用阶段带宽，不把各阶段倍数机械相乘：

| 阶段 | 挑战区间 | 必须出现的信号 |
| --- | ---: | --- |
| 基线 | 28 | 全部门禁 PASS |
| M0 可观测性 | 结果不作要求 | 能解释 90% 以上事务时间去向 |
| M1 消除无效等待 | 80～250 | 零提交桶显著下降，完成率 >95% |
| M2 提交与 MVCC 重构 | 300～900 | 普通读无全局屏障，提交临界区进入亚毫秒级 |
| M3 heap/index 页级并发 | 800～1,800 | 平均 CPU 达 6～10 核，不同页写并行 |
| M4 prepared/写集合并/WAL 调优 | 1,500～3,000+ | NewOrder p50 降至亚秒级，fsync 批次稳定 |
| M5 稳定性与恢复收口 | 保持峰值的 90% 以上 | 三轮差异小、无零提交桶、恢复 <60 秒 |

阶段区间是工程目标，不是预测结果。若 M1 完成后吞吐仍无明显变化，必须根据 profile 重新排序，不得为了追赶表格继续叠加未归因改动。

## 四、M0：先建立性能证据

### 4.1 必须增加的低开销计数

在 `RMDB_PERF_DIAG=1` 时输出进程内聚合值，默认关闭，不输出逐事务日志：

| 子系统 | 指标 |
| --- | --- |
| 事务 | begin/commit/abort、五类 abort reason、活动事务峰值 |
| MVCC | prepare_read/write 次数、shard 等待、`txn_state_latch_` 等待、pending wait 次数与耗时 |
| 提交 | validate、WAL append、durable wait、publish、cleanup 分段耗时 |
| heap | 每表 insert/update/delete 次数，file/page latch 获取、总等待、最大等待 |
| index | 每索引 lookup/insert/delete、root/leaf 等待、split/merge 次数与耗时 |
| WAL | append bytes、buffer flush、write、fsync、group size、leader/waiter 时间 |
| Buffer Pool | hit/miss、dirty eviction、无空闲 frame 等待、磁盘读写 |
| 执行 | 每 prepared statement 的调用、成功、abort、执行总时长和最大时长 |

计数器必须使用 thread-local 累加后批量归并，避免把诊断原子操作本身变成热点。不得记录运行时表名、SQL、参数和测试数据。

### 4.2 M0 验收

- 诊断关闭时相对基线吞吐差异不超过自然波动。
- 能区分“等待锁”“等待 fsync”“执行扫描”“回滚”和“发送响应”。
- 32 客户端的一次测试中，所有分段时间能大致解释端到端延迟。
- 后续每个阶段只根据实际占比决定是否进入。

## 五、M1：先消除超时、放弃和队头阻塞

### 5.1 基于完整 `RecordKey` 的早期写意向

热点冲突目前可能执行到提交才失败。建议增加通用写意向表：

- key 为 `(mvcc_file_id, Rid)`，不使用表名和事务类型；
- 当 UPDATE/DELETE/INSERT 的真实 RID 已解析后立即申请；
- 多 key 按稳定全序申请，防止 AB-BA 死锁；
- 同事务重复写同一 key 直接复用；
- 等待超过短预算时返回可重试 `TRANSACTION_ABORT`，不能无限卡住 EXEC_BATCH；
- 事务 COMMIT、ABORT、断连和 AUTO_ABORT 都必须释放；
- 等待后必须重新检查快照、版本和唯一约束。

NewOrder 的全部 stock key 在第一依赖阶段可由已绑定参数得到时，应按 `(供货仓, 商品)` 排序去重后申请；如果某条通用执行路径尚不知道完整 key，就在 key 解析出来时再申请，不能按“这是 NewOrder”写专用分支。

收益来源不是减少真实冲突，而是让冲突事务在做大量 heap/index/WAL 工作前有序排队或快速失败。

### 5.2 admission control 只作为过载保护

32 个连接不等于必须让 32 个写事务同时进入最拥塞的提交阶段。根据活动写事务数、pending wait 和 durable queue 做自适应 admission：

- 只限制正在占用稀缺写资源的事务；只读事务不共用一个总令牌；
- 水位由队列长度和等待时间反馈调节，不写死“官方是 32 客户端”；
- 被限流的事务尚未持有 heap/index latch 或写意向；
- admission 等待计入诊断，并设可控上限。

它用于阻止过载崩塌，不是长期掩盖全局锁。

### 5.3 M1 验收

- NewOrder 与 Payment 完成率均达到 95% 以上。
- 三轮零提交 5 秒桶总数从 60 降到不超过 3。
- 不发生 60 秒 batch response timeout。
- p99 不以超过自然波动的 abort 增长换取吞吐。
- SI/SER、AUTO_ABORT 和多 key 死锁回归全部通过。

## 六、M2：重构提交与 MVCC，可见性不再依赖全局读锁

这是百倍路线的核心阶段，也是正确性风险最高的阶段。不能在一个提交中同时修改所有细节，分四步完成。

### 6.1 M2-A：定义不可变提交状态机

为事务明确状态：

```text
ACTIVE
→ VALIDATING
→ WAL_DURABLE
→ COMMITTED_VISIBLE
→ CLEANED

任一可失败点：ACTIVE/VALIDATING → ABORTING → ABORTED
WAL_DURABLE 之后不得普通回滚
```

`commit_ts` 只有在 COMMIT WAL 已 durable、物理私有状态已完整安装且提交不再失败后才能对新快照可见。状态转换使用 release/acquire 语义或在对应 shard latch 下完成。

### 6.2 M2-B：私有版本与物理基线分离

建议采用“稳定物理基线 + 内存 MVCC delta”的通用结构：

- UPDATE/DELETE 在事务执行期只写事务私有 version，不改共享 heap 基线；
- INSERT 可以预留 RID 并写入物理槽，但必须由 pending owner/version 标记隐藏；
- 读取先按 `RecordKey` 查本事务版本、可见 committed delta，再回退物理基线；
- COMMIT WAL 保存足够的 before/after image；WAL durable 后原子发布 version 的 commit_ts；
- 后台 materializer 把已提交 delta 合并到 heap，只有在不再被活动快照需要时才回收旧版本；
- 崩溃后 REDO 从 durable WAL 恢复物理基线，内存 delta 不要求跨进程保存。

这样提交不再逐项修改共享 heap，普通读也不需要用全局屏障防止看到半物理状态。

### 6.3 M2-C：MVCC-aware index

索引键未变化的 UPDATE 不做索引操作。键变化和 INSERT/DELETE 采用带可见性元数据的索引项：

- 新索引项在事务执行期安装为 pending，只对 owner 可见；
- 旧索引项保留到提交发布和老快照结束；
- 查到 RID 后必须以 MVCC version 做最终可见性校验；
- 唯一检查同时考虑 committed 可见项和其他事务 pending intent；
- COMMIT 只发布版本元数据，不在临界区做整棵树删除/插入；
- GC 根据全局最老活动快照延迟删除旧索引项。

若短期无法完成多版本索引，第一阶段可只对“不改变索引键的 UPDATE”启用 delta 快速路径；涉及索引键变化、INSERT、DELETE 继续走带短提交屏障的正确慢路径。

### 6.4 M2-D：移除逐记录 `commit_apply_latch_`

只有在 M2-B/C 已证明读者不会观察半提交状态后才能执行：

- `get_record()`、`batch_get_records()` 和 scan 不再逐记录获取全局提交共享锁；
- 快照创建从单调的 published commit watermark 读取；
- 每个 MVCC shard 独立保护自己的 version chain；
- checkpoint/GC 使用快照复制、epoch 或短暂 metadata latch，不长期阻塞事务；
- 全局锁只允许用于罕见的 schema/checkpoint 发布，不进入普通 OLTP 记录读取。

### 6.5 M2 验收

- 在物理安装、COMMIT append、fsync、publish 和 materialize 各点暂停线程，读者始终只见完整旧状态或完整新状态。
- 每个关键点 SIGKILL 后，winner/loser 判定与表索引状态一致。
- 普通 point lookup 的全局 commit latch 获取次数降为 0。
- 提交 publish 临界区 p99 小于 200 微秒；durable wait 单独计量。
- 32 客户端平均 CPU 至少达到 4 核，且 NewOrder/min 达到 300 以上才继续 M3；否则重新 profile。

## 七、M3：heap 与 B+ 树页级并发

### 7.1 heap 锁拆分

将 `insert_latch_` 的职责拆为：

- `file_meta_latch`：只保护 `num_pages`、free-list 头和新页分配；
- page latch：保护 bitmap、slot、`num_records` 和页内记录；
- equality-cache shard latch：按 offset/key 分片；
- record intent/MVCC shard：保护事务级冲突，不让物理页锁承担事务锁职责。

操作顺序：

```text
INSERT: reserve free page → pin page → page X latch → allocate slot → WAL → modify → unpin
UPDATE: pin known page → page X latch → validate RID/version → WAL/private delta → release
DELETE: pin known page → page X latch → validate → WAL/private tombstone → release
```

free-list 只在页面由满变非满或由非满变满时增量更新。禁止每次提交重建全文件 free-list。

### 7.2 B+ 树 latch crabbing

分阶段替换整树 `root_latch_`：

1. root metadata 保留短锁，仅保护 root page id 和树高变更。
2. point lookup 使用父页 S latch → 子页 S latch → 释放父页。
3. 不分裂的 leaf insert/delete 只持目标叶页 X latch。
4. 可能 split/merge 时自顶向下保留必要祖先 X latch，确认子页安全后尽早释放祖先。
5. 兄弟页操作按 page_id 排序获取，禁止左右顺序不一致。
6. page latch 存于 buffer frame 的内存元数据，不写入持久页格式。

第一版不引入无锁 B-link/OLC，也不修改持久化 `IxPageHdr` 布局。先获得安全的页级并行，再依据 profile 判断是否需要乐观读。

### 7.3 批量索引维护

同一事务的索引写按 `(index_id, key)` 排序、去重：

- 相同 leaf 的多个 INSERT/DELETE 在一次 pin/latch 内完成；
- UPDATE 未改变索引列时跳过该索引；
- insert→delete 抵消，重复 update 只保留最早旧键和最终新键；
- 唯一性检查仍在发布前完成；
- rollback 使用同一合并状态机逆向恢复。

### 7.4 M3 验收

- 不同页面的 heap 更新和不同叶页索引写能够真实并行。
- 通过多线程随机 insert/delete/update/lookup/scan、唯一冲突、split/merge、回滚和恢复测试。
- root latch 等待占事务时间低于 5%，heap file-meta latch 低于 2%。
- 平均 CPU 达到 6～10 核，NewOrder/min 挑战 800～1,800。
- 任一索引/表不一致或恢复错误立即回退整个索引并发阶段。

## 八、M4：减少每事务固定成本

### 8.1 不可变 prepared 模板

PREPARE_SET 阶段完成：

- parse、analyze、列绑定、索引选择和输出 schema；
- 生成不可变 plan/executor factory；
- 为参数、表达式临时值和结果行预计算槽位布局。

EXEC_BATCH 阶段只做：

- typed 参数写入连接私有 parameter frame；
- 创建或复用连接私有 executor state；
- 重置游标、聚合器和结果 buffer；
- 顺序执行 operation。

不得在多个连接之间共享会被 `bind_plan_parameters()` 修改的 plan。推荐共享不可变模板，每连接维护独立参数槽和运行态。

### 8.2 事务内写集合并

用事务本地 `unordered_map<RecordKey, PendingWrite>` 合并同 RID 写入：

| 序列 | 最终状态 |
| --- | --- |
| INSERT → UPDATE | 一次 INSERT，保存最终 after image |
| INSERT → DELETE | 抵消物理写；保留必要的语义/日志状态 |
| UPDATE → UPDATE | 最早 before + 最终 after |
| UPDATE → DELETE | 最早 before + tombstone |
| DELETE → INSERT | 按唯一键和可见性规则判为 replace 或冲突，不能简单覆盖 |

COMMIT、ABORT、索引维护和 WAL 都消费同一份规范化写集，避免多个互相矛盾的 write_set。

### 8.3 记录与结果内存复用

- point lookup 使用栈上或线程本地固定大小 record buffer；
- batch 查询结果在 1 MiB 上限内复用连接级 response builder；
- CHAR 参数使用长度视图，只有跨请求持有时才复制；
- 小向量保存常见的 5～15 个 order_line/stock key；
- 避免每个 operation 重建列名、索引名和 schema。

这些属于 M4，而不是 M1。只有在锁等待已大幅下降、CPU 执行占主导后才值得投入。

### 8.4 M4 验收

- PREPARE 后每 operation 的 parser/analyzer 调用为 0。
- 同连接和跨连接参数并发无串值、无 plan 污染。
- 每事务 heap 分配次数和复制字节显著下降。
- NewOrder p50 挑战低于 500 ms，p99 低于 2 s。

## 九、M4-WAL：合规 group commit 调优

在提交到达已足够并行后，再调 WAL：

### 9.1 leader/waiter 模型

- COMMIT 线程 append 后记录自己的 `commit_lsn`；
- 首个线程成为 leader，聚合短窗口内已经 append 的事务；
- leader 对同一个 WAL fd 执行 write + `fsync`/`fdatasync`；
- 更新 `durable_lsn` 后一次唤醒覆盖范围内的 waiter；
- waiter 只在 `durable_lsn >= own_commit_lsn` 时返回成功。

### 9.2 自适应聚合

不要固定假设 1 ms 最优。依据队列深度选择 0～1000 微秒窗口：

- 队列已有多个 COMMIT 时立即 flush；
- 队列只有一个且近期 fsync 昂贵时允许短聚合；
- durable wait 接近延迟预算时立即 flush；
- 窗口上限固定且可配置，不能为了 batch 无限延迟 ACK。

### 9.3 WAL 验收

- 32 个并发 COMMIT 审计仍为 32/32 durable coverage。
- 平均 group size 明显大于 1，fsync/commit 比例显著下降。
- fsync 失败时所有未覆盖 waiter 均失败，不产生成功 ACK。
- SIGKILL 后只恢复 durable winner，未覆盖事务为 loser。

## 十、M5：checkpoint、恢复和 LOAD 收口

### 10.1 checkpoint 不停顿 OLTP

- 在短 metadata latch 下复制 dirty page 集、active transaction table、durable LSN 和索引快照描述；
- 释放事务全局锁后写 checkpoint 内容；
- 最后以原子 restart marker 发布；
- checkpoint 不持有 `commit_apply_latch_` 扫描全库；
- restart marker 只有在对应 checkpoint WAL 和数据满足恢复前提后才更新。

### 10.2 恢复限制在 checkpoint 之后

- 分析阶段从经过校验的 restart offset 开始；
- committed winner REDO 幂等；active loser action 仅登记给 UNDO，不先物理 REDO；
- free-list 增量维护，只有检测到元数据不可信时才全量重建；
- 恢复结束避免对全库无差别 flush，按实际 dirty page 和 WAL 边界持久化；
- 监听只能在系统目录、索引、free-list 和恢复事务状态可安全查询后开放。

### 10.3 LOAD

LOAD 不计排名，但必须稳定低于 900 秒。按收益顺序：

1. CSV 使用复用行 buffer 和无 locale 数值解析。
2. 多行组成一个 WAL block，仍保留每行恢复信息和最终原子事务。
3. heap 连续页批量写入，减少每行 buffer lookup。
4. 索引可先收集键值并 bulk build；只有在 LOAD 失败时能整体丢弃未发布索引，且最终结果与逐行维护完全一致时启用。
5. LOAD COMMIT 仍等待覆盖自身 WAL 的稳定化。

### 10.4 M5 验收

- 三轮吞吐差异不超过 10%，无零提交 5 秒桶。
- LOAD 在相同环境保持低于 600 秒，且九表校验通过。
- SIGKILL 后监听 + `show tables;` + 全部恢复检查低于 60 秒，给 90 秒门槛留足余量。
- 连续两次崩溃恢复结果一致，数据库大小不异常增长。

## 十一、禁止与暂缓项

| 方案 | 裁决 | 原因 |
| --- | --- | --- |
| COMMIT WAL durable 前发布 commit_ts | 禁止 | ACK 未提前也不代表可见性提前合规 |
| 删除冲突检测、把 pending 当 committed | 禁止 | 直接违反 SI/SER 和审查红线 |
| 针对 TPC-C 表名、列名、SQL 或 statement_id 特判 | 禁止 | 正式标识符不透明，且属于硬编码 |
| 固定 32 客户端令牌作为正确性前提 | 禁止 | 客户端数不是语义前提 |
| 近似 COUNT/SUM、缓存固定答案 | 禁止 | 一致性要求真实、精确结果 |
| 只优化 NewOrder，主动牺牲 Payment/Delivery | 禁止 | 五类事务和计数门禁均需通过 |
| writer-priority 全局读写锁作为终态 | 否决 | 容易形成数据库级队头阻塞 |
| 直接删除 `root_latch_` | 禁止 | split/merge 和页生命周期会损坏 |
| 持久页内放 `std::mutex`/`std::atomic` | 禁止 | 对象布局和重启语义不成立 |
| 一步同时上 B-link、OLC、无锁 GC 和新页格式 | 暂缓 | 无法隔离索引损坏来源 |
| 盲目扩大 Buffer Pool | 暂缓 | 当前 RSS 低不等于 miss 是主瓶颈，先看计数 |
| 继续做单条复制等微优化 | 暂缓 | 当前主要证据指向等待，不是 allocator |

## 十二、实验方法与保留标准

### 12.1 固定 A/B 条件

- 同一 Release 编译参数、机器、CPU 亲和性和数据库初始快照；
- 同一 workload seed；
- 32 客户端，30 秒预热，连续 3×150 秒；
- 每个候选至少运行三次，报告中位数和最差一次；
- 一次只改变一个可归因变量；架构阶段内部也要拆成可单独回退的小提交；
- 诊断计数关闭和开启各跑一次，确认观测开销。

### 12.2 必记指标

| 类别 | 指标 |
| --- | --- |
| 正确性 | 功能、恢复、durability、LOAD、在线一致性、post-crash |
| 排名 | 每轮 NewOrder/min、中位数、仓库覆盖 |
| 完成 | 五类 attempted/committed/expected rollback/abandoned/completion |
| 延迟 | 五类 p50/p99/max，尤其 NewOrder |
| 稳定性 | 每轮 CV、零提交 5 秒桶、最慢 batch |
| CPU | 平均/峰值核数、用户态/系统态 |
| 锁 | 获取数、总等待、p99/max 等待、队列长度 |
| MVCC | conflict reason、pending wait、version chain 长度、GC 数 |
| WAL | append/write/fsync、bytes、group size、durable wait |
| Buffer | hit/miss、dirty eviction、frame wait、读写字节 |
| 恢复 | analysis/redo/undo/index/free-list/flush 分段耗时 |

### 12.3 保留条件

候选改动必须同时满足：

1. `docs/正确性门槛关键要求.md` 的全部适用回归通过。
2. 三次 A/B 的 NewOrder/min 中位数提升至少 15%，最差一次不低于基线 95%。
3. NewOrder 与 Payment 完成率不下降；M1 后目标均为 95% 以上。
4. p99、零提交桶和恢复时间不能出现不可解释的明显恶化。
5. 提升能由计数器解释；无法归因时标为待验证，不叠加下一项。
6. 不依赖正式测评隐藏数据，不探测测评程序，不输出敏感运行内容。

## 十三、执行顺序

必须按以下顺序推进：

1. **冻结成功基线**：保留 `9e657d2` 源码和 PASS 报告，可随时回退。
2. **M0 观测**：补齐事务、锁、WAL、Buffer、执行分段计数。
3. **M1 完成率**：完整 RecordKey 写意向、稳定锁序、短等待和过载保护。
4. **M2-A 正确提交状态机**：先解决提前可见审查风险。
5. **M2-B/C 私有版本与索引可见性**：让提交不再逐项物理改写。
6. **M2-D 去全局读屏障**：只有私有状态模型验证后才能删除逐记录锁。
7. **M3 heap 页级并发**：拆 free-list、page、cache 锁。
8. **M3 B+ 树页级并发**：先安全 latch crabbing，再谈乐观读。
9. **M4 prepared 与写集合并**：让 CPU 成本随有效事务而不是 SQL operation 增长。
10. **M4-WAL group commit**：提交已并行后再调聚合窗口。
11. **M5 checkpoint/recovery/LOAD**：稳定守住 90 秒和 900 秒门槛。
12. **三轮正式回归**：只有全部正确性通过且性能可复现，才更新成功基线。

任何阶段出现正确性失败、数据库损坏、response timeout 或 post-crash 超时，都停止后续优化，回退到该阶段开始前的最后一个 PASS 版本。
