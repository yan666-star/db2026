| 条目 | 裁决 | 依据与处理 |
|------|------|------------|
| 3.1 提交阶段拆分 | **拒绝原方案** | 原方案会在 COMMIT WAL 稳定化及堆/索引物理应用完成前发布可见 `commit_ts`。其他事务可能读取并依赖一个随后物理应用失败或崩溃丢失的状态，违反原子可见性和恢复要求。保留当前 `commit_apply_latch_` 边界，后续只能在不提前发布版本的前提下缩短锁内工作。 |

| 3.3 group commit 延迟 | **采纳** | 默认聚合窗口改为 1000us；`force_flush_up_to()` 仍要求 `durable_lsn_ >= target_lsn` 后返回，不改变 ACK 持久化边界。 |

## 二、Abort 率根因分析

### 2.1 机械路径

决赛排名 32 客户端 SNAPSHOT ISOLATION，4 热仓承载 ~65% 归属流量，每热仓 1 热区，热区 ~65% 事务进入。

```
32 客户端并发
  → 热点 RID (warehouse/district/stock) 上多事务重叠
  → 事务 A 取快照 start_ts 后执行读+写
  → 事务 B 对同一 RID 写入并先提交，commit_ts > A.start_ts
  → A 进入 prepare_write / check_write_conflict
  → 检测到 latest_commit > start_ts  (transaction_manager.cpp:1122)
  → mark_mvcc_txn_aborted + throw TransactionAbortException
  → A 整笔回滚，所有已执行工作（解析、索引访问、版本构造）浪费
```

**abort 主因 = SI stale-snapshot 写写冲突**（first-committer-wins 的败方）。这不是 bug，是 SI 的正确行为，但频率过高导致有效吞吐极低。

### 2.2 量化证据（来自优化日记）

| 客户端数 | NewOrder tpmC | 提交率 | 主因 |
|---------:|--------------:|-------:|------|
| 1 | ~4497 | 100% | 无冲突 |
| 16 | ~891 | ~2% | 热点行写写冲突 |
| 32 | ~418 | <1% | 热点行写写冲突雪崩 |

SI=1 准入控制可消除 abort（tpmC 4959@16c），但代价是全局串行——32 客户端下完全浪费并发度。OJ 实测 SI=1 得 947 tpmC（远低于本地短测），说明 360 秒长测中串行上限 + 索引页膨胀共同压低了吞吐。

### 2.3 非主因排除

| 可能原因 | 实际影响 | 证据 |
|----------|---------|------|
| Lock Manager 5s 超时 abort | 无 | SI 路径跳过 2PL 锁 (`should_lock_non_mvcc()=false`) |
| SI 准入串行 | 无（默认关闭） | `RMDB_SI_MAX_ACTIVE=0`，`admit_snapshot_transaction` 直接返回 |
| SSI 危险结构 abort | 排名不触发 | 排名用 SI，SSI 仅 SER 连接；SI 不维护 rw 图 |

## 三、修改方案：性能优化

按"预期吞吐收益 × 正确性风险可接受度"排序。用户明确允许"极端取巧"方式——以下方案均在通用锁/MVCC/索引/WAL 机制内操作，不硬编码表名/SQL，不降 ACID，但允许比通用数据库更激进的参数和策略。

### P0：必须完成（直接决定能否有效排名）

---

#### 3.1 缩短 commit 临界区：拆分版本发布与物理应用

**现状**：`commit_apply_latch_`（全局独占）在 `commit_mvcc()` 整个期间持有——从版本发布 + commit_ts 分配（纯内存，微秒级）到物理记录更新 + 索引维护（含文件 I/O，毫秒级）。所有 commit 全局串行。

**改动**：

```
Phase 1（版本发布）: 独占 commit_apply_latch_ + mvcc_latch_
  → check_commit_conflict_under_latch
  → 分配 commit_ts
  → 标记 pending 版本为已提交
  → 收集 PhysicalOp 列表
  → 释放 mvcc_latch_，释放 commit_apply_latch_

Phase 2（物理应用）: 无全局锁，使用已有的 per-file insert_latch_ + per-index root_latch_
  → 逐 op：check_physical_before → delete_indexes → delete_record → update_record → update_indexes
  → 任一失败：回滚本 commit 已应用部分（逆序 undo），然后 abort

Phase 3（日志）: 写 COMMIT log → force_flush_up_to → 返回成功
```

**关键正确性论证**：
- 读者通过版本链读取：commit_ts 发布后，`get_visible_record_under_latch()` 从版本链 data 返回新值，**不依赖物理记录是否已应用**。因此 Phase 1 结束后读者即可看到新版本。
- 同一 RID 的多个 commit 仍按 commit_ts 序到达 Phase 2——因为 Phase 1 在 `commit_apply_latch_` 下串行分配 commit_ts，后到者的 commit_ts 更大。Phase 2 对同一文件/索引的写操作由 `insert_latch_` / `root_latch_` 保护顺序。
- `check_physical_before` 在 Phase 2 每次物理写前重新验证——因为 Phase 1 与 Phase 2 之间有窗口，其他 commit 的 Phase 2 可能已修改了物理行。验证失败则回滚本 commit。
- COMMIT 日志在 Phase 3 写入（物理应用完成后），崩溃恢复语义不变：日志出现 → 物理已应用；日志不出现 → 读者可能看到已发布版本但物理未完成，恢复时 redo 补齐。

**上次回退原因**：早期实现未在 Phase 2 重新做 `check_physical_before`，导致读者看到"已提交新版本 + 未更新旧索引"的部分应用状态。本次方案修正：**Phase 2 每个 op 前重新 check_physical_before，失败即回滚**。

**落点**：
- `src/transaction/transaction_manager.cpp:1433-1567` (`commit_mvcc`)
- `src/transaction/transaction_manager.h:337-342` (锁序注释)

**预期效果**：commit 不再全局串行于 I/O。32 客户端下并发 commit 吞吐提升 2-4×。**单次修改中收益最大**。

**正确性复验**：
- [ ] SI first-committer-wins：两个事务同 RID，Phase 1 串行分配 commit_ts，败方在 Phase 1 的 `check_commit_conflict_under_latch` 中 abort
- [ ] 读者可见性：commit_ts 发布后、物理应用前，读者从版本链读到新值；物理应用后从物理记录读到同值
- [ ] Phase 2 中途失败回滚：已应用的 op 逆序 undo，已发布的版本标记回 abort
- [ ] kill-9 恢复：WAL COMMIT 日志在 Phase 3 写入，未出现 → 恢复时 undo 该事务
- [ ] SSI 危险结构检测不受影响（在 Phase 1 之前完成）

#### 3.2 消除 WAL 过度 flush：LSN 目标化刷盘

**现状**：`buffer_pool_manager.cpp:18-22` 的 `flush_wal_before_page_write()` 调用 `flush_log_to_disk(true)` 刷**整个**日志缓冲 + fsync。逐页淘汰时每页触发一次全量 fsync，极度浪费。

**改动**：改为 `log_manager->force_flush_up_to(page_lsn)`。`force_flush_up_to` 已存在且正确（`log_manager.cpp:87-122`），只刷到目标 LSN 并共享 fsync。连续淘汰多页时，仅一次 fsync 覆盖 max(page_lsn)。

**落点**：
- `src/storage/buffer_pool_manager.cpp:18-22`：改调用
- `src/storage/page.h`：确认 `Page` 已存储 `lsn_`（已有，`page.h:49`）
- 逐页淘汰路径 (`update_page`, `flush_page`, `delete_page`) 传入 page lsn

**预期效果**：fsync 次数大幅减少（从每页 1 次到每批次 1 次）。对长测 360 秒中缓冲池频繁淘汰场景效果显著。

**正确性复验**：
- [ ] WAL-before-page：`durable_lsn >= page_lsn` 在脏页写前保证
- [ ] kill-9 恢复正确

---

#### 3.3 Group commit 延迟调优

**现状**：`group_commit_delay()` 默认 200μs（`log_manager.cpp:19-35`），env `RMDB_GROUP_COMMIT_US` 上限 5000μs。32 客户端 SI 下，如果 §3.1 生效后并发 commit 增加，200μs 可能只聚合 1-2 条日志。

**改动**：将默认值从 200μs 提升到 1000μs（1ms），或通过 env 设为 500-2000μs 做 A/B。排名指标是 NewOrder/min 中位数，1ms 延迟对 150s 窗口影响可忽略，但能让每次 fsync 覆盖更多 commit。

**落点**：`src/recovery/log_manager.cpp:19-35`

**预期效果**：fsync 次数减少 3-5×，commit 延迟增加 <1ms。

**正确性复验**：每个 ACK 仍等待 `durable_lsn_ >= commit_lsn`（不变）。

#### 3.4 冲突域准入：per-key 令牌替代全局 SI=1

**现状**：SI 准入控制（`admit_snapshot_transaction`，`transaction_manager.cpp:306-335`）默认关闭。开启 `RMDB_SI_MAX_ACTIVE=1` 可消除 abort 但全局串行。

**改动**：实现**通用冲突域准入**——在 prepared plan 执行前，提取唯一索引等值键作为冲突域 token。同一 token 的 SI 事务排队；不同 token 并行。

```
EXEC_BATCH 到达
  → 解码 statement_id + typed params
  → 对每个 DML operation，检查 prepared plan 的索引访问模式
  → 提取唯一索引等值条件对应的参数值 → 冲突域 key = (index_id, key_value)
  → 申请该 key 的准入 token（hash 分片，per-key FIFO 队列，容量=1）
  → 获准后刷新 start_ts（同现有 ensure_snapshot_admission 逻辑）
  → 执行
  → commit/abort 后释放 token
```

**不识别 TPC-C 表名**：通用机制——对任何 prepared plan，若 WHERE 子句能匹配唯一索引的全部等值列，则提取冲突域。无法提取时退化为不准入（不限并发）。

**多 key 事务**（如 NewOrder 访问 warehouse + district + 多 stock）：按 index_id + key_value 字典序申请，避免 ABBA 死锁。

**落点**：
- `src/transaction/transaction_manager.h`：新增 `ConflictDomainAdmission` 类，per-key 队列
- `src/execution/sql_execution_service.cpp:405-416`：`execute_prepared` 中调用
- `src/optimizer/plan.h`：Plan 需暴露唯一索引等值列位序（PREPARE 时计算一次）

**预期效果**：不同仓库/区的事务完全并行；同一热区的事务排队但快照刷新后几乎不 abort。预期 NewOrder 提交率从 <1% 提升到 30-60%（4 热仓各 1 个活跃 writer × 10 区 = 40 并发槽）。

**正确性复验**：
- [ ] SI 语义不变（准入仅调度，不改变隔离）
- [ ] 快照在准入后刷新（复用 `ensure_snapshot_admission` 逻辑）
- [ ] 多 key 死锁：字典序申请 + 超时 abort
- [ ] 无饥饿：FIFO 队列

### P1：高收益优化

#### 3.5 MVCC 版本表分片

**现状**：全局 `mvcc_latch_`（`transaction_manager.h:344`）保护 `record_versions_`、`mvcc_txns_`、`gc_dirty_keys_`、SSI 图。16 客户端累计等待 1.81s；32 客户端将显著增长。

**改动**：

```cpp
struct MvccShard {
    std::mutex latch;
    std::unordered_map<RecordKey, std::vector<MvccVersion>, RecordKeyHash> histories;
    std::unordered_set<RecordKey, RecordKeyHash> dirty_keys;
};
std::array<MvccShard, 64> mvcc_shards_;  // 替代 record_versions_
std::mutex txn_state_latch_;             // 单独保护 mvcc_txns_
```

分片号 = `hash(file_id, page_no) & 63`。

- 读取/prepare_write/abort 只持目标 shard 锁
- commit 按写集涉及的 shard ID 升序加锁（避免 ABBA）
- SSI 图（`incoming_rw`/`outgoing_rw`）仍在 `txn_state_latch_` 下；`dependency_forms_dangerous_structure` 在该锁下快照 txn 列表
- GC 按 shard 独立执行

**上次回退原因**：整页一次持有 `mvcc_latch_` 扩大了临界区，阻塞其他事务。本次分片化不扩大任何单 shard 临界区。

**落点**：`src/transaction/transaction_manager.h:344-346`，`.cpp` 中所有 `lock_mvcc(mvcc_latch_)` 调用点

**预期效果**：非冲突 RID 的版本操作完全并行。预计 mvcc 等待降低 10-30×。

**正确性复验**：
- [ ] 同一 RID 冲突检查原子性（单 shard 锁下完成）
- [ ] 跨 shard commit 按升序加锁无死锁
- [ ] SSI 危险结构检测仍原子（在 txn_state_latch_ 下）
- [ ] GC watermark 正确

#### 3.6 同 RID 事务内写合并优化

**现状**：`prepare_write` 已支持更新 `own_pending` 版本（`transaction_manager.cpp:1314-1325`），但 `check_write_conflict` 仍被 `UpdateExecutor` 每次 UPDATE 语句调用（`executor_update.h:186`），`append_write_record` 每次追加新 WriteRecord（`executor_update.h:249`），导致 `write_set_` 膨胀。

**改动**：
1. `UpdateExecutor` 中，对已在 `txn->write_records_` 中的 RID，跳过 `check_write_conflict`（own_pending 路径已保证正确性）
2. `append_write_record` 对同 RID 的 UPDATE 合并：只保留最早 before_image + 最新 after_image

**落点**：`src/execution/executor_update.h:186,249`；`src/transaction/transaction.h` write_records 结构

**预期效果**：NewOrder 5-15 条 stock UPDATE 减少 50-80% 冲突检查和写集膨胀。

**正确性复验**：
- [ ] first-committer-wins 仍由 commit 时 `check_commit_conflict_under_latch` 兜底
- [ ] abort 回滚用最早 before_image 正确
- [ ] 索引键变化：同 RID 多次 UPDATE 可能产生多个旧键→新键，合并时需保留全部索引键变化记录

---

#### 3.7 批量装载路径优化

**现状**：`sql_execution_service.cpp:529-559` 逐行 `parse_csv_line → vector<string> → vector<Value> → InsertExecutor::Next()`。每行独立堆分配 + 索引操作。

**改动**（阶段一，不改事务语义）：
1. 64 KiB 双缓冲读取 CSV 文件
2. 输入缓冲上切字段，直接写入定长 `RmRecord`（跳过 `vector<string>` 和 `vector<Value>` 中转）
3. 批量 64-256 行共用一次 `insert_latch_` + `root_latch_` 获取
4. 索引句柄在 LOAD 开始时缓存（复用 key buffer）
5. 批末有界刷脏，避免 Buffer Pool 全部 pin 住

**落点**：`src/execution/sql_execution_service.cpp:529-559`；`src/record/rm_file_handle.h` 新增 `batch_insert_records` 接口

**预期效果**：装载速度 2-4×。确保 order_line (1.5M+ 行) + stock (5M 行) 在 900s 预算内完成。

**正确性复验**：
- [ ] 唯一性检查仍逐行执行
- [ ] WAL 写入顺序不变
- [ ] 批内失败时整批回滚
- [ ] LOAD 后 COUNT + 索引抽样正确
- [ ] kill-9 后装载结果符合命令成功边界

---

#### 3.8 EXEC_STREAM 计划缓存

**现状**：排名路径通过 PREPARE_SET/EXEC_BATCH 已避免重复解析。但 `dispatch_stream`（功能测试、装载、恢复查询）仍走全局 `parser_mutex_` + 全量解析。parser 全局锁累计等待 20.78s（热点 #1）。

**改动**：在 `SqlExecutionService` 中新增 LRU 计划缓存（容量 64-128），以 SQL 文本 hash 为 key。命中时跳过 parse/analyze/plan，直接 `bind_plan_parameters` + execute。DDL 时失效。

**落点**：`src/execution/sql_execution_service.cpp:240-252,402`

**预期效果**：功能测试 + 装载 + 恢复查询中重复 SQL 的解析开销消除。排名路径不受影响（已走 PREPARE_SET）。

**正确性复验**：
- [ ] DDL/CREATE INDEX/DROP 失效缓存
- [ ] 参数绑定正确
- [ ] 并发访问安全（读锁/写锁）

### P2：中收益优化

---

#### 3.9 缩短 pending_writer_wait_budget

**现状**：默认 2000μs（`transaction_manager.cpp:220`，env `RMDB_PENDING_WAIT_US`）。热行上 32 客户端排队等 2ms 后仍因 stale-snapshot abort——等的时间浪费了。

**改动**：降至 200-500μs。pending writer 大部分在 500μs 内完成提交或 abort；超时即 abort，让客户端重试。

**预期效果**：热行上每个冲突减少 1.5-1.8ms 等待；150s 窗口内更多重试机会。

**落点**：`src/transaction/transaction_manager.cpp:216-230`

**正确性复验**：SI 语义不变（budget 纯调度参数）。

---

#### 3.10 unique_key_conflict 检查优化

**现状**：`check_unique_key_conflict`（`transaction_manager.cpp:1135-1227`）对每个 INSERT 线性扫描 `mvcc_unique_conflict_keys_by_file_[file_id]`。随 NewOrder/Delivery 累积，该集合膨胀。

**改动**：将候选集从 `vector<RecordKey>` 改为 `unordered_map<CompositeKey, ConflictCandidate, KeyHash>`，按复合键哈希直接查找。GC 时同步清理。

**落点**：`src/transaction/transaction_manager.h` 数据结构；`.cpp:1135-1227`

**预期效果**：INSERT 路径 CPU 降低，减少 `mvcc_latch_` 持有时间。

---

#### 3.11 Sort + LIMIT 早停

**现状**：`SortExecutor::beginTuple()`（`execution_sort.h:89-101`）全量物化后排序，`limit_` 仅在 `ProjectionExecutor::is_end()` 裁剪。OrderStatus `ORDER BY o_id DESC LIMIT 1` 需物化全部匹配订单。

**改动**：当 `limit_num > 0` 时，使用 top-N 堆（O(rows × log N)）替代全量排序。N=1 时退化为单变量跟踪最大/最小值。

**落点**：`src/execution/execution_sort.h:89-101`；`src/optimizer/planner.cpp` 传播 limit 到 SortPlan

**预期效果**：OrderStatus 从 O(rows × log rows) 降至 O(rows)。

---

#### 3.12 O(1) COUNT 维护

**现状**：无行数缓存，`SELECT COUNT(*)` 始终全表扫描。

**改动**：在 `RmFileHdr` 或 `TabMeta` 中维护 `row_count`：INSERT +1，DELETE -1（含 MVCC tombstone 应用），abort 回滚修正，恢复 redo/undo 修正。`COUNT(*)` 优化：当表无活跃写事务且计数已 durable 时直接返回。

**落点**：`src/record/rm_file_handle.h`（文件头新增字段）；`src/system/sm_meta.h`；`src/execution/executor_aggregation.h`（短路）

**预期效果**：装载后 9 次 COUNT 从 O(rows) 降至 O(1)；恢复后 37 项整数聚合校验加速。

---

#### 3.13 MIN/MAX 索引端点优化

**现状**：MIN/MAX 始终走全量扫描 + 聚合。Delivery 的 `MIN(no_o_id)` 可从索引 `(no_w_id, no_d_id, no_o_id)` 的 `lower_bound` 在 O(log N) 内取得。

**改动**：planner 检测 MIN/MAX + 匹配索引 + 生成 IndexScanPlan(limit=1 + visibility skip)。

**落点**：`src/optimizer/planner.cpp:503-530`；`src/execution/executor_index_scan.h`

**预期效果**：Delivery MIN 从 O(matching_rows) 降至 O(log N + visible_skips)。

---

#### 3.14 Buffer Pool 容量调优

**现状**：32K 页 = 128 MiB（`config.h:36`）。决赛数据 10M+ 行 + 10 索引，热工作集可能超出。

**改动**：A/B 测试 65536 (256 MiB) / 131072 (512 MiB)。修改 `BUFFER_POOL_SIZE` 或改为运行时配置。

**落点**：`src/common/config.h:36`

**预期效果**：热点页命中率提升，减少读盘。512 MiB 时 RSS 约 0.5 GB（OJ 实测 0.39 GB 可行）。

---

### P3：低收益 / 高风险 / 长期

---

#### 3.15 延迟索引页回收安全恢复

**现状**：`coalesce_or_redistribute` 对非根节点为 no-op（`ix_index_handle.cpp:493-510`），长测后空叶页累积，扫描退化。OJ tpmC 从本地 2989 降至 947，部分原因在此。

**改动**：开发并发 insert/delete + merge 压力回归后，重新启用延迟合并（非递归，使用 free list + 父节点 latch coupling）。

**风险**：历史 crash（`find_child` 断言）。必须有专项回归后才能合入。

---

#### 3.16 替换策略实验

**现状**：LRU，易受顺序扫描污染。

**改动**：实现 LRU-K 或 2Q（借鉴 RMDB2025 算法代码，不搬 BufferPoolManager）。扫描页进入 probation，二次访问进入 protected。

**条件**：诊断证明 COUNT / StockLevel 扫描赶出热点索引页时再做。

---

#### 3.17 B+ 树页级 latch coupling

**现状**：写操作独占整棵树的 `root_latch_`。多索引并发写串行。

**改动**：读共享 + 写按路径从叶到根的 latch coupling。极高风险，需专项回归。

## 八、激进策略备忘

用户明确允许"极端取巧"方式。在通过上述正确性复验的前提下，以下激进参数/策略可以考虑：

| 策略 | 说明 | 风险 |
|------|------|------|
| `RMDB_SI_MAX_ACTIVE=2~4` + 自动重试 | 比 SI=1 多利用并发，比不限多挽救 abort；需配合冲突域准入 | abort 仍存在，但重试可补偿 |
| group_commit_delay = 2-5ms | 更大 batch 降低 fsync 频率 | p99 延迟上升，但中位数不受影响 |

| MVCC 版本 chain 不存 before_image | 只存 after_image + 从事务写集取 before；减少 50% 内存复制 | abort 回滚需从写集取 before |
