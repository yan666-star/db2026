# 决赛性能修改方案（审查精简版）

更新时间：2026-08-12

本方案只讨论通用数据库机制，不针对固定表名、列名、SQL、statement_id、客户端编号或测评阶段写专用分支。每项性能改动必须先通过功能、隔离、持久化和崩溃恢复门禁，再比较 NewOrder/min。

## 一、赛题边界

决赛排名取 32 个客户端、50 个仓库、三个 150 秒窗口的 NewOrder/min 中位数。排名路径使用 SNAPSHOT ISOLATION、PREPARE_SET 和 typed EXEC_BATCH；功能、装载、恢复和一致性查询仍使用 EXEC_STREAM。

以下条件不可用性能换取：

1. 功能 25 项、恢复 5 项和 COMMIT 持久化审计必须通过。
2. COMMIT 成功响应前，commit record 必须被同一 WAL 对象上的可核验稳定化操作覆盖。
3. 未提交或最终失败的事务不得被其他事务观察；表记录和全部索引必须整体提交或整体回滚。
4. AUTO_ABORT 必须先完成回滚，再返回失败 BATCH_RESULT。
5. SIGKILL 后须在 90 秒内完成监听、`show tables;` 和恢复后一致性检查。
6. 优化必须适用于一类合法输入；前置条件不成立时必须回退到正确通用路径。

自动测试通过只能证明本次覆盖未发现错误，不能替代源码层面的 ACID 审查。

## 二、当前评测结论

### 2.1 最近两次正式评测

2026-08-12 版本包含两项改动：MVCC 普通读取由全局独占锁改为共享锁；单记录读取去掉一次堆分配和复制。两项改动在同一提交中，不能分别归因。

| 指标 | 上一轮 | 2026-08-12 | 判断 |
| --- | ---: | ---: | --- |
| 必通过项 | PASS | PASS | 正确性门槛保持 |
| NewOrder/min 中位数 | 31.2 | 34.0 | +9.0%，小幅提高 |
| 总放弃率 | 8.17% | 18.78% | 明显变差 |
| NewOrder 完成率 | 79.86% | 75.89% | 下降 |
| NewOrder p50 | 19.153 s | 26.111 s | 明显变差 |
| NewOrder p99 | 88.597 s | 63.910 s | 改善 |
| Payment 完成率 | 98.71% | 80.55% | 明显变差 |
| 三轮零提交 5 秒桶合计 | 23 | 57 | 稳定性明显变差 |
| 数据库平均 CPU | 300.5% | 291.8% | 基本持平 |

裁决：本轮是“吞吐小幅正收益，但稳定性和完成率回退”，不能记为已经定型的有效优化。两轮的装载时间、RSS、磁盘占用和可执行文件大小差异较大，也不是严格的单变量 A/B。

共享读锁可能增加独占提交者等待，进而造成 writer 饥饿或更多冲突放弃；这只是待验证假设。正式报告没有锁等待和 I/O profile，当前不能据此定因。

### 2.2 当前可确认的粗粒度路径

源码中仍存在以下可能限制 32 客户端并发的路径：

- `TransactionManager::commit_apply_latch_`：普通读取共享，版本发布、GC、检查点独占。
- `TransactionManager::txn_state_latch_`：部分写准备路径在持锁期间执行物理校验。
- `RmFileHandle::insert_latch_`：insert、update、delete 仍按文件串行。
- `IxIndexHandle::root_latch_`：索引写操作在整次 insert/delete 期间独占整棵树。
- Phase 2 物理应用最多允许 8 个事务并发。

这些是源码事实，不等于已完成归因。旧方案中“B+ 树占 60%、stock 写占 30%”等比例没有 profile 证据，全部撤销。

## 三、P0：先修正提交线性化风险

当前 `commit_mvcc()` 的顺序是：

```text
分配 commit_ts 并把版本标为已提交
→ 释放 commit_apply_latch_
→ Phase 2 更新 heap 和 index
→ 追加 COMMIT WAL 并稳定化
→ 返回成功
```

这段顺序存在源码级风险：

- 新事务的快照可能包含尚未完成物理应用、仍可能失败的版本。
- 多条 heap/index 修改在 Phase 2 中逐项完成，读者可能遇到部分索引已经切换、部分尚未切换的中间状态。
- commit_ts 发布早于 COMMIT WAL 稳定化。即使 ACK 没有提前，也不能把“可见性提前”视为合规。

后续实现必须明确一个提交线性化点，并满足：

1. 线性化点之前，版本、heap 和 index 的中间状态均不可被其他事务观察。
2. 线性化点之后，事务不能再因普通冲突或物理校验失败而回滚。
3. 新事务的快照不得包含尚未完成提交的事务。
4. COMMIT ACK 仍须等待 commit record 的可核验稳定化。

当前结构下，低风险回退方案是让独占提交屏障覆盖物理应用、失败回滚和持久化，在全部成功后再发布 commit_ts。若要重新拆开该屏障，必须先具备可证明的私有版本或 MVCC-aware index，使旧索引项在发布前仍可正确访问、新索引项在发布前不可见。仅在 Phase 2 重新校验物理行，不能解决提前可见问题。

P0 验证必须补充：

- 在 Phase 2 每个操作之间并发执行旧键、新键、表扫描和快照查询，确认只出现完整旧状态或完整新状态。
- 在 COMMIT WAL 稳定化前暂停提交线程，确认其他连接不能建立包含该事务的快照。
- 在物理应用、COMMIT append、fsync 和发布前后分别 SIGKILL，核对表与所有索引。

## 四、优化路线

### P1-1：拆分最新改动，定位回退来源

建立三个版本：

1. 基线。
2. 只保留单记录零重复复制。
3. 在版本 2 上启用共享读锁。

记录 `commit_apply` 读/写获取次数和等待时间、独占写者最长等待、pending writer 超时、各事务放弃原因、各 5 秒提交数。若版本 3 重现完成率和零提交桶回退，优先采用 writer-preference 门控：独占写者开始等待后阻止新读者进入，而不是继续扩大共享读区间。

单记录零复制是局部内存优化，理论风险较低，但仍只能以独立 A/B 结果决定是否保留。

### P1-2：缩短 `txn_state_latch_` 临界区

`prepare_write()` 当前在事务状态锁范围内调用物理校验。目标是：

1. 锁内只读取事务状态、版本元数据并生成校验快照。
2. 释放状态锁后访问 heap/index。
3. 重新按固定顺序获取状态锁和目标 MVCC shard，验证期间状态没有变化，再安装 pending version。

不能简单把 I/O 移到锁外后直接写入；必须有版本号或等价的二次验证，防止 TOCTOU 冲突。此项完成后再考虑拆分 SSI 图、unique conflict 索引等事务元数据。

### P1-3：拆分 heap 文件级 DML 锁

`insert_latch_` 不应长期同时承担空闲链维护和任意页更新的互斥。建议分两步：

- insert 的 RID 分配、文件头和 free-list 变更保留文件级锁。
- 已知 RID 的 update/delete 改为页级互斥；不同页可以并发，同页仍串行。

前置条件是页 pin 生命周期、bitmap、`num_records`、free-list 进出和 WAL-before-data 均有明确保护。禁止只删除文件级锁而依赖“热点通常不在同页”的假设。

### P1-4：减少冲突前的无效工作

官方负载会集中访问热点 district 和 stock 行。目标不是取消 first-committer-wins，而是让必然失败的事务更早排队或中止。

可采用基于通用 `RecordKey` 的写意向：

- 只对已经由真实参数解析出的完整键生效。
- 多键按稳定顺序获取，失败时释放全部意向。
- 排队完成后刷新快照，并重新执行必要读取和冲突检查。
- 不能根据事务类型、表名或不完整键集合提前放行。

EXEC_BATCH 的后续键可能依赖前一阶段查询结果，不能假定事务开始时已经知道完整写集。因此该项应从“键被解析后的早期写意向”做起，不实施按事务类型的全局令牌。

### P1-5：事务内同 RID 写合并

当前 MVCC pending version 已能覆盖同事务的后续值，但事务 write_set、物理操作和索引维护是否仍有重复，需要用计数器确认。只有观察到同一 `RecordKey` 在单事务内重复进入物理提交队列，才引入事务本地映射。

合并必须保留：

- 最早 before image；
- 最终 after image；
- insert→update、update→delete、delete→insert 的正确状态机；
- 旧索引键到最终索引键的一次原子切换；
- abort 和恢复所需的完整信息。

旧方案关于“一笔 NewOrder 会对同一 stock RID 更新 5～15 次”没有证据，删除该假设，也不再给出未经测量的倍数收益。

### P2：B+ 树页级并发

`root_latch_` 使所有索引写操作整棵树串行，是重要候选，但必须先增加索引读锁、写锁、分裂和合并的等待计数。没有等待占比前，不直接重写索引格式。

实施顺序：

1. 保留 root 元数据锁，先让不引起结构变化的叶页操作使用页级锁。
2. 为 split/redistribute/merge 建立自顶向下、可证明无死锁的 latch crabbing。
3. 完成多线程随机 insert/delete/lookup/scan、唯一索引、回滚、checkpoint 和恢复回归。
4. 只有读锁等待仍占主导时，再评估带版本验证的乐观读。

不在持久化的 `IxPageHdr` 中直接放置 `std::atomic`，也不在第一步同时引入 B-link、OLC、页面格式升级和无锁扫描。多项结构变化混在一起，无法定位索引损坏或恢复回退。

### P3：由数据驱动的后续调优

| 方向 | 进入条件 | 处理原则 |
| --- | --- | --- |
| group commit | sync 次数、批大小或 durable wait 成为主耗时 | 只调整聚合窗口；每个 ACK 仍等待覆盖自身 commit record 的稳定化 |
| Buffer Pool | miss、dirty eviction 或读写调用显著 | 做容量 A/B；不能仅凭低 CPU 扩容 |
| LOAD | 接近 900 秒门槛或装载抖动影响有效性 | 优化批量插入和建索引；LOAD 不直接参与排名 |
| 计划/算子 | EXEC_BATCH 执行 CPU 明确占主导 | 复用只读计划，隔离参数和运行态 |
| MIN/MAX、COUNT、Sort+LIMIT | 对应事务或一致性查询成为长尾 | 作为局部优化，不列为 NewOrder 主线 |

## 五、暂缓或否决的提案

| 提案 | 裁决 | 原因 |
| --- | --- | --- |
| Phase 1 提前发布 commit_ts | 否决 | 可能提前可见且可见性早于持久化 |
| 用单个事务的 start_ts 做 eager pruning | 否决 | 不是全局最老活动快照，可能删除其他事务仍需版本 |
| 直接移除 B+ 树 root latch 并上无锁读 | 暂缓 | 缺少 page-latch、split/merge 和恢复证明 |
| 修改持久页结构为 atomic/version/high-key | 暂缓 | 页面兼容、原子对象持久化和恢复风险过高 |
| 根据平均 fsync 自动设置延迟 | 暂缓 | 缺少同步分布和批大小证据 |
| O(1) COUNT、近似聚合、预置结果 | 否决 | 事务化维护成本高；近似或预置结果违反真实执行 |
| 固定 SI 并发数作为最终方案 | 仅 A/B | 可用于诊断，但不能依赖固定客户端数保证正确性 |
| 针对 TPC-C 名称或 SQL 的快速路径 | 否决 | 违反不透明标识符和反硬编码要求 |
| “31→数千”等固定预期 | 删除 | 没有 profile 和受控实验支撑 |

## 六、实验与保留标准

### 6.1 固定实验条件

- 同一提交、Release 构建、机器、数据库初始快照和 workload seed。
- 32 客户端，30 秒预热，连续三个 150 秒测量窗口。
- 每次只改一个变量，至少运行三次，报告中位数和最差一次。
- 正式评测使用动态数据，适合确认门禁和最终结果；不同正式评测之间不能替代本地受控 A/B。

### 6.2 必记指标

| 类别 | 指标 |
| --- | --- |
| 排名 | 三轮 NewOrder/min 及中位数 |
| 完成 | 五类 attempted、committed、expected rollback、abandoned、completion |
| 延迟稳定性 | NewOrder p50/p99、每轮 CV、零提交 5 秒桶 |
| 并发 | 各 latch 获取数、总等待、最大等待、Phase 2 排队 |
| 冲突 | pending wait 结果、write/unique/commit conflict、AUTO_ABORT 耗时 |
| WAL | append bytes、write/sync 次数、平均批大小、durable wait |
| Buffer/I/O | hit/miss、dirty eviction、读写字节和调用次数 |

### 6.3 保留条件

候选改动必须同时满足：

1. 功能、SI/SER、Wire、AUTO_ABORT、COMMIT 持久化、在线一致性和 SIGKILL 恢复全部通过。
2. NewOrder/min 的提升超过同环境自然波动。
3. 不能用完成率、p50/p99 或零提交桶的明显恶化换取小幅中位数提升。
4. 结果无法复现、指标互相矛盾或归因不清时，标记为“待验证”，不写成已解决瓶颈。

## 七、建议执行顺序

1. 修正或证明提交线性化点，消除提前可见风险。
2. 将“零复制”和“共享读锁”拆开 A/B；验证 writer 饥饿假设。
3. 缩短 `txn_state_latch_`，把物理 I/O 移出锁并做二次验证。
4. 将 heap 的文件级 DML 串行拆为 free-list 锁和页级锁。
5. 基于完整 `RecordKey` 减少冲突前无效工作。
6. 用等待计数决定是否实施 B+ 树页级锁耦合。
7. 最后才调 group commit、Buffer Pool、LOAD 和查询微优化。

每一步单独提交、单独回归、单独记录。任何正确性或恢复回退都立即停止后续性能外推。
