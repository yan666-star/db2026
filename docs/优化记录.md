# 性能优化记录

本文件只记录已经完成正式评测的改动。未复测的设想写入《决赛修改方案》，不在这里记为成果。

## 2026-08-12：MVCC 共享读取与单记录零重复复制

### 改动

- 将 `commit_apply_latch_` 改为读写锁：普通 MVCC 读取使用共享锁，版本发布、GC 和检查点继续使用独占锁。
- 单记录读取把物理记录所有权直接交给 MVCC 可见性判断，去掉一次堆分配和记录复制。
- 未修改 SQL、Wire、快照规则、提交日志和恢复流程。

### 结论

本轮不能记为“优化成功”。排名吞吐小幅提高，p99 下降，但完成率、p50 和连续提交稳定性明显变差，Payment 放弃数也由 5 增至 78。共享读锁可能让读取更容易并发，却增加了独占提交者等待或冲突放弃；这只是待验证假设，报告没有提供锁等待或 I/O profile，不能直接定因。

两次正式评测的装载时间、RSS、磁盘占用和可执行文件大小差异较大，因此它们不是严格受控的单变量 A/B。单记录零复制与共享锁也在同一提交中，无法判断各自贡献。

### 后续判定

1. 分开测量“仅去复制”和“再启用共享读锁”两个版本。
2. 记录 `commit_apply` 读/写等待、`txn_state_latch_` 等待、pending writer 超时和各事务放弃原因。
3. 若共享锁版本仍出现完成率、p50 或零提交桶明显回退，不继续扩大读并发；优先缩短读锁范围或加入防止 writer 饥饿的机制。
4. 所有候选仍须通过功能、隔离、COMMIT 持久化、在线一致性和 SIGKILL 恢复门禁。
