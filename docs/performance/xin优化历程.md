# xin 分支优化历程

> 分支：`xin`（当前最终答辩版）  
> 核心成果：正式评测排名吞吐 **134 → 15,620.8 NewOrder/min**（约 **116.57×**），P50 延迟约 **5.74s → 13.8ms**，功能 / 持久化 / 崩溃恢复全部 PASS。  
> 相关短文：[性能优化前后版本对比](性能优化前后版本对比.md) · [优化日记](优化日记.md) · [本轮修改关键要素](本轮修改关键要素.md)

本文按**时间线 + 方法 + 内容**整理 `xin` 上的性能与正确性演进，便于答辩口述与复盘。所有改动均落在通用机制内，不识别固定表名 / SQL 文本。

---

## 1. 背景与目标

### 1.1 评测约束

决赛性能赛题以 TPC-C 兼容饱和负载为主：

- 排名口径：32 客户端、多轮测量窗口的 **NewOrder/min 中位数**
- 必须同时通过：功能、Load、COMMIT 持久化、压测后一致性、`kill -9` 崩溃恢复
- 资源上限：学生进程树 RSS 等有硬限制（曾出现内存超线问题）

### 1.2 优化前的主要矛盾

早期正确性基线已能跑通，但吞吐卡在百级 NewOrder/min。诊断与设计文档（见 `docs/design/finals_no_global_wait_design.md`）把瓶颈归纳为：

1. **全局协调过重**：`commit_apply_latch_`、索引级 `split_latch_`、大范围 MVCC 闩锁把无关事务串在一起  
2. **急切写盘**：SI 路径语句期就改堆表 / 索引；一旦 abort，回滚 + 全库 checkpoint / fsync 代价巨大  
3. **批处理不完整**：`EXEC_BATCH` 只覆盖相邻同 prepared INSERT；NewOrder 仍拆成大量独立存储操作  
4. **计划侧浪费**：逻辑优化器薄弱，复合索引前缀与连接顺序利用不足，Delivery / OrderStatus / StockLevel 等扫面过大  
5. **恢复跟不上吞吐**：吞吐上去后 WAL 暴涨，恢复阶段逐条 `pread` 导致迟迟无法监听

目标不是堆特例快路径，而是把 **计划 → 暂存写 → 页级批提交 → 分片 MVCC → 局部索引闩 → 便宜 abort → 快速恢复** 串成一条通用链。

### 1.3 合规红线（全程未破）

- 不改 Wire v3、SQL 语法、4KB 页、堆 / B+ 树磁盘格式、WAL 记录格式  
- COMMIT ACK 前必须 `durable_lsn >= commit_lsn`  
- 未持久化事务不对其他事务可见  
- 保留 AUTO_ABORT、SI、SERIALIZABLE/SSI、FLOAT32、崩溃恢复  
- 禁止表名 / 列名 / statement_id / 客户端数特判

## 2. 总体路线图

```text
M0 基线与计数
  → M1–M2 缓冲池（PageGuard / 分片页表 / 内存上限）
  → M3 堆表页锁与空闲页
  → M4 B+Tree latch crabbing
  → M5 MVCC 分片 + 事务私有写批 + 提交发布
  → M6 WAL 组提交与恢复扫描加速
  → M7 同叶/同页批写 + 计划侧索引前缀与连接排序
  → M8 正确性修补、无效 abort 降本、内存超线收口
```

对应实现计划见 [newplan.md](newplan.md) 与 [../design/2026-08-14-finals-no-global-wait-implementation-plan.md](../design/2026-08-14-finals-no-global-wait-implementation-plan.md)。

## 3. 分阶段历程

### 阶段 A：架构转向 — “No Global Wait”

**代表提交：** `561480a` 文档、`865837c` 计划、`2dd1717` / `2d4172b` / `0d834ff` / `62f7144` 等实现提交。

**方式：**

- 引入 **TransactionWriteBatch**：执行器只 stage 逻辑写，不在语句期急切改物理页  
- SI 写在校验通过前对他人不可见；提交时再物理应用  
- MVCC 状态 **分片**（版本链、唯一键意图等），冲突 **fail-fast**，减少全局闩锁持有时间  

**内容要点：**

| 模块 | 做了什么 |
|------|----------|
| 事务 | 事务私有写批；`stage_insert/update/delete`；`merge_visible` 保证自身可见 |
| MVCC | `TxnRegistry` + Record/UniqueIntent 分片；提交时间戳与“连续可见前缀”分离 |
| 并发 | 去掉“一个 writer 拖死无关 reader”的全局 commit-apply 习惯用法 |

**为什么有效：** TPC-C NewOrder 写集大且热点集中；急切写 + 全局锁会把 abort 成本放大到整库。改为“先算后提交”，冲突事务多数只需丢弃内存批。

---

### 阶段 B：存储局部化 — 堆表与 B+Tree

**代表提交：** `940fbfc`（局部 crabbing）、`e20ee64`（按堆页 / 索引叶批提交）、`88da772`（批突变活锁修复）、`2de44d4`（空闲页候选）。

**方式：**

1. **B+Tree latch crabbing**：结构修改按页局部加锁，取消索引级大锁串行整棵树  
2. **同叶 / 同页批写**：排序后的 mutation 按目标叶页（或堆页）分组，一次写保护内完成一组 INSERT/DELETE  
3. **安全回退**：叶代际变化、归属校验失败、容量不足时回退完整树路径  
4. **加锁顺序**：分裂涉及当前页与兄弟页时按物理页号排序，避免死锁  

**效果：** NewOrder 连续写 `orders` / `new_orders` / `order_line` 等复合索引时，不再每条键都从根重走，缓冲池与闩锁压力显著下降。这是吞吐从“百级”跃到“万级”的存储层基础。

---

### 阶段 C：提交边界与正确性护栏

**代表提交：** `af29f3c`（durable 批提交边界）、`46525ca` / `447cd54`（语句期 SI/SSI 冲突中止）、后续若干 `修复` / `修正`。

**方式：**

- 批提交仍满足：**物理应用完成 → COMMIT 日志落盘 → 再发布可见**  
- 语句期检测到 SI/SSI 冲突则及时 abort，避免堆大量注定失败的工作  
- 发布失败可消费时间戳但不产生可见版本，保证快照只看到连续已发布前缀  

**内容要点（答辩常问）：**

- 读者通过版本链读；不能在索引尚未更新完时提前发布 `commit_ts`（早期两阶段 commit-apply 曾因此回退）  
- 历史索引代际变化后，扫描可刷新候选 RID；堆槽已删时仍可从历史版本恢复合法快照行  

---

### 阶段 D：查询计划 — 少扫、多用索引

**代表提交：** `c874c0e`（及前后规划器增强）。

**方式（`planner.cpp` 逻辑优化）：**

1. 谓词规范化与去重  
2. 单表谓词尽早下推  
3. 等值关系传播，扩大可用常量 / 连接约束  
4. 用“最长连续索引前缀”评分候选索引  
5. 综合连接关系 + 前缀覆盖 + 过滤条件做**通用连接排序**  
6. 索引只缩小候选，**最终仍执行全部 JOIN / WHERE**，结果语义不变  

**内容与收益：**

- Delivery、OrderStatus、StockLevel、一致性检查中的多表 JOIN，从大范围扫描转为复合前缀定位  
- 与已有“复合索引动态绑定 + 按页批量回表”能力衔接，而不是写死 TPC-C SQL  

---

### 阶段 E：便宜 Abort 与 WAL / 恢复

**代表提交：** `c874c0e` 中事务路径、`log_record_scanner` 相关恢复优化、以及更早的 abort / checkpoint 相关修补。

**方式：**

| 问题 | 做法 |
|------|------|
| 无物理副作用的 abort 仍全库 checkpoint / 单独 fsync | 纯内存 / 未改物理表的 abort 走轻量路径 |
| 高吞吐后 WAL 巨大，恢复 `pread` 爆炸 | 固定缓冲顺序扫描；analyze/redo 复用；消除重复全量扫 |
| Active loser 与 winner 唯一键冲突 | loser 跳过完整物理 REDO，改为收集信息后 UNDO |
| 恢复后就绪慢 | 有检查点时跳过无谓 free-list 重建；定向 flush；索引快照复制加速 |

**数据点（对比文档）：** 同一份约 35MiB WAL，恢复相关系统调用从约 63.5 万次降到约 3,312 次（约 -99.5%）。该优化不在事务热路径，但保证正式 Post-crash Recovery 可过。

---

### 阶段 F：资源收口 — 内存超线

**代表提交：** `76d7167`（缓冲池上限）、`44c52eb`（修改内存超线问题）等。

**方式：**

- 按机器内存估算缓冲池（约物理内存一定比例，带上下限 / 环境变量覆盖）  
- 控制 MVCC GC / 缓冲与评测 RSS 上限对齐  
- 在吞吐与内存之间取评测可接受的折中（最终正式评测峰值 RSS 约 5.56 GiB，仍在允许范围）

## 4. 方法学：怎么做优化

`xin` 上的做法可以概括为五步循环：

```text
1. 门禁先行：功能 + 一致性 + kill-9 不过，不谈 tpmC
2. 诊断定位：锁等待、fsync 次数、abort 分类、WAL/恢复 syscall
3. 通用机制改写：批处理、分片、局部闩、计划启发式——禁止特例 SQL
4. A/B 对照：同环境多轮中位数；正确性一票否决
5. 大胆回退：本地变快但 OJ / 正式一致性失败的候选全部撤回
```

**曾验证后回退的方向（避免重蹈）：**

- 过早缩短 commit-apply、在物理应用前发布版本  
- 扩大 `mvcc_latch_` 持锁范围做“批量可见性”  
- 部分机械容器优化（表面快、端到端变慢或 OJ WA）  
- 未充分回归的索引递归 merge（高提交率下可崩）  

详见 [优化日记.md](优化日记.md)。

## 5. 最终保留的核心内容（答辩可背）

按层次从下到上：

1. **缓冲池**：页表共享 / 分片、PageGuard、RSS 友好上限  
2. **堆表**：页级批应用、空闲页候选、与 MVCC 删除清理配合  
3. **B+Tree**：局部 crabbing、同叶批写、页号有序加锁、代际校验  
4. **事务 / MVCC**：写批暂存、分片状态、fail-fast 冲突、提交发布与可见前缀分离  
5. **计划**：谓词下推 / 等值传递 / 索引前缀评分 / 通用连接排序  
6. **Abort**：无物理修改时避免全库 checkpoint / 无意义 fsync  
7. **恢复**：缓冲扫描 WAL、loser 不完整物理 REDO、检查点与索引快照加速就绪  

**正式评测端点（摘要）：**

| 指标 | 起始 `2de44d4` | 最终 `34ce7b5`（其后还有内存修补至 `44c52eb`） |
|------|----------------:|-----------------------------------------------:|
| NewOrder/min（中位） | 134 | 15,620.8 |
| P50 | 5742.6 ms | 13.8 ms |
| P99 | 14701.9 ms | 63.7 ms |
| Abort rate | 15.14% | 14.59% |
| 正确性 | PASS | PASS（功能 25、恢复 5、Post-crash 全过） |

## 7. 答辩口述建议（2–3 分钟）

1. **问题**：正确性过后，32 客户端被全局锁、急切写和弱计划卡在百级吞吐。  
2. **路线**：写批暂存 + 分片 MVCC + 页局部索引闩 + 同叶批写 + 计划侧前缀与连接排序。  
3. **纪律**：COMMIT 先落盘再可见；冲突 fail-fast；无物理修改的 abort 不刷整库。  
4. **结果**：正式中位 1.56 万 NewOrder/min，延迟降至十毫秒级，恢复与一致性仍全过。  
5. **原则**：只改通用内核机制，用门禁和回退保证“快”建立在“对”之上。
