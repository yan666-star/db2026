# 性能优化前后版本对比

## 1. 对比范围

本文只比较性能优化开始时的正确性基线与最终版本，不展开记录中间版本及其失败过程。

| 项目 | 起始版本 | 最终版本 |
| --- | --- | --- |
| Git 版本 | `2de44d44b374755dc6698656a09d57abc63cb646` | `34ce7b51c309e5f6839313b5ffc9acfefce74a26` |
| 正式评测时间 | 2026-08-15 02:11:46 | 2026-08-15 14:16:12 |
| 评测结论 | PASS | PASS |
| 排名口径 | 32 客户端、三个有效测量窗口的 NewOrder/min 中位数 | 32 客户端、三个有效测量窗口的 NewOrder/min 中位数 |

两个端点版本都通过了当次评测要求的正确性检查。因此，下面的性能提升不是以跳过事务语义、WAL 持久化、MVCC 可见性或崩溃恢复为代价取得的。

## 2. 正式评测结果对比

| 指标 | 起始版本 | 最终版本 | 变化 |
| --- | ---: | ---: | ---: |
| 排名吞吐率 | 134 NewOrder/min | 15,620.8 NewOrder/min | **116.57 倍** |
| P50 延迟 | 5,742.599 ms | 13.844 ms | 降至约 1/414.81 |
| P99 延迟 | 14,701.886 ms | 63.665 ms | 降至约 1/230.92 |
| Abort rate | 15.14% | 14.59% | 下降 0.55 个百分点 |
| 仓库覆盖 | 完成规定测量 | 50/50，三个窗口全部完成 | 满足正式排名要求 |

最终三个正式测量窗口的 NewOrder/min 分别为：

- Round 1：22,535.6
- Round 2：15,620.8
- Round 3：14,376.0

最终排名取三轮中位数 15,620.8 NewOrder/min。相对于起始版本的 134 NewOrder/min，提升约 115.57 倍增量，即最终吞吐约为原来的 116.57 倍。延迟也从秒级、十秒级下降到十毫秒级，说明提升来自数据库执行路径和并发能力的整体变化，而不是单纯增加失败或提前放弃事务；最终 Abort rate 反而略有下降。

资源方面，最终评测的峰值学生进程树 RSS 为 5.56 GiB，高于起始版本的 2.29 GiB。这说明最终吞吐提升伴随着更高的内存占用；仅凭两次报告不能把增量精确归因到某个模块，但该代价在最终评测中仍处于允许范围。

## 3. 最终版本保留的核心改动

从 `2de44d44...` 到 `34ce7b51...`，`src/` 共涉及 25 个文件，净变化为新增约 1,201 行、删除约 214 行。以下只总结最终版本中仍然存在、并共同形成最终性能结果的通用数据库机制。

### 3.1 补全逻辑优化器与通用连接排序

起始版本的 `Planner::logical_optimization()` 基本为空，索引选择、条件处理和投影裁剪分散在物理计划构造过程中，难以系统地减少中间结果。

最终版本在 `src/optimizer/planner.cpp` 中形成了完整的查询级优化流程：

- 对谓词进行规范化和去重，避免重复计算同一过滤条件；
- 将只依赖单表的谓词尽早下推，减少进入连接算子的记录数；
- 根据等值关系传播可推导条件，使更多表获得可用的等值约束；
- 按“已连接列和本表常量条件能覆盖的最长连续索引前缀”评价候选索引；
- 综合连接关系、索引前缀覆盖程度和过滤条件选择通用连接顺序；
- 最终仍执行全部原始 JOIN 和 WHERE 条件，索引只负责缩小候选集合，不改变 SQL 结果。

这使 TPC-C 中涉及复合主键、仓库号、地区号和订单号的查询能够从大范围扫描转为复合索引前缀定位，尤其降低了 Delivery、OrderStatus、StockLevel 以及一致性关系检查的代价。

逻辑优化器会把结果交给已有的复合索引动态绑定和按页批量读取能力：完整键执行等值查找，真前缀执行范围扫描，无法形成连续前缀时回到通用扫描。因此，这一轮新增的是让优化器稳定、通用地选择这些能力，而不是新增一条只识别 TPC-C 表名或 SQL 文本的特殊路径。

### 3.2 B+Tree 同叶批写与安全的并发叶链操作

起始版本虽然已有 staged write 和部分批提交能力，但非单调 B+Tree 叶链会使同一叶页上的批量写入反复从根节点重新查找，并在分裂、兄弟页和页号顺序之间产生额外锁竞争。

最终版本在 `src/index/ix_index_handle.cpp` 中：

- 将排序后的索引 mutation 按目标叶页分组；
- 对同一叶页的一组 INSERT/DELETE 在一次写保护下完成；
- 只有叶页容量不足、代际变化或归属校验失败时才回退到完整树路径；
- 叶页分裂涉及当前页和相邻页时按物理页号确定加锁顺序；
- 每次快速路径仍校验叶页代际、键范围、前后兄弟关系和唯一键约束。

NewOrder 会连续写入 orders、new_orders、order_line 等复合索引。同叶批写消除了逐条重走根路径的大量 buffer、latch 和比较开销，是吞吐从百级跃升到万级的重要存储层基础。

### 3.3 缩短无效回滚路径

最终版本缩短了没有物理副作用的事务中止路径：

- 没有产生物理修改的 abort 不再执行全库 checkpoint，也不再单独触发一次无意义的 WAL fsync；
- 已产生修改的事务仍执行完整 AUTO_ABORT、WAL、heap、index 和 MVCC 清理。

这避免了热点冲突事务在没有改动任何数据时仍触发昂贵的全库操作和同步写。优化没有跳过必要回滚，也没有削弱冲突检测。最终正式评测的 Abort rate 从 15.14% 降至 14.59%，说明吞吐增长不是由放弃更多事务获得的。

### 3.4 MVCC 快照、提交发布与历史版本可见性

批量提交和并发物理应用提高吞吐后，必须保证快照只能包含已经完整发布的提交。最终版本在 `src/transaction/txn_registry.cpp` 和 `transaction_manager.cpp` 中将“分配提交时间戳”与“推进对新快照可见的连续提交前缀”分离：

- 事务开始或进入 snapshot admission 时只捕获已经发布完成的时间戳；
- 提交事务先完成 index version 和 heap MVCC version 的发布，再把对应时间戳加入连续可见前缀；
- 并发提交完成顺序不同于时间戳分配顺序时，后续快照不会跨过尚未发布完成的空洞；
- 发布失败会消费时间戳但不产生可见版本，并允许后续连续前缀继续推进；
- 索引扫描在历史索引版本代际变化后补充刷新候选 RID，heap 物理槽已删除时仍允许 MVCC 从历史版本恢复合法快照记录。

这些修改主要承担正确性保护：它们使更激进的并发、批提交和索引更新能够继续运行，而不会出现部分提交可见、旧快照漏行或删除后错误消失。

### 3.5 WAL 顺序缓冲扫描与恢复启动加速

高吞吐版本会产生远大于起始版本的 WAL。如果恢复阶段仍对每条日志分别读取 header 和 body，并在每次读取前查询文件大小，正式规模重启会产生大量 `pread64` 和文件状态系统调用，导致数据库迟迟无法监听端口。

最终版本新增 `src/recovery/log_record_scanner.{h,cpp}`：

- 使用固定容量缓冲区顺序扫描 WAL；
- 正确处理跨缓冲区日志记录和末尾不完整记录；
- `analyze()` 与 `redo()` 复用统一扫描器；
- `analyze()` 得到的有效日志末尾和最大 LSN 直接初始化 `LogManager`，消除启动阶段的一次重复全量扫描；
- active loser 仍只登记给逆序 UNDO，不执行会与 committed winner 冲突的物理 REDO；
- 不改变 WAL 格式、COMMIT 持久化顺序或恢复后的可见性语义。

本地对同一份约 35.1 MiB WAL 的系统调用采样中，恢复相关调用量从约 63.5 万次降到约 3,312 次，下降约 99.5%。该优化不进入正常 TPC-C 事务热路径，却保证了吞吐提高、WAL 增大后仍能通过正式 Post-crash Recovery。

## 4. 正确性保持结果

最终版本不是只通过 TPC-C 吞吐测量，而是完成了完整评测链：

| 正确性项目 | 最终结果 |
| --- | --- |
| 功能测试 | 25 项全部 PASS |
| 恢复测试 | 5 项全部 PASS |
| COMMIT 持久化审计 | 32/32 成功应答均由 `fsync` 覆盖 |
| TPC-C LOAD | 9 张表、25,051,805 行全部校验通过 |
| 正式排名窗口 | 三轮全部完成，仓库覆盖 50/50 |
| Pre-crash consistency | 13 项通过 |
| Post-crash aggregate checks | 44 项通过 |
| Post-crash relational checks | 5,974 项通过 |
| Post-crash Recovery | PASS，恢复及检查总耗时 101.35s |

Post-crash 的 101.35 秒包含恢复后的大量聚合和关系验证，不等同于监听 readiness 时间；最终报告判定 Post-crash Recovery 为 PASS。

## 5. 最终结论

从 `2de44d44...` 到 `34ce7b51...`，优化没有改变决赛 Wire v3、SQL、TPC-C、MVCC、WAL 和 COMMIT 应答语义。最终版本通过逻辑优化与复合索引前缀规划、B+Tree 同叶批写、无效回滚路径缩短、MVCC 提交发布修正以及 WAL 恢复扫描加速，将正式排名吞吐从 134 提高到 15,620.8 NewOrder/min，达到原来的约 116.57 倍；同时 P50 从 5.74 秒降到 13.844 毫秒，P99 从 14.70 秒降到 63.665 毫秒，并通过全部功能、持久化、恢复和正式 TPC-C 检查。

这次优化的核心不是某一个特例快速路径，而是把查询计划、索引访问、批量存储、事务并发和崩溃恢复串成了一条能够在 32 客户端、50 仓库正式负载下共同工作的通用执行链。
