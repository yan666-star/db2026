## 二、不可削弱的十项要求

### 2.1 通用 SQL 与不透明标识符

实现必须按收到的 SQL、schema 和类型执行，不能依赖 TPC-C 的公开表名、列名、固定 statement_id、客户端编号、数据库名、CSV 文件名或请求交错。

必须覆盖：

- 多列 `UPDATE`，右值按更新前的同一行计算并原子应用；
- `col = col +/- value +/- value` 左结合算术；
- `!=` 与 `<>` 两种不等于语法；
- 多表 JOIN、别名、复合谓词、聚合、`DISTINCT`、排序和 `LIMIT`；
- 复合索引最左前缀、唯一索引和索引/表扫描结果一致；
- INT、CHAR、FLOAT 的比较、绑定、存储和返回语义一致。

性能快速路径的前置条件不满足时，必须回退到通用执行路径，而不是返回近似结果或跳过语义。

### 2.2 Wire Protocol 状态机

服务端必须完整实现公开 Wire v3 契约：

- 握手及 8 字节 frame header 使用循环短读/短写；
- frame 长度不包含 header，payload 最大 1 MiB；
- `EXEC_STREAM` 查询严格返回 `META → ROW* → RESULT_END`，命令只返回 `COMMAND_OK`；
- `PREPARE_SET` 全部验证成功后原子替换连接级字典；失败时旧字典仍可用；
- `EXEC_BATCH` 严格按 operation 顺序执行，只返回一个完整 `BATCH_RESULT`；
- 成功、可重试冲突和不可重试错误的 operation 计数、失败位置和结果集数量符合协议；
- 同一连接只有一个进行中请求，不自行重排，不把中间结果拖到下一次请求发送。

当前实现入口主要位于：

- `src/network/wire_codec.cpp`
- `src/network/wire_messages.cpp`
- `src/network/request_dispatcher.cpp`
- `src/network/prepared_dictionary.cpp`
- `src/execution/sql_execution_service.cpp`

### 2.3 AUTO_ABORT 原子回滚

所有排名 batch 均带 AUTO_ABORT。任一 operation 失败时必须：

1. 停止执行后续 operation；
2. 回滚本事务已经产生的全部 heap、index、MVCC 和事务元数据影响；
3. 释放锁、写意向和等待关系；
4. 结束活动事务；
5. 清空失败 batch 已收集的部分查询结果；
6. 最后发送一个 `TRANSACTION_ABORT` 或 `ERROR` 状态的 `BATCH_RESULT`。

客户端不会再补发第二次 ABORT。不能先响应再异步清理，也不能通过断开连接代替事务回滚。

### 2.4 SNAPSHOT ISOLATION 与 SERIALIZABLE

排名固定使用 SNAPSHOT ISOLATION；功能测试还会检查 SERIALIZABLE。必须保证：

- 事务快照在规定边界建立，整个事务读取同一合法快照；
- 未提交、已回滚和仍在物理应用的版本不可见；
- 同一记录的并发写满足 first-committer-wins 或等价冲突规则；
- 不发生脏读、丢失更新、删除后复活和唯一键重复；
- SERIALIZABLE 下能阻止规定的读写偏斜、谓词写偏斜和幻读；
- 冲突失败返回可重试事务中止，而不是卡住连接直至超时。

MVCC 分片、写意向、早期冲突检测或 admission control 只能改变等待位置，不能改变隔离结果。

### 2.5 提交线性化与可见性

每个成功事务必须有唯一、可说明、可测试的提交线性化点：

- 线性化点之前，其他事务只能看到完整旧状态；
- 线性化点之后，其他事务只能看到完整新状态；
- heap、全部索引、MVCC 版本和唯一约束不能出现部分提交；
- 一旦发布为已提交，就不能再因普通冲突或物理校验失败而回滚；
- 新事务不得把尚未完成提交的事务纳入快照。

特别注意：当前成功基线的 `commit_mvcc()` 在源码中先为 pending version 填入 `commit_ts`，随后才在 Phase 2 应用 heap/index，外层 `commit()` 再追加并稳定化 COMMIT WAL。虽然本次自动测评通过，但“可见性早于物理完成或持久化”不应作为可保留的正确性设计。下一轮重构必须把可见性发布移到物理应用成功且提交不能再失败之后，或者引入能证明等价正确的私有物理版本与 MVCC-aware index。

### 2.6 WAL 与 COMMIT 持久化

每次返回 COMMIT 成功前必须满足：

- 该事务的所有 WAL 按 LSN 顺序追加到同一个可审计 WAL 对象；
- 覆盖该事务 COMMIT record 的稳定化操作已经成功；
- `durable_lsn >= commit_lsn`；
- 写页遵守 WAL-before-data；
- `fsync`/`fdatasync` 失败时不能返回成功；
- group commit 可以让多个事务共享一次稳定化，但每个等待者只能在覆盖自己的 durable watermark 后收到 ACK。

禁止 ACK 提前、只 flush 用户态缓冲区、把 COMMIT 写到不可审计的另一份日志，或通过定时器假定已经落盘。

### 2.7 heap、索引和唯一约束原子一致

任意成功 INSERT、UPDATE、DELETE 后：

- heap 中的记录与每个索引项一一对应；
- 更新索引列时，旧键删除和新键插入属于同一事务；
- 唯一冲突在提交成功前确定，失败事务不得留下幽灵索引项；
- ABORT、断连 AUTO_ABORT 和恢复 UNDO 后均恢复到同一个合法旧状态；
- 表扫描和任一合法索引路径在可见性过滤后返回相同集合。

页级并发或 latch crabbing 必须明确保护 bitmap、`num_records`、free-list、父子指针、兄弟链、root 元数据、split/merge 和 buffer pin 生命周期。

### 2.8 TPC-C 五类事务语义

不能只优化 NewOrder。五类事务都必须持续成功提交并满足公开不变量：

- NewOrder：原子分配 `d_next_o_id`，正确计算金额和库存字段，远程供货语义正确，无效商品完整回滚；
- Payment：同步累计 warehouse、district、customer 金额并插入一条 history；
- OrderStatus：按规范选择客户、最近订单及其明细；
- Delivery：每个 district 原子领取最早未配送订单，更新订单、明细和客户余额，不能重复领取；
- StockLevel：按规定订单窗口统计低库存的不同商品。

正式负载会集中访问热点 district、stock 和跨仓客户。锁排序和冲突处理必须对真实交错成立，不能依赖单线程或固定仓库归属。

### 2.9 FLOAT32、聚合和 LOAD

- FLOAT 存储、literal、typed bind 和 Wire 返回都必须遵守 IEEE-754 binary32；
- FLOAT 算术按赛题规定舍入；严格校验要求 0 ULP 时不能用近似缓存；
- `SUM(FLOAT)` 将 binary32 输入精确扩展到 binary64 累加，最后只舍入一次为 binary32；
- LOAD 必须根据 CSV header 建立列映射，不能假定固定文件列顺序；
- LOAD 仍是原子操作，失败后不能留下部分表或部分索引；
- 初始 stock YTD、行数、范围、关联完整性和全部九表校验必须通过。

LOAD 优化可以批量解析、批量插入和批量建索引，但不能跳过 WAL、索引维护或最终校验。

### 2.10 SIGKILL 恢复与启动就绪

排名结束后数据库会被 SIGKILL。重启必须在 90 秒内：

1. 完成 WAL 分析、REDO、UNDO 和必要的索引/空闲链恢复；
2. 由目标 rmdb 进程拥有监听端口；
3. 完成握手；
4. 通过 Wire 执行 `show tables;`；
5. 通过恢复后一致性和持久性检查。

成功提交的数据必须存在，未成功提交的数据不可见。恢复必须幂等；重复崩溃不能导致已删除记录复活、索引重复、free-list 损坏或数据库持续膨胀。

当前恢复代码对 active loser 的 action 记录只登记给 UNDO、不执行物理 REDO，这一行为用于避免 loser 与 committed winner 发生唯一索引冲突。后续优化恢复扫描时必须保留等价语义。

## 三、当前成功实现中应保留的能力

以下项目已经由源码和本次报告共同提供了可复用基线：

| 能力 | 当前实现锚点 | 后续要求 |
| --- | --- | --- |
| Prepared 协议 | `prepared_dictionary.cpp`、`request_dispatcher.cpp` | 保持原子字典安装、typed bind 和唯一 BATCH_RESULT |
| Batch AUTO_ABORT | `RequestDispatcher::dispatch_batch()` | 失败响应前完成回滚并清空部分结果 |
| 持久 COMMIT | `TransactionManager::commit()`、`LogManager::force_flush_up_to()` | ACK 前 durable watermark 覆盖自身 commit LSN |
| MVCC/SSI 元数据 | `transaction_manager.cpp` 的 txn state 和 MVCC shards | 可分片，但不可取消冲突与谓词依赖 |
| loser 恢复 | `RecoveryManager::redo()` / `undo()` | active loser 不作为 winner 物理 REDO，UNDO 可重复 |
| LOAD 原子性 | `SqlExecutionService::execute_load()` | 保留完整回滚、索引和最终 COMMIT |
| FLOAT/Wire 类型 | parser、execution、wire codec | 保持 binary32 位级语义 |

“应保留的能力”不等于必须保留当前锁粒度、容器或函数结构。允许重构实现，只要外部语义和崩溃边界不变。

关键 SIGKILL 注入点至少包括：写操作 WAL append 前后、COMMIT append 前后、稳定化前后、物理应用中间、可见性发布前后、checkpoint 元数据更新前后。

## 五、变更准入规则

每项优化必须回答并记录：

1. 改动消除了哪个已测量瓶颈？
2. 新的并发对象、锁顺序和线性化点是什么？
3. WAL、heap、index、MVCC 的提交与回滚顺序是什么？
4. 在每个崩溃点上，恢复会把事务判为 winner 还是 loser？
5. 通用慢路径何时启用？
6. 哪些测试证明它仍满足本文件要求？
7. 吞吐提升是否可复现，是否以完成率或尾延迟恶化为代价？

不能明确回答上述问题的改动，不进入主分支。任何基于固定名称、固定测试数据、跳过持久化、提前可见、部分回滚或近似结果的方案均直接否决。
