# src 根目录：线下资格赛修改百科

## 0. 新增功能不要一上来全仓搜索乱改

先判断题目属于哪一种：

```text
只是新写法，能翻译成旧语义：主要改 parser
需要新增语义标志：parser -> Analyze -> Plan -> Executor
需要改表/索引数据：再进入 System/Record/Index/Transaction
只是换缓存算法：Replacer 接口不动，替换实现
```

### 0.1 以 SEMI JOIN 走完整链

```text
lex.l 识别 SEMI
yacc.y 构造 join_type
SelectStmt 保存
Query 复制
JoinPlan 保存
Portal 把 Plan 交给 JoinExecutor
JoinExecutor 只输出左行且每个左行一次
```

任何一步漏传，后面看到的都是默认 INNER_JOIN。

### 0.2 `Portal::convert_plan_executor(plan,context,...)`

最重要参数：

| 参数 | 含义 |
|---|---|
| `plan` | 当前递归处理的 Plan 节点 |
| `context` | 当前事务和日志环境 |
| `filter_plan` | 给扫描器回填 Filter rows 的可选指针 |
| `enable_equality_cache` | 是否允许特定扫描缓存 |
| `track_serializable_reads` | 是否登记串行化读集合 |

函数看到 ProjectionPlan，会先递归转换 `x->subplan_` 得到 prev Executor，再 new ProjectionExecutor。看到 JoinPlan，会分别递归 left/right，再 new JoinExecutor。

为什么递归：Plan 本身是树，Executor 也必须按相同父子关系构造。

### 0.3 `Portal::start(plan,context)` 与 `run`

start 做准备：把 Plan 分类、创建 Executor、UPDATE/DELETE 先收集 Rid。run 真正调用 QlManager。将两者分开使 PortalStmt 能同时保存输出列、执行器和计划。

### 0.4 新功能是否需要改 Portal

```text
旧 Plan 加字段，旧 Executor 读取 -> 通常不改 Portal
新 Plan 类型/新 Executor -> 必须加转换分支
改变输出 schema -> 检查 collect_output_cols
```

例如 ProjectionPlan 加 `is_distinct_`，Portal 本来就把 `x.get()` 传给 ProjectionExecutor，不需要新分支；新增 DistinctPlan 则必须加。

## 1. 总调用链

```text
客户端 SQL
 -> rmdb.cpp：连接、会话、事务边界、调用解析器
 -> parser：SQL -> AST
 -> Analyze：AST -> Query
 -> Optimizer/Planner：Query -> Plan 树
 -> Portal：Plan 树 -> Executor 树
 -> QlManager：执行查询、DDL、事务命令
 -> execution/system/record/index/transaction
```

## 3. rmdb.cpp 的对象归属

服务启动时创建全局管理器，它们不是一条 SQL 的局部变量：

| 对象 | 类型 | 拥有/依赖 | 作用 |
|---|---|---|---|
| `disk_manager` | `DiskManager` | 最底层全局对象 | 文件页读写 |
| `buffer_pool_manager` | `BufferPoolManager` | 依赖 DiskManager | 缓存磁盘页 |
| `rm_manager` | `RmManager` | 依赖磁盘和缓冲池 | 表记录文件 |
| `ix_manager` | `IxManager` | 依赖磁盘和缓冲池 | 索引文件 |
| `sm_manager` | `SmManager` | 依赖 RM/IX | 数据库目录、表、索引句柄 |
| `txn_manager` | `TransactionManager` | 依赖锁和 SM | 事务开始、提交、回滚、MVCC |
| `planner` | `Planner` | 依赖 SM | Query 转 Plan |
| `optimizer` | `Optimizer` | 依赖 Planner | 语句总计划入口 |
| `ql_manager` | `QlManager` | 依赖 SM/事务 | 实际运行查询和命令 |
| `portal` | `Portal` | 依赖 SM | Plan 转 Executor |
| `analyze` | `Analyze` | 依赖 SM | AST 语义分析 |

每个客户端线程的重要变量：

| 变量 | 归属/生命周期 | 作用 |
|---|---|---|
| `fd` | `client_handler`，连接期 | 客户端 socket |
| `data_recv` | 每次循环复用 | 接收 SQL |
| `data_send` | 连接期缓冲 | 返回结果 |
| `offset` | 当前响应 | 已写入返回缓冲的长度 |
| `txn_id` | 整个连接 | 让 BEGIN 后多条 SQL 找到同一事务 |
| `session_isolation` | 整个连接 | 当前会话隔离级别 |
| `Context` | 连接/语句调用 | 打包事务、日志、锁、输出缓冲 |
| `raw_sql` | 当前请求 | 原始 SQL，用于事务边界和特殊命令识别 |

## 4. 一条普通 SELECT 的调用顺序

```text
yy_scan_string/yyparse
 -> ast::parse_tree
 -> Analyze::do_analyze
 -> Optimizer::plan_query
 -> Portal::start
 -> Portal::convert_plan_executor
 -> Portal::run
 -> QlManager::select_from
```

新增标准 SQL 关键字时，优先从 parser 修改；不要在 `rmdb.cpp` 用字符串判断绕过 parser。只有 `LOAD`、输出开关这类协议/会话命令才适合在入口提前处理。

## 5. Portal 的三个关键职责

### 5.1 PortalStmt

| 字段 | 类型 | 作用 |
|---|---|---|
| `tag` | `PortalTag` | 查询、DDL/DML、命令工具等运行类别 |
| `sel_cols` | `vector<TabCol>` | 输出列标题 |
| `root` | `unique_ptr<AbstractExecutor>` | 执行器树所有权根节点 |
| `plan` | `shared_ptr<Plan>` | 原计划树，EXPLAIN/统计仍会使用 |

### 5.2 `start()`

读取 DMLPlan/OtherPlan，决定：直接执行命令、先扫描 Rid 再 UPDATE/DELETE，还是构造 SELECT 执行器树。

### 5.3 `convert_plan_executor()`

递归结构：父 Plan 先递归转换 `subplan_`/`left_`/`right_`，再把子执行器移动给父 Executor。若新增真正独立的 Plan 类型，必须在这里加入 `dynamic_pointer_cast<NewPlan>` 分支；若只是给已有 Plan 加布尔标志，通常无需改 Portal。

## 7. 根目录修改原则

1. `unique_ptr<Executor>` 表示唯一拥有执行器；向父节点传递用 `std::move`。
2. `shared_ptr<Plan>` 允许 Portal、EXPLAIN、执行器共同引用计划。
3. `Context *` 是借用指针，Executor 不负责释放。
4. 新 Plan 若 Portal 不识别，会落入 Unexpected field type。
5. 不要把 SQL 语义判断都塞进 rmdb.cpp；名字和类型检查属于 Analyze。

## 8. 新增功能的完整纸上推演法

拿到题目先写一行“最小新增状态”。例如 ANTI JOIN 的新增状态只有 `JoinType=ANTI_JOIN`，BETWEEN 甚至不新增状态而是重写成两个 Condition。

然后画：

```text
谁产生 -> 谁保存 -> 谁传递 -> 谁执行 -> 谁输出
```

如果某一层没有读取新增字段，这个字段会在链路中断掉。典型中断：AST 有 join_type，但 Query 没复制；Plan 有 type，但 Portal 总创建旧 Executor；Executor 输出左列，但 Portal 表头仍收集左右列。

## 9. 根目录专题：新增独立 Plan/Executor

必须同步四处：

```text
plan.h：PlanTag + NewPlan
planner.cpp/optimizer.h：生成 NewPlan
portal.h::convert_plan_executor：NewPlan -> NewExecutor
execution：实现 NewExecutor
```

Portal 分支骨架：

```cpp
else if (auto x = std::dynamic_pointer_cast<NewPlan>(plan)) {
    return std::make_unique<NewExecutor>(
        convert_plan_executor(x->subplan_, context),
        x.get(), context);
}
```

若新功能能复用 Projection/Filter/Join，只给旧 Plan 加字段通常改动更少。

## 10. 根目录专题：新增非标准会话命令

标准 SQL 优先走 parser。只有 `LOAD file INTO table`、输出开关等协议命令才在 rmdb.cpp 预解析。新增时需要明确：

- 是否需要当前事务。
- 是否允许在显式事务内。
- 失败是否触发 abort。
- 输出是否写 data_send 和输出文件。
- 命令文本是否区分大小写。

不要在持有全局 parser mutex 时做长时间文件 I/O。

## 11. Portal 输出列同步

新算子改变输出 schema 时，`collect_output_cols()` 和 Executor::cols() 必须一致。例如 ANTI JOIN 只输出左表列：执行器记录长度、cols、Portal 表头三者都要只含左侧。否则可能记录是左表长度，但打印器按左右列 offset 读越界。

## 12. 资格赛现场改动优先级

```text
能 parser 重写 -> 不加执行器
能旧 Executor 加标志 -> 不加新 Plan
必须改变迭代语义 -> 新 Plan/Executor
涉及物理数据 -> 同查 record/index/transaction
涉及磁盘格式 -> 最后选择，风险最高
```
