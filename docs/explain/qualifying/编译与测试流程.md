## 2. 编译（Release，对齐测评）

```bash
cd /root/db2026
```

**含义：** 回到仓库根。

```bash
mkdir -p build
```

**含义：** 创建构建目录 `build/`；`-p` 表示已存在也不报错。源码与编译产物分离，方便清理。

```bash
cd build
```

**含义：** 进入构建目录，在此执行 cmake/编译，产物落在 `build/` 下。

```bash
cmake .. -DCMAKE_BUILD_TYPE=Release
```

**含义：**

- `cmake ..`：读取上一级目录的 `CMakeLists.txt`，在当前 `build/` 生成构建文件。
- `-DCMAKE_BUILD_TYPE=Release`：Release 模式（优化开、调试符号少），接近测评的 `-O2` 构建。

```bash
cmake --build . -j$(nproc)
```

**含义：**

- `cmake --build .`：按刚才生成的配置真正编译。
- `-j$(nproc)`：并行任务数 = CPU 核数，加快编译。
- 会编出 `rmdb`、`unit_test`、各静态库等。

只编服务端：

```bash
cmake --build . -j$(nproc) --target rmdb
```

**含义：** 只构建名为 `rmdb` 的目标，改了一点业务代码时比重编全部更快。

**产物：**

| 路径 | 说明 |
|------|------|
| `build/bin/rmdb` | 数据库服务进程（监听 **8765**） |
| `build/bin/unit_test` | GoogleTest 单元测试可执行文件 |

改过 `lex.l` / `yacc.y` 后需重新编译 parser/`rmdb`（cmake 会驱动 flex/bison）。

彻底重编：

```bash
cd /root/db2026
rm -rf build
```

**含义：** 删掉整个构建树（中间文件、旧配置），避免缓存/旧目标导致怪问题。

```bash
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release
cmake --build . -j$(nproc)
```

**含义：** 空目录重新配置并全量编译（`&&` 表示前一条成功才执行后一条）。

可选：编译交互客户端

```bash
cd /root/db2026/rmdb_client
mkdir -p build && cd build
cmake .. && cmake --build . -j$(nproc)
```

**含义：** 进入官方 client 子工程，同样用 cmake 编出可连 `8765` 的交互客户端。

## 3. 启动 / 停止服务

```bash
cd /root/db2026
```

**含义：** 从仓库根启动时，相对路径 `./build/bin/rmdb` 才正确。

```bash
pkill -9 -x rmdb 2>/dev/null || true
```

**含义：**

- `pkill -9 -x rmdb`：按精确进程名 `rmdb` 发 SIGKILL，强制杀掉残留服务（释放 8765）。
- `2>/dev/null`：没有进程时的报错丢到空设备。
- `|| true`：整句始终返回成功，避免脚本因“没得杀”而中断。

```bash
rm -rf /tmp/my_test_db
```

**含义：** 删掉旧的测试库目录，保证从空库开始，避免脏数据干扰。

```bash
./build/bin/rmdb /tmp/my_test_db > /tmp/rmdb.log 2>&1 &
```

**含义：**

- `./build/bin/rmdb`：启动数据库服务。
- `/tmp/my_test_db`：库目录路径；不存在则创建，数据文件落在此目录。
- `> /tmp/rmdb.log`：标准输出写到日志文件。
- `2>&1`：标准错误也并进同一日志。
- `&`：后台运行，终端还能继续敲命令。

等待端口就绪：

```bash
python3 - <<'PY'
import socket, time
for _ in range(50):
    try:
        socket.create_connection(("127.0.0.1", 8765), 0.2).close()
        print("ready")
        break
    except OSError:
        time.sleep(0.1)
else:
    raise SystemExit("rmdb not up, see /tmp/rmdb.log")
PY
```

**含义：** 内嵌一小段 Python（`<<'PY' ... PY` 是 heredoc）：

- 循环最多约 5 秒，尝试 TCP 连接本机 `8765`。
- 连上就说明服务在听端口，打印 `ready`。
- 一直失败则退出并提示看日志（进程可能启动失败）。

测活（Wire：SQL + `\0`）：

```bash
python3 - <<'PY'
import socket
s = socket.create_connection(("127.0.0.1", 8765), 5)
s.sendall(b"show tables;\0")
print(s.recv(8192))
s.close()
PY
```

**含义：**

- 建立到 RMDB 的 TCP 连接（超时 5 秒）。
- 按 Wire 习惯发送 `show tables;` 并以 **`\0`** 结束一帧。
- 打印服务器返回；能收到合法响应说明 SQL 路径可用（不仅是端口开了）。
- `close()` 关闭连接。

结束进程：

```bash
pkill -9 -x rmdb 2>/dev/null || true
```

**含义：** 与上文相同，测完强制停掉服务。

**注意：**

- `rmdb <库名>` 在**启动时的当前工作目录**语义下解析路径（绝对路径如 `/tmp/...` 不受 cwd 影响）。
- 同时只能有一个 `rmdb` 占用 8765。
- 事务状态绑定在 TCP 连接上；多语句脚本需保持同一连接。

## 5. 功能 / SQL 回归

### 5.1 手工发 SQL

起库后：

```bash
python3 - <<'PY'
import socket

def exe(sql):
    s = socket.create_connection(("127.0.0.1", 8765), 10)
    s.sendall(sql.encode() + b"\0")
    data = b""
    while b"\0" not in data:
        chunk = s.recv(8192)
        if not chunk:
            break
        data += chunk
    s.close()
    print(data.split(b"\0", 1)[0].decode("utf-8", "replace"))

exe("create table t(a int);")
exe("insert into t values (1);")
exe("select * from t;")
PY
```

**含义：**

| 片段 | 含义 |
|------|------|
| `create_connection(..., 8765)` | 连上数据库服务 |
| `sql.encode() + b"\0"` | 把 SQL 编成字节并加协议结束符 |
| `recv` 循环直到见到 `\0` | 读完一帧响应 |
| `s.close()` | 本例每句新建连接；简单冒烟够用，**带事务的多句应用 `run_sql.py` 保单连接** |
| 三个 `exe(...)` | 依次建表、插入、查询，打印结果对照预期 |

或使用已编译的 `rmdb_client`（交互输入 SQL，内部同样连 `127.0.0.1:8765`）。

隔离级别示例：

```sql
set transaction isolation level snapshot isolation;
set transaction isolation level serializable;
```

**含义：** 会话级设置快照隔离 / 可串行化；决赛功能门禁会测这类配置，之后新开的事务按该级别执行。

### 5.2 仓库自带恢复 / 检查点脚本

```bash
cd /root/db2026
pkill -9 -x rmdb 2>/dev/null || true
rm -rf recovery_no_checkpoint_db
```

**含义：** 回仓库根、杀旧进程、删掉本用例数据库目录，保证干净环境。

```bash
./build/bin/rmdb recovery_no_checkpoint_db > /tmp/rmdb_rec.log 2>&1 &

```

**含义：** 在仓库根下创建/打开相对目录 `recovery_no_checkpoint_db` 并后台启动；`sleep 2` 粗等服务起来（也可用前面的端口探测脚本）。

```bash
python3 SQL测试/sql_test/run_sql.py SQL测试/sql_test/01_without_checkpoint_before_crash.sql
```

**含义：**

- 运行仓库提供的 SQL 驱动：`run_sql.py`。
- **同一条 TCP 连接**上顺序执行 `.sql` 里的语句（适合 BEGIN/COMMIT）。
- 该文件通常以 `crash` 结尾，会让服务器异常退出，模拟崩溃。

```bash
./build/bin/rmdb recovery_no_checkpoint_db > /tmp/rmdb_rec.log 2>&1 &
sleep 2
python3 SQL测试/sql_test/run_sql.py SQL测试/sql_test/02_without_checkpoint_verify.sql
```

**含义：** 用**同一个库目录**重启（触发恢复），再跑验证 SQL，检查崩溃前已提交数据是否还在、未提交是否消失。

更多说明见 `SQL测试/sql_test/README.md`、`SQL测试/10_sql_test/README.md`。

## 8. 提交前自检清单

| 阶段 | 本地怎么验 | 含义 |
|------|------------|------|
| 编译 | Release 成功，`rmdb` 可运行 | 测评第一关就能过编译 |
| 功能 | DDL/DML/聚合/索引/隔离级 | 对应功能正确性门禁 |
| COMMIT 持久化 | 提交后 kill -9 再重启 | 对应 COMMIT 审计/持久语义 |
| 崩溃恢复 | 有/无 checkpoint | 对应恢复用例 |
| LOAD | load + COUNT | 对应装载与行数校验 |
| TPC-C 形事务 | 单线程跑通混合事务 | 降低排名阶段直接 ERROR/超时 |
| Post-crash | 崩溃后大表聚合仍对 | 对应性能阶段末尾一致性 |

官方流水线（参考）：Compile → Function + 持久化/恢复 → Load → TPC-C → Pre-crash 一致性 → SIGKILL → Post-crash 一致性 →（通过后）I/O 诊断。

## 常见问题（对应指令层面）

1. **工作目录 / 库路径**  
   - 相对库名：相对**启动 rmdb 时的 cwd**。  
   - `/tmp/xxx`：绝对路径，与 cwd 无关。  
   - `LOAD` 里的相对文件路径：相对**库目录**。

2. **`pkill -9 -x rmdb`**  
   端口被占、旧进程未退时必做；`-9` 不可被进程正常清理逻辑拦住。

3. **SQL 为何要加 `\0`**  
   本项目简易/兼容路径用空字符标一帧结束；测评正式协议更完整，但本地冒烟这样即可。

4. **`run_sql.py` vs 每句新建连接的 `exe()`**  
   事务、多语句、崩溃用例用 `run_sql.py`（单连接）；单句冒烟用短 Python 即可。

5. **解析改挂了**  
   `rm -rf build` 后重新 `cmake` + 全量编译，避免旧的 flex/bison 产物残留。

## 题干样例 SQL 怎么纳入测试（完整流程）

目标：把赛题/测试说明里的「测试示例 + 期待输出」变成可重复执行的本地用例。

### A. 准备目录与文件

建议按题目编号建目录（名字可自定）：

```bash
cd /root/db2026
mkdir -p SQL测试/from_problem/q2
```

**含义：** 专门放「从题干抄来的」用例，和仓库自带的恢复脚本分开，避免搞混。

把题干 SQL 贴进文件，例如 `SQL测试/from_problem/q2/01_create_table.sql`：

```sql
-- 来源：测试说明 / 题目二 测试点1
-- 期待：show tables 依次看到 t1；t1+t2；仅 t2；空

create table t1(id int,name char(4));
show tables;
create table t2(id int);
show tables;
drop table t1;
show tables;
drop table t2;
show tables;
```

**书写规则：**

| 规则 | 说明 |
|------|------|
| 每条语句以 `;` 结束 | `run_sql.py` 按分号切分 |
| `--` 开头为注释 | 可写题号、期待输出摘要 |
| 不要依赖题干里的「期待输出」表格本身 | 那是人工对照用；文件里只放**可执行 SQL** |
| 多测试点 → 多文件 | 如 `01_...sql`、`02_...sql`，一个点一个文件更清晰 |
| 需要崩溃 | 单独一行写 `crash;`（见 C 节） |

可选：把期待输出另存文本，方便 diff：

```bash
# 例如手工整理题干表格为纯文本
# SQL测试/from_problem/q2/01_create_table.expected.txt
```

### B. 普通功能样例（无崩溃）——推荐路径

**1）确认已编译**（没改过代码可跳过）：

```bash
cd /root/db2026/build
cmake --build . -j$(nproc) --target rmdb
```

**2）起一个干净库：**

```bash
cd /root/db2026
pkill -9 -x rmdb 2>/dev/null || true
rm -rf /tmp/q2_01_db
./build/bin/rmdb /tmp/q2_01_db > /tmp/rmdb_q2.log 2>&1 &
sleep 1
```

**含义：** 每个样例（或每组相关样例）用独立库目录，避免表名冲突、脏数据。

**3）跑题干 SQL：**

```bash
cd /root/db2026
python3 SQL测试/sql_test/run_sql.py SQL测试/from_problem/q2/01_create_table.sql
```

**含义：**

- `run_sql.py`：仓库自带驱动，**一条 TCP 连接**跑完整个文件（事务状态不丢）。
- 终端会打印 `>>> 语句` 和服务器返回；把返回与题干「期待输出」逐项对照。

常用可选参数：

```bash
python3 SQL测试/sql_test/run_sql.py 你的.sql --host 127.0.0.1 --port 8765 --timeout 10
```

| 参数 | 含义 |
|------|------|
| `--host` / `--port` | 服务地址（默认本机 8765） |
| `--timeout` | 单次收发超时秒数 |
| `--delay` | 语句之间间隔（默认 0.05s） |

**4）测完停服务（可选）：**

```bash
pkill -9 -x rmdb 2>/dev/null || true
```

**5）一轮多个测试点：**

```bash
for f in SQL测试/from_problem/q2/*.sql; do
  echo "======== $f ========"
  pkill -9 -x rmdb 2>/dev/null || true
  rm -rf /tmp/q2_run_db
  ./build/bin/rmdb /tmp/q2_run_db > /tmp/rmdb_q2.log 2>&1 &
  sleep 1
  python3 SQL测试/sql_test/run_sql.py "$f" || exit 1
done
pkill -9 -x rmdb 2>/dev/null || true
```

**含义：** 每个 `.sql` 用干净库跑一遍；任一失败 `exit 1` 便于脚本化回归。

### C. 带崩溃 / 恢复的题干样例

题干若分「崩溃前操作」和「重启后应看到什么」，拆成两个文件。

**文件 1：** `SQL测试/from_problem/recovery/01_before.sql`

```sql
-- 崩溃前：写入并提交（按题干填写）
create table t(id int);
begin;
insert into t values (1);
commit;
crash;
```

**文件 2：** `SQL测试/from_problem/recovery/02_after.sql`

```sql
-- 重启后：按题干期待查询
select * from t;
```

**执行顺序：**

```bash
cd /root/db2026
pkill -9 -x rmdb 2>/dev/null || true
rm -rf /tmp/prob_rec_db

# 崩溃前
./build/bin/rmdb /tmp/prob_rec_db > /tmp/rmdb_rec.log 2>&1 &
sleep 1
python3 SQL测试/sql_test/run_sql.py SQL测试/from_problem/recovery/01_before.sql
# 末尾 crash 会杀掉服务

# 必须用同一库目录重启
./build/bin/rmdb /tmp/prob_rec_db > /tmp/rmdb_rec.log 2>&1 &
sleep 2
python3 SQL测试/sql_test/run_sql.py SQL测试/from_problem/recovery/02_after.sql
```

**含义：** `crash` 模拟 SIGKILL；重启同一目录触发恢复；`02_after.sql` 的结果应等于题干「恢复后期待」。

仓库里同类真实例子（可直接抄结构）：

- `SQL测试/sql_test/01_without_checkpoint_before_crash.sql`
- `SQL测试/sql_test/02_without_checkpoint_verify.sql`

### D. 需要固定隔离级别时

在样例文件**最前面**加上题干要求的设置（在第一个 `begin` 前）：

```sql
set transaction isolation level snapshot isolation;
-- 后面跟题干 SQL
begin;
...
```

或：

```sql
set transaction isolation level serializable;
```

**含义：** 决赛 SI/SER 相关样例必须先设会话隔离级别，再开事务。

### E. 对照「期待输出」

`run_sql.py` **不会自动判分**，需要你人工或半自动对比：

1. 看终端里每个 `>>>` 后的返回是否与题干表格一致（列名、行、顺序、浮点格式等）。  
2. 若要保存本次输出：

```bash
python3 SQL测试/sql_test/run_sql.py SQL测试/from_problem/q2/01_create_table.sql \
  | tee /tmp/q2_01_got.txt
```

**含义：** `tee` 一边显示一边写入文件，便于和 `.expected.txt` 并排看。

3. 粗略 diff（格式往往不完全一致，只能辅助）：

```bash
diff -u SQL测试/from_problem/q2/01_create_table.expected.txt /tmp/q2_01_got.txt || true
```

### F. 和「仓库自带 5.2 脚本」的区别

| 类型 | 文件从哪来 | 库目录 |
|------|------------|--------|
| 题干纳入测试 | 你从 PDF/题面抄成 `SQL测试/from_problem/...` | 建议 `/tmp/题目_用例_db`，自定 |
| 5.2 恢复回归 | 仓库已有 `01_without_checkpoint_*.sql` 等 | 如 `recovery_no_checkpoint_db` |

两者都用同一个驱动：`python3 SQL测试/sql_test/run_sql.py <文件.sql>`。

### G. 检查清单（每个题干样例）

- [ ] SQL 已保存为 `.sql`，语句有 `;`  
- [ ] 注释里写了题号 / 测试点 / 期待摘要  
- [ ] `rmdb` 已启动且端口 8765 可连  
- [ ] 用**干净库**跑（或明确要续跑旧库）  
- [ ] `run_sql.py` 跑通无 ERROR  
- [ ] 终端输出与题干期待一致

## 11. 一键测试脚本（离线）

仓库提供两套脚本，**不访问网络**，适合无外网环境终端一键测。

| 脚本 | 用途 |
|------|------|
| `scripts/run_offline_tests.sh` | 通用回归：编译、unit、恢复、性能烟雾、q9 等 |
| `scripts/run_final_func_tests.sh` | 决赛线下功能题：跑你在 `SQL测试/from_problem/` 里自建的 `.sql` / `.expected` |

日志默认写到 `test_logs/`（已加入 `.gitignore`）。

### 11.1 通用回归：`run_offline_tests.sh`

```bash
cd /root/db2026
chmod +x scripts/run_offline_tests.sh   # 首次
./scripts/run_offline_tests.sh          # 默认 quick = 初赛功能向
```

**含义：** 按需编译后跑**初赛功能**相关仓库测集；结束打印 PASS/FAIL 汇总。

常用模式：

```bash
./scripts/run_offline_tests.sh quick           # 默认：unit + from_problem + q7 + q9 + 第10题基础恢复
./scripts/run_offline_tests.sh all             # quick + 加重恢复/OJ + 初赛性能烟雾
./scripts/run_offline_tests.sh unit            # 第1题 unit_test
./scripts/run_offline_tests.sh q7              # 第七题 Join
./scripts/run_offline_tests.sh q9              # 第九题隔离级
./scripts/run_offline_tests.sh q10             # 第十题基础 checkpoint（00–06）
./scripts/run_offline_tests.sh recovery        # 加重：full_recovery + oj_recovery
./scripts/run_offline_tests.sh perf            # 初赛性能测试烟雾（非功能题）
./scripts/run_offline_tests.sh build           # 只编译
```

常用选项：

```bash
./scripts/run_offline_tests.sh --skip-build quick   # 已有 build/bin，跳过编译
./scripts/run_offline_tests.sh --rebuild all        # 删 build 后全量重编再测
./scripts/run_offline_tests.sh --jobs 8 quick       # 指定并行编译线程
./scripts/run_offline_tests.sh -h                   # 帮助
```

**含义：**

| 参数 / 模式 | 含义 |
|-------------|------|
| `quick` | **初赛功能向**日常回归（不含 perf / full_recovery 加重项） |
| `all` | quick + OJ/加重恢复 + 性能烟雾 |
| `perf` | 仅初赛性能测试烟雾 |
| `recovery` | 仅加重恢复套件 |
| `--skip-build` | 不调 cmake，直接用现有 `build/bin/rmdb` |
| `--rebuild` | `rm -rf build` 后 Release 重编，改 parser 后建议用 |

`quick` 具体步骤：

1. `unit_test`（第1题）  
2. `SQL测试/from_problem`（题干用例，含第2题样例等）  
3. `7_sql_test`（第7题 Join）  
4. `9_sql_test`（第9题 SI/SER）  
5. 第10题基础恢复：`00` checkpoint smoke + `01–06` 有/无 checkpoint  

失败时终端会打出对应步骤日志尾部；完整日志在 `test_logs/offline_*`。

### 11.2 决赛线下功能题：`run_final_func_tests.sh`

面向「从题干抄测试示例 + 期待输出」的本地判分。封装的是 `scripts/run_final_func_tests.py`。

#### 目录约定

```text
SQL测试/from_problem/
  README.md
  q02_ddl/                              # 一题一个目录，建议 qNN_主题
    01_create_table.sql                 # 普通功能点：每次干净库执行
    01_create_table.expected            # 可选；有则自动对比（推荐）
    02_insert_select.sql
    02_insert_select.expected
  q10_recovery/
    01_no_ckpt.before.sql               # 末尾写 crash;
    01_no_ckpt.after.sql                # 同库重启后再跑
    01_no_ckpt.after.expected           # 只对比重启后输出
```

**含义：**

- 普通点：一个 `.sql` 对应一个测试点；同名 `.expected` 用于自动对比。
- 恢复点：`*.before.sql` + `*.after.sql` 成对；脚本会起库 → 跑 before（含 crash）→ **同一库目录**重启 → 跑 after → 与 `.after.expected` 对比。
- 对比会忽略边框线、`Total record(s)` 等装饰，可直接抄题干里的简写表格。

仓库已带示例：`q02_ddl`（第二题前两个测试点）、`q10_recovery`（无 checkpoint 崩溃恢复）。更细说明见 `SQL测试/from_problem/README.md`。

#### 新建一题测例

```bash
cd /root/db2026
python3 scripts/run_final_func_tests.py --init q05_agg
```

**含义：** 创建 `SQL测试/from_problem/q05_agg/`，并放入模板 `01_sample.sql` / `01_sample.expected`。把题干 SQL、期待输出分别贴进去（或改名成 `01_xxx.sql`）。

`.sql` 书写要点：

| 规则 | 说明 |
|------|------|
| 语句以 `;` 结束 | 驱动按分号切分 |
| `--` 开头为注释 | 可写题号、测试点 |
| 需要崩溃 | 单独一行 `crash;` |
| 需要隔离级 | 文件开头 `set transaction isolation level ...;` |

#### 一键跑

```bash
cd /root/db2026
chmod +x scripts/run_final_func_tests.sh   # 首次

./scripts/run_final_func_tests.sh          # 跑 from_problem 下全部用例
./scripts/run_final_func_tests.sh q02      # 只跑目录名含 q02 的题
./scripts/run_final_func_tests.sh q10      # 只跑恢复相关示例
```

等价 Python 调用：

```bash
python3 scripts/run_final_func_tests.py
python3 scripts/run_final_func_tests.py q02
python3 scripts/run_final_func_tests.py --list
python3 scripts/run_final_func_tests.py --skip-build q02
```

**含义：**

| 命令 | 含义 |
|------|------|
| 无参数 | 发现并执行 `SQL测试/from_problem/**` 下全部用例 |
| `q02` | 过滤：目录名包含该关键字 |
| `--list` | 只列出用例，不执行 |
| `--skip-build` | 不编译，用现有 `rmdb` |

通过 / 失败会打印汇总；详细输出在 `test_logs/final_func_*`。

#### 用当前输出生成 `.expected`

确认结果正确后：

```bash
python3 scripts/run_final_func_tests.py --record q05
```

**含义：** 把归一化后的实际输出写入对应 `.expected`（或 `.after.expected`），之后再跑就变成自动判分。先肉眼确认对了再 `--record`，避免把错误结果固化进去。

#### 和通用回归怎么配合

```bash
# 改完代码：先通用冒烟
./scripts/run_offline_tests.sh --skip-build quick

# 再跑本周正在做的功能题测例
./scripts/run_final_func_tests.sh --skip-build q05
```

**含义：** `run_offline_tests` 保证底层/恢复/性能路径没坏；`run_final_func_tests` 对准当前题干测试点。两者互补，不是二选一。
