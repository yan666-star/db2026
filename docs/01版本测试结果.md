# 官方性能评测信息、外部工具分析与本地测试方案

## 结论

本地评测必须先通过通用正确性门槛，再比较吞吐量。不能在数据库实现中识别固定表名、字段、SQL 文本或评测事务后走专用路径。可接受的优化必须位于通用索引、优化器、执行器、事务、缓存、WAL 和恢复机制中，并对任意等价 SQL 保持原语义。

仓库现有烟雾、并发探针、一致性和恢复脚本仍然有用。本次新增两个互补入口：

- `SQL测试/performance_test/run_generic_acid_suite.py`：随机化表名的通用事务、隔离和恢复测试，防止实现只适配 TPC-C 固定 SQL。
- `SQL测试/performance_test/run_official_like_benchmark.py`：按官方公布的事务比例、并发度、预热/测量窗口和三轮中位数规则运行 TPC-C 形状的本地性能负载。

这两个脚本是本地工程测试，不是官方私有评测器的复刻，结果不能直接等同于官方成绩。

## 群消息关键点

### 合规边界

1. 禁止针对固定表名、字段结构或 SQL 文本做专用匹配。
2. 禁止绕过通用解析、分析、优化和执行流程来提升评测跑分。
3. 优化只能落实在通用机制中，包括索引、执行器、事务、缓存和 WAL。
4. 优化不能改变 SQL 原有语义，也不能产生 SQL 未声明的副作用。
5. 已存在此类评测硬编码必须立即移除；初赛截止后核实可能取消资格。

因此，测试端可以使用 TPC-C 表和官方事务形状模拟负载，但数据库服务端不能识别并特殊处理这些名字或 SQL。还应使用随机表名、不同常量、不同语句顺序和不同隔离级别做反向验证。

### 索引信息

性能查询会带 `ol_w_id`。官方不会额外建立 `(ol_o_id, ol_d_id)` 二级索引，只建立以下 `order_line` 复合索引：

```sql
CREATE INDEX order_line(ol_w_id, ol_d_id, ol_o_id, ol_number);
```

本地建索引脚本已经采用这一列顺序。优化器应通过通用的连续前缀、上下界和剩余谓词逻辑使用该索引，不能为 `order_line` 写专用规则。

### 正确性门槛

检查重点为 ACID 和并发正确性：

- 成功提交的数据必须持久化。
- 未提交数据不能被其他事务读到。
- abort 后插入、删除、更新以及索引项必须全部回滚。
- 同一行的并发写必须按隔离级别串行化或让冲突事务 abort。
- 需要关注幻读；在 SI/SSI/串行化模式下，同一事务内的快照范围读应保持一致。
- 表记录、索引、MVCC 版本链、WAL 和恢复后的状态必须一致。

隔离级别未被严格限定为 RC、RR、SI 或 SSI 中的某一个。官方回复给出的底线是通常不低于 Read Committed。不能把 `set output_file off` 偷偷绑定为隔离级别开关；隔离级别应显式设置。

### 性能负载与计分

事务比例总计 23 份：

| 事务 | 比例 |
| --- | ---: |
| NewOrder | 10/23 |
| Payment | 10/23 |
| OrderStatus | 1/23 |
| Delivery | 1/23 |
| StockLevel | 1/23 |

每一轮先预热 30 秒，预热吞吐不计分；随后正式测量 360 秒。共运行 3 轮，以三轮成功提交 NewOrder 的 tpmC 中位数作为最终指标，不取最高值，也不取平均值。

请求量充足且并发较高，公开信息约为 16–32 个客户端；已有澄清明确提到 16 个并发线程。本地应至少分别测试 16 和 32 客户端。测试 scale 小于 50、warehouse 数较低，热点 district、warehouse 和 stock 行的锁/MVCC 冲突会显著影响吞吐。

事务 `abort`/`commit` 没有隐藏的特殊埋点，公开回复只说明性能环境数据量更大。因此本地小数据通过不代表大数据和长时间并发一定通过。

### 评分闸门

以下项目全部通过后才进入性能排名：

1. 功能测试。
2. 数据加载结果检查。
3. 压测后的 TPC-C 数据一致性检查。
4. `kill -9` 后的崩溃恢复检查。

任一项失败，性能成绩为 0；全部通过后性能测试得分为 100，再按 tpmC 排名。

## 两个外部目录的用途

### `concurrency_test`

该目录是一个旧版 C++ SQL 并发回归驱动器：

- 测试文件用 `preload`、多个 `txn` 和 `permutation` 描述预置 SQL、事务操作和全局交错顺序。
- 每个事务保持一个独立 TCP/Unix socket。
- 驱动器按 `permutation` 指定顺序逐条发送 SQL，并把服务端响应写入结果文件。

可借鉴之处是“多连接 + 确定性交错”的模型，适合构造脏读、写写冲突、回滚和幻读用例。

不能直接作为当前完整测试器的原因：

- 示例只有并发读，没有结果断言、性能统计、一致性审计或恢复检查。
- `crash` 操作使用 `txn_id=-1`，主循环却仍按该值访问事务数组，实际执行会越界。
- SQL 解析依赖简单的空格和子串匹配，输入校验不足；重复操作名会覆盖映射。
- 网络接收缓冲固定为 8192 字节，只执行一次 `recv`，不能可靠处理长响应和分包。
- 代码有裸指针泄漏、过时 API、固定默认端口等工程问题。
- 顶层目录和内层目录是重复副本，`__MACOSX` 只是压缩包元数据。

本次没有复制这套 C++ 代码，而是复用了仓库中能正确读取 NUL 结尾协议的 Python 客户端，并保留“独立连接、受控交错”的测试思想。

### `generate_data`

该目录是旧版 TPC-C CSV 数据生成器，覆盖 9 张表：warehouse、district、customer、history、new_orders、orders、order_line、item 和 stock。默认配置为 50 个 warehouse，每个 warehouse 10 个 district、每个 district 3000 个 customer/order、100000 个 item/stock，数据量很大。

可借鉴之处：

- 表结构、字段长度和 TPC-C 初始数据之间的关系。
- `d_next_o_id=ORDER_PER_DISTRICT+1`、未处理订单从 2101 开始等初始约束。
- 生成较大 CSV 后可用于测试 load、索引构建和长时间压测。

不直接接入本地自动测试的原因：

- 输出路径硬编码为旧工程的 `../src/test/performance_test/table_data/`。
- scale 编译期写死为 50，缺少命令行参数；一次生成的数据可能远超虚拟机资源。
- 源码存在编码损坏迹象、全局状态和重复实现，未提供构建文件或数据校验。
- 生成器只负责数据，不负责事务驱动、tpmC、并发正确性、一致性或恢复。
- 顶层与内层同样是重复副本。

因此本地 quick 测试继续使用仓库内的小型 CSV；需要更真实 scale 时，可以先修复该生成器，使 warehouse、item、customer、输出目录和随机种子可配置，并在生成后增加行数和业务约束校验。不要直接以默认 50 warehouse 在资源有限的虚拟机中运行。

## 本地测试矩阵

Ubuntu 上可以先用统一入口执行构建、单元测试、三种隔离配置的通用测试、性能烟雾测试和混合负载：

```bash
bash 'SQL测试/performance_test/run_local_evaluation.sh' quick
CLIENTS=32 SKIP_BUILD=1 bash 'SQL测试/performance_test/run_local_evaluation.sh' full
```

下列分层命令适合需要单独定位失败时使用。

### 第一层：快速通用正确性

随机表名确保数据库实现无法依赖 TPC-C 名称：

```bash
python3 'SQL测试/performance_test/run_generic_acid_suite.py' \
  --start-server --crash-check --isolation snapshot
```

建议再测试默认 RC 和 serializable：

```bash
python3 'SQL测试/performance_test/run_generic_acid_suite.py' --start-server --isolation default
python3 'SQL测试/performance_test/run_generic_acid_suite.py' --start-server --isolation serializable
```

覆盖场景：

- 同一事务内 update/delete/insert 后整体 rollback。
- 写事务未提交时的并发读，允许读旧版本或阻塞，但禁止读到未提交新值。
- 两个事务向唯一索引写入相同键，必须只有一个成功。
- SI/serializable 事务前后两次范围 count 不得出现新插入的幻影。
- commit 后立即 `kill -9`，重启后行数和值必须保持。

### 第二层：现有专项测试

```bash
python3 'SQL测试/performance_test/run_performance_smoke.py' --start-server
python3 'SQL测试/performance_test/run_performance_mixed_probe.py' --start-server
python3 'SQL测试/performance_test/audit_tpcc_consistency.py' --concurrency 16 --txn-count 200
```

还应运行 `SQL测试/10_sql_test` 下与 checkpoint、完整恢复和 statement TPC-C 相关的脚本，以及 `build/bin/unit_test`。

### 第三层：短时性能回归

先用 quick 模式发现死锁、abort 风暴和脚本问题：

```bash
python3 'SQL测试/performance_test/run_official_like_benchmark.py' \
  --start-server --quick --clients 16 --crash-check
```

再分别以 16、32 客户端运行可控时间窗口：

### 第四层：正式形状的本地长测

默认参数即公开的 30 秒预热、360 秒测量、3 轮和 16 客户端：

```bash
python3 'SQL测试/performance_test/run_official_like_benchmark.py' \
  --start-server --crash-check
```

结果写入 `build/official_like_benchmark.json`。重点观察每轮 tpmC、commit rate、各事务 abort 数、连接错误、平均/最大延迟以及三轮中位数。不要只看最高一轮。

仓库自带的微型 CSV 在初始状态下，三个 district 的
`sum(orders.o_ol_cnt) - count(order_line)` 并不为零。测试器会记录这一初始差值，
并要求压测后及崩溃恢复后差值保持不变；不能直接对这批微型数据启用“差值必须为零”
的严格检查，否则会在负载开始前产生稳定误报。

## 如何判断优化是否安全

每次修改优化器、索引、buffer pool、MVCC、锁或 WAL 后至少满足：

1. 随机表名通用 ACID 测试通过。
2. 默认隔离和目标隔离级别均通过相应语义检查。
3. TPC-C quick 压测前后的一致性检查通过。
4. `kill -9` 重启后的已提交标记和一致性检查通过。
5. 16/32 客户端下没有持续死锁、连接错误或异常 abort 风暴。
6. 使用不同随机种子、表名、常量和数据规模时收益仍存在。
7. 服务端代码中没有 TPC-C 表名、字段名、事务名或完整 SQL 文本判断。

只有在这些前提下，tpmC 提升才可视为通用且可信的性能改进。

### 结果分析

1. 单客户端所有事务均成功，说明事务本身、基本 SQL 路径、索引维护和自写处理不存在必然失败。
2. 总 TPS 在 4 客户端达到峰值 183.83，仅比单客户端提高约 8%；8 客户端以后成功吞吐反而下降，表现为明显的并发负扩展。
3. 并发增加后尝试量继续上升，但大量写事务很快 abort，系统资源主要消耗在失败事务和回滚上，形成 abort storm。
4. OrderStatus 和 StockLevel 始终 100% 成功，问题集中在 NewOrder、Payment 和 Delivery 的热点写路径。
5. NewOrder 受影响最严重，提交率从单客户端 100% 降到 32 客户端的 0.49%；Payment 从 100% 降到 1.62%。
6. 当前微型数据只有 1 个 warehouse、3 个 district 和 10 个 item。每个 NewOrder 更新 5–10 个 stock，事务之间很容易重叠；所有 Payment 又会写同一个 warehouse 行，因此该数据会显著放大写冲突。
7. 这些结果不能直接代表官方更大 scale 下的 tpmC，但足以说明当前锁等待、MVCC 写冲突或冲突后立即 abort 策略缺少扩展性。
8. 在所有并发配置下数据一致性和恢复均正确，因此当前首先是性能问题，而不是已发现的 ACID 正确性问题。

### 后续诊断建议

先把 NewOrder 改为每单只包含一条 order-line，在相同并发下复测：

```bash
for clients in 8 16 32; do
  python3 'SQL测试/performance_test/run_official_like_benchmark.py' \
    --start-server \
    --clients "$clients" \
    --warmup-seconds 5 \
    --measure-seconds 30 \
    --rounds 1 \
    --min-order-lines 1 \
    --max-order-lines 1 \
    --json-output "build/benchmark_one_line_${clients}.json"
done
```

- 如果 NewOrder 提交率显著上升，主要瓶颈是多 stock 热点更新及其冲突处理。
- 如果仍接近当前水平，应优先检查 district 序号热点、pending writer 等待、锁冲突立即 abort 和唯一索引冲突路径。
- 随后应使用更接近正式评测 scale 的数据复测，避免针对 10 个 item 的极端微型负载过度优化。
- 所有优化仍必须落在通用锁、MVCC、索引、buffer pool、WAL 和执行路径中，不能识别 TPC-C 表名或 SQL 文本。

2. 并发越高，缩短 NewOrder 的收益越明显：32 客户端 tpmC 提升超过 11 倍。
3. Delivery 提交率也明显改善，说明更短的 NewOrder 减少了 orders、new_orders、order_line 和 district 相关路径上的锁持有或版本冲突时间。
4. Payment 改善有限，在 8 客户端甚至基本不变，符合其主要瓶颈是所有事务更新同一 warehouse 行以及少量 district/customer 热点，而不是 order-line/stock。
5. 即使只有一条明细，tpmC 和 TPS 仍随 8→16→32 客户端下降，NewOrder 提交率仍从 26.90% 降到 5.52%，因此系统的通用写冲突处理仍存在负扩展，不能只归因于测试数据中的多 stock 重叠。
6. 下一步应在更大 item、district 和 warehouse scale 上复测，并分别诊断 warehouse、district、stock 三类热点；优化方向应是通用的等待/冲突策略、缩短临界区、减少 abort 前无效工作及降低回滚成本。

## 2026-07-11 Task 1/Task 2 新基线

测试器校准后，16 客户端 `official-shape` quick 基线为 605.25 tpmC；旧 SQL
形状被明确保留为 `mini-contention`，同条件为 485.88 tpmC。两种模式均通过
压测后一致性和 `kill -9` 恢复。

实施严格限定的 volatile-only MVCC abort 免强制刷盘后，`official-shape`
tpmC 达到 784.98，相对提升 29.7%；TPS 从 139.61 提升到 173.44，平均延迟
从 14.93 ms 降至 12.73 ms。

ABORT 强制刷盘从约 7500 次降至 686 次，另有 8007 次安全跳过；强制同步
累计耗时从约 4.29 秒降至 0.52 秒。682 次物理回滚仍对应 682 次 checkpoint
flush，证明 INSERT/物理回滚耐久路径未被绕过。新增纯 UPDATE/DELETE abort、
后续日志带出和立即崩溃恢复用例均通过。

### Task 3 等待预算结论

`RMDB_PENDING_WAIT_US=0/50/200/500/2000` 三轮 A/B 中，2000 us 的 NewOrder
tpmC 中位数最高，为 829.54。已解决等待约 68.1% 来自 writer abort，说明有限
等待能够让部分事务继续，而不是全部等待后仍因 writer commit 必然失败。

因此保留默认 2000 us。最终通用 ACID、volatile abort 恢复、已提交持久性、
压测后一致性和 `kill -9` 均通过；独立 quick 恢复回归 tpmC 为 821.50。

### Task 4a BufferPool 锁拆分

BufferPool 全局 latch 被诊断为第一锁热点后，命中路径改为页表共享锁并增加
per-frame 状态锁；淘汰、装页、删除和全量 flush 继续使用页表独占锁。

同配置 tpmC 从 829.36 提升到 866.88（+4.5%），TPS 从 167.24 提升到
176.74（+5.7%）；页表平均等待从 10.10 us 降到 8.00 us，frame 平均等待
仅 0.052 us。完整 quick、一致性和崩溃恢复全部通过。

后续公平 commit-apply 读写 gate 虽将该锁的 read wait 降低 81.3%，但 tpmC
下降 0.9%、TPS 下降 1.2%，同时 MVCC latch 等待增加 77.4%。该实验未保留，
最终版本仍使用原 commit-apply 互斥语义。
