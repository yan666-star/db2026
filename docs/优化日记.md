
## 优化记录摘要

历史优化过程已压缩，只保留对后续性能工作仍有价值的结论：

- MVCC 热路径：唯一键冲突检查只关注发生过 MVCC 写入的候选 key；非索引列 UPDATE 不做无意义的唯一键检查和索引维护。
- 读路径：优化缓冲池命中、唯一键点查、索引范围扫描与叶页读取，目标是缩短事务执行时间和冲突窗口。
- abort 成本：保留 `RMDB_PERF_DIAG` 诊断；纯内存 MVCC abort 可避免不必要的 checkpoint flush；pending writer 采用有限等待，最终仍按 SI 冲突规则决定提交或 abort。
- 保持边界：不放松 MVCC 可见性、写冲突、WAL、COMMIT/ABORT 顺序、redo/undo、checkpoint 或表/索引/版本链同步维护。

## 回归验证

每次优化至少验证官方性能脚本的功能、Load Data、压测后 TPC-C 一致性和 `kill -9` 恢复阶段；本地重点覆盖并发 NewOrder 守恒、失败 NewOrder 无残留、扫描与索引一致、未提交写不可见，以及 abort 不覆盖已提交更新。

## 2026-07-11 Task 2：volatile-only MVCC abort 免强制刷盘

严格限定的 `volatile_only_mvcc_abort` 同时满足：

1. 事务使用 MVCC；
2. 没有执行物理 rollback；
3. 没有进入 `commit_mvcc` 物理应用阶段。

这类事务仍把 ABORT record 追加到有序日志缓冲区，但不再单独调用
`flush_log_to_disk(true)`。非 MVCC abort、INSERT 等物理回滚和进入 commit
应用后的 abort 保留原来的 checkpoint flush 与强制日志刷盘路径。

新增恢复覆盖：纯 UPDATE/DELETE rollback、ABORT 被后续提交日志带出后崩溃、
ABORT 后立即 `kill -9`。原有 INSERT rollback 和已提交事务持久性检查继续保留。

与 Task 1 相同的 16 客户端 official-shape quick 对比：

| 指标 | Task 1 | Task 2 | 变化 |
| --- | ---: | ---: | ---: |
| NewOrder tpmC | 605.25 | 784.98 | +29.7% |
| TPS | 139.61 | 173.44 | +24.2% |
| 总提交率 | 13.06% | 13.83% | +0.77 pp |
| 平均延迟 | 14.93 ms | 12.73 ms | -14.8% |
| ABORT 强制刷盘次数 | 7500 | 686 | -90.9% |
| ABORT 强制刷盘耗时 | 4.29 s | 0.52 s | -87.9% |
| 跳过 ABORT 强制刷盘 | 0 | 8007 | 新增 |

Task 2 中 `abort_checkpoint_flush=682`、`abort_physical_rollback=682`，说明需要
物理回滚的事务仍走耐久路径，没有把所有 abort 无条件改成免刷盘。所有通用
ACID、性能 smoke、压测后一致性和崩溃恢复命令均成功结束。

## 2026-07-11 Task 3：pending writer 等待预算

新增诊断把 resolved wait 拆分为 writer committed、writer aborted 和 writer
state gone；benchmark 可通过 `--pending-wait-us` 对同一负载做可复现 A/B。

16 客户端、official-shape、三轮 2 秒预热/8 秒测量结果：

| 等待预算 | tpmC 中位数 | TPS 中位数 | 提交率 | 平均延迟 |
| ---: | ---: | ---: | ---: | ---: |
| 0 us | 680.28 | 191.95 | 12.73% | 10.69 ms |
| 50 us | 686.95 | 183.55 | 12.78% | 11.11 ms |
| 200 us | 724.68 | 186.02 | 13.12% | 11.25 ms |
| 500 us | 687.08 | 174.10 | 13.32% | 11.75 ms |
| 2000 us | **829.54** | 172.33 | **13.98%** | 13.10 ms |

2000 us 下共观测 26,706 次等待：4,967 次等到 writer abort，2,326 次等到
writer commit，1 次 writer state gone，19,411 次 timeout。在已解决等待中，
约 68.1% 等到 writer abort，因此等待确实能挽救部分 SI 事务；0 us 虽然总 TPS
较高，但成功 NewOrder tpmC 明显更低。

保留现有默认 2000 us，不增加线程 sleep、全局串行或隐藏重试。最终通用 ACID、
volatile abort 两种崩溃时机、已提交持久性、压测后一致性及 benchmark `kill -9`
全部通过；最终 quick tpmC 为 821.50。

## 2026-07-11 Task 4a：BufferPool 页表与 frame 锁拆分

诊断基线中 BufferPool 全局 latch 累计等待 22.08 秒，平均 10.10 us，明显高于
commit-apply read 的 7.72 秒和 MVCC latch 的 1.80 秒；命中率约为 100%，因此
优化目标是命中/取消固定并发，而不是磁盘 miss。

实施通用页表共享锁和 per-frame 状态锁：

- fetch hit、unpin 和单页 flush 持有页表共享锁。
- miss、装页、淘汰、删除和全量 flush 持有页表独占锁。
- 每个 frame 独立保护 `pin_count/is_dirty`。
- `pin_count 0→1` 与 LRU 移除、`1→0` 与 LRU 加入仍在同一个 frame 临界区。
- commit-apply 和 MVCC 锁在本阶段未修改。

16 客户端 official-shape quick 对比：

| 指标 | 修改前 | 修改后 | 变化 |
| --- | ---: | ---: | ---: |
| NewOrder tpmC | 829.36 | 866.88 | +4.5% |
| TPS | 167.24 | 176.74 | +5.7% |
| Buffer 页表总等待 | 22.08 s | 19.56 s | -11.4% |
| Buffer 页表平均等待 | 10.10 us | 8.00 us | -20.8% |
| per-frame 平均等待 | 未分离 | 0.052 us | 新增 |

完整 local quick、并发一致性、非法 item rollback、压测后一致性、order-line
基线差值和 `kill -9` 恢复全部通过。剩余页表等待与物理 abort 的 checkpoint
独占全量刷盘高度相关；该问题需要 CLR/恢复协议证明，暂不在低风险阶段处理。

### 未保留：commit-apply 公平读写 gate

曾将普通记录读取改为共享 read guard，并让物理 commit/GC/checkpoint 使用带
writer intent 的公平独占 guard。该实验把 commit-apply read 等待从 7.87 秒
降至 1.47 秒，但串行压力转移到 MVCC latch：MVCC 等待从 1.76 秒升至 3.12 秒。

| 指标 | BufferPool 版本 | 公平读写 gate | 变化 |
| --- | ---: | ---: | ---: |
| NewOrder tpmC | 866.88 | 859.22 | -0.9% |
| TPS | 176.74 | 174.58 | -1.2% |
| 平均延迟 | 12.82 ms | 13.10 ms | +2.2% |
| commit-apply read 等待 | 7.87 s | 1.47 s | -81.3% |
| MVCC latch 等待 | 1.76 s | 3.12 s | +77.4% |

该改动没有形成端到端收益，却增加了并发协议复杂度，因此已完整回退，只保留
诊断计数和已验证有收益的 BufferPool 锁拆分。后续不得仅凭某一把锁等待下降
就重复引入该方案；必须证明成功 tpmC/TPS 的整体提升。

## 2026-07-11 参考文档复核与 Task 5a：索引点查去临时堆分配

复核《决赛优化专题》和《设计与实现文档》后，当前版本已经具备哈希化 LRU、
批量记录读取、批量索引扫描等机制；下列方案暂不直接引入：

- `fast_count/fast_min`：必须同时证明当前事务的 MVCC 可见性，不能只依赖物理行数或索引首项；
- 改用较弱隔离级别或简化冲突检查：会改变现有 SI 语义；
- B+ 树 crab-latching、CLR/WAL 协议重构：可能有收益，但需要更大范围的并发与恢复证明；
- 针对固定表、字段或 SQL 的专用路径：明确禁止。

本阶段采用文档中的通用“减少构造/析构与内存分配”方向。原
`IxIndexHandle::get_value` 在每一层 B+ 树页面上都创建和销毁一个堆分配的
`IxNodeHandle`。修改后在共享根锁保护下使用栈上轻量句柄逐层读取，页面
fetch/unpin 顺序、键比较、锁范围和返回结果保持不变。该优化对任意 B+ 树唯一键点查生效，
不读取表名、字段名或 SQL 文本。

该候选必须与上面的 16-client 三轮基线进行 A/B；若 tpmC 中位数没有稳定收益，
则回退本阶段，不与后续优化合并。
