## 保留的有效优化

### 1. 纯内存 MVCC abort 免强制刷盘（+29.7% tpmC）

**思路：** 区分三类 abort——纯 MVCC 内存 abort（仅 pending 版本，未触及物理表）、物理回滚 abort（INSERT 等）、已进入 commit 应用阶段的 abort。第一类 ABORT 日志仍写入有序缓冲区，但不单独 fsync；若崩溃丢失，恢复会将事务当 loser 重做 undo，物理表本就是旧正确状态。

**效果：** ABORT 强制刷盘从 ~7500 次降至 ~686 次，8007 次安全跳过；强制刷盘耗时从 4.29s 降至 0.52s。物理回滚仍走完整 checkpoint flush 路径。16-client tpmC 从 605→785（+29.7%），TPS 从 140→173。

### 2. Pending writer 有限等待（预算 2000us）

**思路：** 遇到 pending writer 时不立即 abort，短时间等待 writer 结束。若 writer abort 则可继续提交；若 writer commit 则必然因 `latest_commit > start_ts` 而 abort。诊断按 writer committed/aborted/timeout 分类统计。

**效果：** 2000us 预算下 ~68% 已解决等待来自 writer abort，确实挽救了部分事务。0us（不等待）总 TPS 高但 NewOrder tpmC 低。默认保留 2000us。

### 3. BufferPool 页表共享锁 + per-frame 状态锁（+4.5% tpmC）

**思路：** 诊断显示 BufferPool 全局 latch 是第一锁热点（22s 累计等待）。命中/unpin 路径改为页表共享锁；每个 frame 独立保护 `pin_count/is_dirty`；淘汰/装页/删除/全量 flush 仍用独占锁。

**效果：** 页表平均等待从 10.10us→8.00us（-20.8%），frame 平均等待仅 0.052us。tpmC 829→867（+4.5%），TPS 167→177（+5.7%）。

### 4. 索引点查去临时堆分配（+4.57% tpmC）

**思路：** `IxIndexHandle::get_value` 原先在每层 B+ 树页面上创建/销毁堆分配 `IxNodeHandle`。改为栈上轻量句柄逐层读取，fetch/unpin 顺序、键比较、锁范围不变。对任意 B+ 树唯一键点查生效。

**效果：** 三轮中位数从 852→891（+4.57%），新版本最低一轮仍高于旧版本最高一轮。

### 5. Parser 全局锁范围缩短

**思路：** 生成的 lexer/parser 使用全局 `ast::parse_tree` 需串行执行。改为在锁内复制根 `shared_ptr` 并释放 lexer buffer，随后语义分析/优化/执行在锁外进行。不改变 AST 内容，仅移除无关客户端间的解析串行等待。

**效果：** 已合并到主线。正式测量诊断显示 parser 全局锁累计等待 20.78s，仍为最大单一热点。

## 2026-07-12 未保留：Task 7 commit-apply 独占锁范围缩短

**思路：** 诊断中 commit-apply read 累计等待 7.66s，根因是 `commit_mvcc()` 在独占锁下既做版本发布（纯内存、微秒级）又做物理应用（含磁盘 I/O、毫秒级）。一个 NewOrder 的全部索引维护都在此锁内，期间所有 reader 被阻塞。

将 commit_mvcc 拆为两阶段：
1. **Phase 1（版本发布）**：独占 `commit_apply_latch_` + `mvcc_latch_` 下执行冲突检查 → 分配 commit_ts → 标记 pending 版本为已提交 → 释放独占锁。`check_commit_conflict_under_latch()` 内已调用 `validate_pending_physical_before()` 做物理 before-image 预验证。
2. **Phase 2（物理应用）**：在全局锁外执行 `delete_indexes → delete_record → update_record → update_indexes`。不重复 `check_physical_before()`，因为 Phase 1 已验证且 SI 冲突检测阻止其他 writer 修改这些记录。

**正确性保证：**
- 读者通过版本链读取——commit_ts 发布后，`get_visible_record_under_latch()` 从版本链 `data` 返回新值，不依赖物理记录
- COMMIT 日志仍在物理应用完成后写入，崩溃恢复语义不变
- 物理应用使用 per-file `insert_latch_` 和 per-index `root_latch_` 做表/索引级串行

**效果（16 clients quick，同环境 A/B）：**

| 指标 | 基线 | Phase A | 变化 |
| --- | ---: | ---: | ---: |
| NewOrder tpmC | 133.95 | **161.26** | **+20.4%** |
| 测量阶段 aborts | 1934 | 1497 | -22.6% |
| 并发一致性 | PASS | PASS | ✅ |
| 压测后一致性 | PASS | PASS | ✅ |
| kill-9 恢复 | PASS | PASS | ✅ |

早期本地 quick 闸门虽通过，但后续更大规模一致性检查发现该方案存在原子性缺口，
因此上述性能数字不能作为保留依据，`b1c2277` 的两阶段实现已经回退。

根因是 Phase 1 在物理表和索引尚未全部更新时就发布 `commit_ts` 并释放
`commit_apply_latch_`。读者随后可能同时观察到“已提交的新版本”和“尚未更新的旧索引”，
导致按新键漏行、按旧键读取后又被谓词过滤，暴露事务部分应用状态。仅靠 SI 写冲突不能
保护读者，也不能保证物理索引在版本发布时已经完成；Phase 1 的一次 before-image 预验证
同样不能替代物理应用前的再次检查。

修复恢复以下不变量：

1. 版本发布、物理表/索引应用以及失败回滚全部位于同一个 commit-apply 独占区间；
2. 每个物理 UPDATE/DELETE 应用前重新执行 `check_physical_before()`；
3. `commit_mvcc()` 全部完成后，外层事务管理器才写出 COMMIT 日志并返回成功。

`3b13d7e` 引入的 MVCC IndexScan/SeqScan 页级批量读取与本问题无关，继续完整保留。

## 2026-07-12 3b 基线后的低风险批量路径优化候选

按收益潜力和正确性风险排序：

1. **批量 MVCC 可见性锁合并（已实施）**：页级 `batch_get_records` 原本对每行分别获取
   `mvcc_latch_`；现在整批持锁一次，但每个 RID 仍调用同一版本选择函数。老数据仍按
   `ts=0` 建立 baseline，own pending、snapshot timestamp 和 delete tombstone 规则不变。
2. **消除执行器内部重复记录复制（已实施）**：IndexScan/SeqScan 从 batch 容器切换
   当前行时移动 `unique_ptr`，`Next()` 对调用方仍返回独立副本，不改变对象所有权边界。
3. **Bitmap 字节级跳过（已实施）**：查找置位/空位时跳过全 0 或全 1 字节，尾部不足
   8 bit 仍逐位检查。新增随机长度、随机位图的 scalar-reference 单元测试。
4. **自适应 batch/chunk 大小（待前三项测量后决定）**：可能减少微型负载的过度预取，
   但会影响 OJ 已验证的页级批量收益，暂不合并。

明确不采用：提前释放 commit-apply、删除物理 before-image 复核、弱化 SI 写冲突、
跳过 WAL/COMMIT 刷盘，或识别固定 TPC-C 表名/SQL。前三项不修改 commit/abort、
索引发布、恢复和隔离级别路径。

### Candidate A 结果：批量 MVCC 单次持锁未保留

三项组合通过全部 ACID、一致性和 kill-9 恢复，但三轮 tpmC 为
706.45 / 662.84 / 581.74，中位数 662.84，低于 3b 本地基线 691.61，且随数据增长
持续恶化。整页一次持有 `mvcc_latch_` 虽减少获取次数，却扩大了热点临界区，阻塞其他
读写事务；该项已完整回退，事务管理器和 RmFileHandle 可见性路径重新与 3b 一致。

Candidate B 仅保留两项机械优化：执行器 batch 记录 move，以及 Bitmap 字节级跳过。
这两项不扩大共享锁范围，也不修改任何版本链、提交、索引或恢复逻辑。

### Candidate B 最终结果：OJ WA，已回退

本地完整 ACID、并发一致性、非法 item rollback、压测后一致性、order-line 基线差值和
kill-9 恢复均通过；三轮 NewOrder tpmC 为 776.64 / 734.66 / 732.55。但最新 OJ 在
Post-transaction consistency validation 阶段失败，因此本地 PASS 和性能收益不能作为
保留依据。相对已知 OJ 966 的 `3b13d7e`，Candidate B 只修改了 IndexScan move、
SeqScan move、Bitmap 快跳和单测；四处已全部回退。

当前整个 `src/` 忽略行尾后与 `3b13d7e` 无差异。后续不得重新引入 Candidate B，
除非先新增能够稳定复现该 OJ 一致性缺口的大规模并发回归用例。

后续不立即修改 batch 大小。3b 的整页批量读取已有 OJ 966 的正向证据，而固定 chunk
会让同一页被重复 fetch，可能牺牲官方大扫描收益；应先以 Candidate B 进行 OJ 对照，
再根据官方结果决定是否单独实验自适应 batch。
