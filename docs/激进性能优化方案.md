# 激进性能优化方案：从 30 → 100k NewOrder/min

> 当前成绩：30 NewOrder/min（末位），第一名 ~100k  
> 差距：~3,333×  
> 时间窗口：决赛截止前  
> 核心原则：**在通用机制内做激进调优，不硬编码表名/SQL，但允许牺牲传统数据库的"优雅"换吞吐**

---

## 零、根因定位：为什么是 30 而不是 30,000？

NewOrder p50 延迟 **27 秒**，Payment p50 **65 毫秒**。差距 400×，但 NewOrder 操作数只有 Payment 的 3~7 倍。

**真正的死因是"护航效应"**（convoy phenomenon）：

```
32 客户端并发 NewOrder
  → 每条 NewOrder 执行 15-35 次记录操作 + 索引维护（~500ms 无竞争）
  → commit 时获取 commit_apply_latch_ 全局互斥锁
  → 锁内执行：版本发布 + 物理记录写入 + 所有索引维护 + 可能触发 fsync
  → 只有 1 个事务能提交，31 个排队
  → 排队的事务持有着 mvcc_latch_ 下拿到的快照 → 等排到时 start_ts 已陈旧
  → check_write_conflict 发现 latest_commit > start_ts → ABORT
  → 几百毫秒的工作全部浪费，客户端重试
  → 重试的事务又排到队尾...
  → 每次只有 1 个事务成功，其余 31 个 abort + 重试
```

**证据链**：
1. p50 27s、p99 81s 不是"慢"，是排队等锁
2. 5 秒桶 CV 117-168%，12-14 个零桶/轮 → 系统周期性完全停滞
3. NewOrder 完成率 77%，但 22.81% abandon（超时/断开），非业务回滚
4. Payment 95.48% 完成 → 短事务逃过了护航

**结论**：瓶颈不是"操作不够快"，是"全局串行化 + 冲突导致有效并发度≈1"。用单线程跑都可能比现在高——至少不会把工作浪费在 abort 上。

## 一、攻击向量：必须击破的四层壁垒

```
                    ┌──────────────────────────────────┐
   壁垒 1 (50%+)    │  commit_apply_latch_ 全局序列化    │ ← 最大瓶颈
                    │  物理应用 + 版本发布 装在同一锁内    │
                    ├──────────────────────────────────┤
   壁垒 2 (30%)     │  SI 热行写写冲突 → 雪崩式 abort     │
                    │  district/stock 同一行上 32 客户端  │
                    ├──────────────────────────────────┤
   壁垒 3 (15%)     │  mvcc_latch_ 全局版本表锁           │
                    │  所有版本读写串行化                  │
                    ├──────────────────────────────────┤
   壁垒 4 (5%)      │  WAL fsync + 索引 root_latch_       │
                    │  每 commit 刷盘 + 每索引写独占       │
                    └──────────────────────────────────┘
```

## 二、P0 方案：击破壁垒 1+2（预期 100-500× 提升）

### 2.1 拆分 commit 临界区：版本发布与物理应用解耦 ★★★★★

**这是唯一最重要的改动。不做这个，其他优化都是徒劳。**

**原理**：
```
改动前（所有工作在全局锁内）：
  commit_mvcc() {
    lock(commit_apply_latch_);       // ← 全局互斥
      check_commit_conflict          // 微秒
      分配 commit_ts                  // 微秒
      标记版本已提交                  // 微秒
      for each write:
        更新物理记录                  // 毫秒，含 I/O
        维护所有索引                  // 毫秒，含 I/O
      unlock(commit_apply_latch_);
    写 COMMIT WAL + fsync             // 毫秒
  }

改动后（版本发布与物理应用解耦）：
  commit_mvcc() {
    // Phase 1: 快速发布 (全局锁, <100μs)
    lock(commit_apply_latch_ + mvcc_latch_);
      check_commit_conflict
      分配 commit_ts
      标记 pending 版本 → committed
      收集 PhysicalOp 列表
    unlock(mvcc_latch_ + commit_apply_latch_);

    // Phase 2: 物理应用 (per-table/per-index 锁, 并发)
    for each op:
      lock(per_table.insert_latch_);   // 与其他表并行
        check_physical_before()        // 重新验证（关键！）
        apply_physical(op)
      unlock(per_table.insert_latch_);

    // Phase 3: 持久化
    写 COMMIT log → force_flush
  }
```

**正确性论证——这是整个方案的核心**：
1. **读者可见性**：读者通过 MVCC 版本链 `get_visible_record_under_latch()` 读取，不依赖物理记录是否已应用。Phase 1 后版本链已更新 → 读者立即看到新值。
2. **崩溃安全**：若 Phase 2 中途崩溃 → COMMIT 日志不存在 → 恢复时 undo 该事务 → 版本链回滚 → 一致。
3. **并发写同一 RID**：Phase 1 在 `commit_apply_latch_` 下串行分配 commit_ts → 同一 RID 的提交严格有序。Phase 2 由 per-table 锁保护顺序。
4. **Phase 2 重新验证**：`check_physical_before()` 在每个 op 前重新检查——因为 Phase 1 与 Phase 2 之间的窗口内，其他事务的 Phase 2 可能已修改了物理行。验证失败 → 回滚已应用部分 → 标记事务 abort。

**落点**：`src/transaction/transaction_manager.cpp:1433-1567` (`commit_mvcc`)

**预期效果**：commit 不再全局串行。16 个并发 commit 同时执行物理应用 → 有效并发度从 1 提升到接近客户端数。**这是从 30 → 几千的第一步**。

### 2.2 消除 SI 热行冲突：事务内写合并 + 快照刷新 ★★★★

**原理**：NewOrder 对同一 stock 行可能多次 UPDATE（一条 order_line 更新一次）。当前实现每条 UPDATE 都做 `check_write_conflict` + `append_write_record`。

**改动**：
1. **事务内同 RID 写合并**：`UpdateExecutor` 检测到 RID 已在 `write_set_` 中 → 跳过 `check_write_conflict`（own_pending 路径已保证正确性），直接更新 `own_pending` 版本。`append_write_record` 对同 RID 只保留最早的 before_image + 最新的 after_image。
2. **写集去重后减少 commit 时索引维护**：5-15 条 stock UPDATE → 合并为 1 条（如果所有操作都在同一 stock 行）。

**落点**：`src/execution/executor_update.h:186,249`；`src/transaction/transaction.h` write_records

**预期效果**：NewOrder 写集大小从 15-35 降到 7-15，冲突检测和索引维护减半。

---

### 2.3 MVCC 版本表分片 ★★★★

**原理**：全局 `mvcc_latch_` 保护所有 `record_versions_`。32 客户端并发读写版本链 → 严重争用。

**改动**：
```cpp
struct MvccShard {
    std::mutex latch;
    std::unordered_map<RecordKey, std::vector<MvccVersion>, RecordKeyHash> histories;
};
std::array<MvccShard, 64> mvcc_shards_;  // hash(file_id, page_no) & 63
```

- 读取/prepare_write/abort 只锁目标 shard
- commit 按写集涉及的 shard ID 升序加锁（避免 ABBA 死锁）
- SSI 依赖图仍在单独的 `txn_state_latch_` 下
- GC 按 shard 独立执行

**落点**：`src/transaction/transaction_manager.h:344-346`，所有 `lock_guard(mvcc_latch_)` 调用点

**预期效果**：非冲突 RID 的版本操作完全并行，mvcc 等待降低 10-30×。

### 2.4 异步物理应用（激进模式）★★★★★

**这是"兵行险招"的核心。对 RID 分布均匀、冲突概率低的事务，允许 Phase 1 后立即返回 ACK，物理应用异步执行。**

**原理**：
```
commit_mvcc() {
    Phase 1: 版本发布 + commit_ts (快速，有锁)
    Phase 2: 写 COMMIT WAL + fsync (持久化)
    → 返回 ACK 给客户端 ← 不等待物理应用！
    
    Phase 3: 后台线程池执行物理应用
}
```

**风险与缓解**：
- 风险：物理应用失败（极少见，因为 Phase 1 已验证冲突）
- 缓解：物理应用失败 → 标记事务为 "physically_broken" → 后续读者从版本链读（仍正确）→ 后台修复线程重试
- 风险：崩溃后物理不完整
- 缓解：WAL 已写入 → 恢复时 redo 补齐物理

**预期效果**：ACK 延迟从 800ms+ 降到 <1ms。并发度从 ~1 提升到接近 32。这是跨越数量级差距的关键。

## 三、P1 方案：击破壁垒 3+4（预期 2-5× 额外提升）

### 3.1 B+ 树写路径页级 latch coupling ★★★

**原理**：当前 `insert_entry`/`delete_entry` 独占锁整棵树的 `root_latch_`。改成页级 latch coupling——沿搜索路径逐页加锁，子页加锁后释放父页。写操作不再阻塞同索引的并发读。

**风险**：高。分裂/合并时的 latch 升级顺序极易死锁。必须用 Blink-tree 或 careful coupling 协议。

**落点**：`src/index/ix_index_handle.cpp`

**预期效果**：同索引的并发读写不再互斥。多事务可同时插入不同索引页。

### 3.2 组提交延迟激进调优

**原理**：当前 `group_commit_delay` 默认 200μs，可设到 2-5ms。在 32 客户端下，2ms 能聚合 10-30 条 commit 日志到同一次 fsync。

**改动**：`RMDB_GROUP_COMMIT_US=2000` 或更大

**风险**：p50 延迟相应增加（但 27s → 1ms 有余量）

### 3.3 Buffer Pool 扩容 + 直接 I/O

**改动**：
- `BUFFER_POOL_SIZE` 从 32768 (128 MiB) → 131072 (512 MiB)
- 可选：打开 `O_DIRECT` 绕过 OS page cache 双重缓冲

### 3.4 预分配 RID 批量插入

**原理**：NewOrder 批量插入 order_line（5-15 行）。当前逐行获取 `insert_latch_` → 分配页/槽位 → 释放锁。改为批量预分配 RID + 一次持锁批量写入。

**落点**：`src/record/rm_file_handle.h` 新增 `batch_reserve_rids(count)`

## 四、P2 方案：锦上添花（预期 1.2-2× 额外提升）

### 4.1 计数器热行无锁化

对于 `SET col = col + delta` 模式：用 `__atomic_fetch_add` 直接修改内存中的值，跳过 MVCC 读写检测。物理落盘时只需写最终值。

**限制**：仅当 WHERE 条件是主键等值且无其他谓词时生效。通用机制，不硬编码列名。

### 4.2 O(1) COUNT(*)

文件头维护 `row_count`。INSERT/DELETE/恢复 时维护。`COUNT(*)` 短路返回。

### 4.3 MIN/MAX 索引端点

`SELECT MIN(col) FROM t WHERE ...` 如 col 上有索引 → `lower_bound` + 一次回表（O(log N)），不走全表扫描。

### 4.4 EXEC_BATCH 计划缓存

32 客户端反复执行相同的 8 条 prepared statement。缓存 `PlannerOutput`，按 statement_id + 参数类型签名查找。

## 五、实施顺序与依赖

```
Step 1: MVCC 版本表分片 (2.3)         ← 独立，风险低，为后续铺路
Step 2: 提交阶段拆分 (2.1)            ← 最大收益，依赖 step 1 的分片
Step 3: 事务内写合并 (2.2)            ← 独立
Step 4: 异步物理应用 (2.4)            ← 依赖 step 2
Step 5: 组提交延迟 (3.2)              ← 独立
Step 6: B+ 树页级 latch (3.1)         ← 高风险，需要专项并发回归
Step 7: 其他 P1/P2 项                 ← 收益递减
```

**每步完成后必须过四道闸门**：
1. 功能测试（25 题）
2. 隔离历史（SI/SER 全数通过）
3. 压测后一致性 + kill-9 恢复
4. 与基线 A/B 对比 NewOrder/min（本地 32c 短测即可）

## 六、哪些不能做（合规红线）

| 禁止 | 原因 |
|------|------|
| ❌ 识别 "warehouse"/"district"/"stock" 等表名走专用路径 | 违反通用性原则 |
| ❌ 跳过 SI 写写冲突检测 | 破坏隔离性 → 一致性检查失败 |
| ❌ COMMIT ACK 前不 fsync WAL | 持久化审计失败 |
| ❌ 用全局变量共享跨事务状态 | MVCC 隔离被破坏 |
| ❌ 去掉 B+ 树的 `find_child()` 断言 | 掩盖索引损坏 |
| ❌ 把 `insert_latch_` 换成无锁 | 页分配/槽位分配需要互斥 |

## 七、预期效果（保守估计）

| 阶段 | 核心改动 | 预期 NewOrder/min | 风险 |
|------|---------|------------------:|------|
| 当前 | — | 30 | — |
| Step 1-3 | MVCC分片 + commit拆分 + 写合并 | 2,000-5,000 | 低 |

**注意**：以上为基于架构分析的理论预期。实际效果必须逐阶段用本地 32 客户端短测验证。TPC-C 排名取三轮中位数，稳定性比峰值更重要。

## 八、最简可行路径（如果时间仅够改一处）

如果只能改**一个文件**的最少代码来最大化提升：

**`src/transaction/transaction_manager.cpp` 的 `commit_mvcc()`** ——将 Phase 1（版本发布 + commit_ts 分配）与 Phase 2（物理应用）拆分，使 commit_apply_latch_ 只保护 Phase 1。

这是 30 → 几千的最短路径。其余优化可以让"几千 → 几万"，但不做这个拆分就永远停在 30。
