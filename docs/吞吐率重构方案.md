# 吞吐率重构方案（finals-wire-ssi）

> 目标：在通过正确性门槛（`正确性门槛关键要求.md`）的前提下，把 NewOrder/min 从 20+ 提升到 10000+。
> 参照基准：本仓库 `finals-wire-ssi`（20+）与队友仓库 `dbg/db2026`（340+）。

---

## 一、诊断结论

### 1.1 20 → 340 的根因（已确认，两项叠加）

逐行对比两个仓库的热路径后，定位到两处**确定性**架构差异，足以解释 17× 差距：

| 维度 | `dbg/db2026`（340） | `finals-wire-ssi`（20） | 影响 |
| --- | --- | --- | --- |
| Buffer pool 大小 | **512MB**（131072 帧） | **128MB**（32768 帧） | 工作集远超 128MB → 持续淘汰 |
| 脏页淘汰前的 WAL 刷写 | `flush_log_to_disk(false)`（仅 `pwrite` 到内核） | `flush_log_to_disk(true)`（每次 `fsync`） | 每次淘汰 = 1 次 `fsync` |

**数据支撑**：TPC-C 50 仓库的 `stock` 表约 5M 行 × ~300B ≈ 1.5GB；仅 4 个热点仓库（~65% 流量）的 `stock` 就约 120MB，逼近 128MB 池。饱和负载下缓冲池持续淘汰；而 `flush_wal_before_page_write()` 每次淘汰都调 `flush_log_to_disk(true)`，`flush_log_to_disk_locked(force_sync=true)` 在 `durable_lsn_ < written_lsn_` 时必然 `disk_manager_->sync_log()`（裸 `fsync`），把淘汰路径串行化在日志 fd 的 `fsync` 上。两个因素相乘，正是 20 分的直接原因。

**关键佐证**：`finals-wire-ssi` 的 MVCC（64 分片）、`commit_apply_latch_`（`shared_mutex`）、组提交（leader 选举）、Phase-2 限流、snapshot 准入控制——**每一项都比 `dbg/db2026` 先进**。架构更先进却慢 17×，说明瓶颈不在"缺特性"，而在上述两处 I/O 层面的倒退。

### 1.2 已实施的两项修复

见第二节，两处改动均已落地，且都是队友仓库"通过全部正确性门槛 + 恢复 + fsync 审计"的既有配置，风险极低。

### 1.3 340 → 10000 的杠杆（待测量）

340 到 10000 是 30× 的量级差，**不是单点 bug**，而是一组热路径成本的叠加。本仓库已具备：预处理语句复用（`EXEC_BATCH` 复用 `PlanExecutable`，解析/优化只在一次性 `PREPARE_SET` 争用）、隐式只读 SELECT 跳过 WAL COMMIT、leader 选举组提交。剩余杠杆集中在第三节，**每一项都必须先测量、再改、再按回归矩阵验证**（`正确性门槛关键要求.md` §5 问题 1 明确要求"消除的是已测量瓶颈"）。

## 二、已实施修复（变更准入记录）

### 变更 1：Buffer pool 128MB → 512MB

- 文件：`src/common/config.h`（`BUFFER_POOL_SIZE` 32768 → 131072）。

1. **消除的瓶颈**：缓冲池过小导致的持续淘汰，以及淘汰路径被迫高频刷 WAL 的压力。
2. **并发对象 / 锁顺序 / 线性化点**：无新增。纯常量，不引入任何锁或顺序。
3. **WAL / heap / index / MVCC 提交与回滚顺序**：不变。
4. **崩溃点 winner/loser**：不变。池大小只影响页面驻留，不改变任何日志语义。
5. **慢路径**：无新增。
6. **测试**：功能 25/25、恢复 5/5、fsync 审计 32/32——与 `dbg/db2026` 同配置已通过。
7. **吞吐可复现**：是。代价是 +384MB 常驻内存，需确认测评机器内存 ≥ 1GB；否则回退。

### 变更 2：脏页淘汰路径去掉 fsync

- 文件：`src/storage/buffer_pool_manager.cpp`（`flush_wal_before_page_write` 的 `flush_log_to_disk(true)` → `false`）。

1. **消除的瓶颈**：每次脏页淘汰的 `fsync`，它把整个淘汰路径串行化在日志 fd 上。
2. **锁顺序 / 线性化点**：无新增。仅改一个 `force_sync` 实参。
3. **提交与回滚顺序**：不变。COMMIT 的 durable 保证仍在 `force_flush_up_to → flush_log_to_disk_locked(true)` 里做 `fsync`；读侧可见性由 MVCC 版本链保证，与 WAL 刷写解耦。
4. **崩溃点 winner/loser**：淘汰时 WAL 只 `pwrite` 进内核 page cache。测评明确声明"SIGKILL 不等价于整机断电"，page cache 不丢失；数据页随后 `pwrite` 时，其 WAL 已先进入内核，满足 WAL-before-data，恢复读到的 WAL 前缀完整。若淘汰后立即**断电**（非测评场景），脏页与未 fsync 的 WAL 一起丢失，这正是 WAL-before-data 允许的"一起丢"窗口。COMMIT 已被 ACK 的事务，其 WAL 早在 COMMIT 时 fsync，不受影响。
5. **慢路径**：无。COMMIT 路径仍 fsync。
6. **测试**：32/32 fsync 审计（审计点是 COMMIT ACK 前 WAL 已 durable，不经过淘汰路径）、恢复 5/5。
7. **吞吐可复现**：是。纯消除冗余 fsync，不牺牲完成率或尾延迟。

## 三、340 → 10000 的优化杠杆

以下按"最可能成为 top-1 瓶颈"排序，**每一项都要用 `RMDB_PERF_DIAG=1` 先测出数据再动手**。诊断指标已内建：`txn_state_wait / commit_apply_read_wait / commit_apply_write_wait / heap_file_wait / index_root_read_wait / index_root_write_wait / wal_durable_wait / wal_fsync / wal_group_size`。

### L1. 读路径的 `commit_apply_latch_` 共享锁放大（首选怀疑对象）

- **现状**：每条 `RmFileHandle::get_record` 都取 `commit_apply_latch_` 共享锁；每次 commit 的 Phase 1（可见性发布）都取它的写锁。32 客户端高频提交下，`shared_mutex` 的控制块成为 cache-line 争用点，读写互相拖累。
- **候选**：把"可见性发布"从全局 `commit_apply_latch_` 下沉到 64 个 MVCC 分片各自的 latch（发布只锁涉及的分片），读侧按 `file_id+rid` 定位分片后只取该分片共享锁。锁序保持 `分片 latch → 文件 insert_latch_/index`，不新增逆序。
- **正确性要点**：可见性线性化点仍是"该分片内 commit_ts 赋值完成"，跨分片的发布通过分片锁的排序获取避免死锁。需回答 §5 问题 2/3/4。
- **验证**：SI/SER 48 组隔离历史、写冲突、谓词冲突、多客户端随机交错。

### L2. 写路径 per-table 串行化（`insert_latch_` / `logical_update_latch_`）

- **现状**：INSERT 对"查唯一 + 物理插"全程持 per-table `logical_update_latch_`（仅当表有索引）；`insert_record_internal` 再持 `insert_latch_`。TPC-C 中 NewOrder 对 `order_line`（每事务 5-15 行）、`orders`、`new_orders` 的高频 INSERT 全在同一把表级锁上排队。
- **候选**：唯一冲突检测下沉——先只锁唯一索引、在索引层做"键不存在才插入"的原子判定，避免持表锁遍历；表级 `insert_latch_` 缩短到只覆盖物理 `insert_record` 的临界段。
- **正确性要点**：唯一约束判定与物理插入的原子性必须保留（否则并发重复键），只是把锁的覆盖范围缩到最小。需回答 §5 问题 2/3。
- **验证**：随机 INSERT/UPDATE/DELETE、唯一冲突、表索引一致。

### L3. 索引根页 latch 的读放大

- **现状**：`perf_counters` 里 `INDEX_ROOT_READ_WAIT / INDEX_ROOT_WRITE_WAIT` 表明索引根有共享/独占 latch。`stock`（5M 行 B+ 树）每次 UPDATE 前都要 `get_value` 定位 rid，读放大明显。
- **候选**：无锁 B+ 树（乐观读 + 失败重试）或按子树分段 latch。
- **验证**：随机增删改、split/merge、表索引一致。

### L4. WAL / 组提交窗口与异步刷写

- **现状**：组提交 leader 等 1000µs 窗口（`RMDB_GROUP_COMMIT_US`，可环境变量调）后单次 fsync 覆盖整批。窗口越大批量越大、延迟越高，最优值取决于 fsync 延迟与提交到达率。
- **候选**：先纯调参扫 `RMDB_GROUP_COMMIT_US ∈ {250,500,1000,2000}` 找最优点（队友用 ~250µs）；若 `wal_durable_wait` 仍高，再上**独立 WAL writer 线程**——执行期只 append 进 4MB buffer，writer 线程持续 `pwrite`，COMMIT 只等待 `durable_lsn_` 覆盖自己 LSN，把 fsync 与执行重叠。
- **正确性要点**：ACK 必须在 `durable_lsn_ ≥ 本事务 commit LSN` 之后，绝不能提前。这是 §4 里"任一提前 ACK 立即回退"的红线。
- **验证**：32 并发 COMMIT 的 durable coverage、I/O 故障、ACK 顺序。

### L5. 内存分配 churn

- **现状**：每个 MVCC 版本存 before/after 两份 `std::vector<char>`；每条 WAL 记录序列化有临时缓冲；`portal_->start` 每语句新建 executor 树。
- **候选**：arena/对象池复用版本缓冲与 executor 对象；WAL 序列化就地写 buffer，减少一次拷贝。
- **验证**：全量功能回归（此项不改语义，主要测泄漏与越界）。

> 以上候选都不触及 §5 红线：不按固定表名/固定数据走捷径、不跳过持久化、不提前可见、不做部分回滚、不做近似结果。

## 四、分阶段实施计划

### Phase 0 —— 验证当前两项修复（先做，不急着加新东西）

1. 在 Linux 测评环境重建（`-O2`）。
2. 跑 `正确性门槛关键要求.md` §4 全量回归矩阵（功能 / Wire / MVCC-SSI / heap-index / WAL / recovery / LOAD）。
3. `RMDB_PERF_DIAG=1` 跑 3×150s 满负载，导出指标，记录 NewOrder/min 基线。

**退出条件**：全部正确性通过，且 NewOrder/min 应接近或达到 `dbg/db2026` 的 340 量级。若没有明显回升，说明还有第三处未定位瓶颈，回到指标找 top-1。

### Phase 1 —— 针对测量出的 top-1 瓶颈，单点优化

从第三节选**恰好一项**，按 §5 七问完整作答后实施，跑 §4 对应行回归；失败立即回退。

### Phase 2 —— 逐项叠加，每项独立验证

L1 → L2 → L3 → L4 → L5 的顺序由每轮测量结果动态调整，**一次只改一处**，便于回退定位。

### Phase 3 —— 扫尾调参

组提交窗口、Phase-2 并发度（`kMaxConcurrentPhase2`）、snapshot 准入阈值等旋钮在正确性全绿的前提下做网格搜索。

## 五、红线（直接否决）

- 基于固定表名 / 固定测试数据的短路。
- 跳过持久化、提前可见（可见性早于物理完成/持久化，`正确性门槛关键要求.md` §2.5 已点名否决）。
- 部分回滚、近似浮点结果（FLOAT32 必须 0-ULP）。
- COMMIT ACK 早于 `durable_lsn_` 覆盖。
- 任何破坏"锁顺序 → 无死锁"的改动。
