# 第 4 页｜六大板块构成完整 RMDB（0:45）

## 本页核心结论

RMDB 不是一条简单的 SQL 流水线，而是由接入、查询、执行、事务、存储和恢复六个板块协同组成；其中事务与恢复会同时约束执行和存储。

## PPT 可直接放置的文字

**1. 接入与协议**

> `ConnectionSession`、`RequestDispatcher` 和 `PreparedDictionary` 负责 Wire v3、类型化参数、PREPARE_SET、EXEC_BATCH、会话状态和批量响应。

**2. 查询处理**

> Parser、Analyzer、Planner 和 Optimizer 完成语法解析、语义检查、谓词处理、索引选择和 Join 规划，生成物理执行计划。

**3. 执行引擎**

> SeqScan、IndexScan、Join、Aggregate 和 DML Executor 消费计划，输出查询结果或产生事务写入。

**4. 事务与并发**

> TransactionManager、TransactionWriteBatch、MvccStore 和 TxnRegistry 负责锁、MVCC、SI/SSI、写意向、冲突判断和提交状态。

**5. 存储与索引**

> Heap File、B+Tree、Buffer Pool、PageGuard 和 Disk Manager 负责记录组织、页面缓存、索引访问、并发页面操作和落盘。

**6. 日志与恢复**

> LogManager、LogRecordScanner 和 Recovery 负责 WAL、group commit、checkpoint、redo、undo 和崩溃恢复。

## 排版设计

- 顶部使用窄幅“接入与协议”横带；
- 中间左侧为“查询处理 + 执行引擎”；
- 中间右侧为“事务与并发”；
- 底部宽幅区域为“存储与索引”；
- 右侧纵向窄带为“日志与恢复”，同时连接事务和存储；
- 模块大小不完全相同，事务、存储和 WAL 占据更大面积；
- 每个模块保留关键类名和一句职责，不做只有名词的空卡片。

## 讲解参考

“接入、查询和执行负责把请求转化为操作；事务层决定操作能否并发提交；存储层完成记录与索引修改；WAL 和恢复保证提交状态可以持续存在。后面的性能问题主要集中在事务、存储和 WAL 三块。”

# 第 5 页｜请求从 SQL 到数据页的运行链路（0:40）

## 本页核心结论

一次请求在查询路径和写入路径上共享 Parser、Planner 与 Executor，但读写进入事务层后会形成不同的数据访问方式。

## PPT 可直接放置的文字

**计划生成**

> 客户端请求由 Wire 层解码，prepared 请求直接复用已有计划；普通请求经过 Parser、Analyzer 和 Planner，得到包含 Scan、Join、Aggregate 或 DML 的执行计划。

**读取路径**

> Executor 根据计划选择 SeqScan 或 IndexScan，通过 B+Tree 获取候选 RID，再由事务层选择当前快照可见的版本，最终从 Heap/MVCC 中获得记录并返回结果。

**写入路径**

> DML Executor 生成 INSERT、UPDATE、DELETE 操作，事务层负责写意向、版本与提交状态；物理修改涉及 Heap、索引和 WAL，只有提交完成后才成为其它事务可见的结果。

## 推荐主图

```text
Client / Wire
      ↓
Parser / Analyzer / Planner
      ↓
Executor
   ↙               ↘
读取：Index/Heap    写入：Transaction
   ↘               ↙
      Buffer Pool / Storage
              ↕
            WAL
```

## 排版设计

- 上方 35% 放计划生成；
- 下方从 Executor 分成读取和写入两条分支，再在存储层汇合；
- 读取分支用蓝色，写入分支用琥珀色；
- WAL 以竖向旁路连接事务和存储，不放在链路最末端；
- 图右侧放三段说明文字，每段控制在两行左右。

## 讲解参考

“查询请求经过计划与执行器后，读取路径主要是索引、可见性和 Heap；写入路径还要经过事务冲突、Heap/Index 修改和 WAL。最终性能优化的重点，就是减少这条写入路径中的无效工作和全局等待。”

# 第 6 页｜事务、存储和 WAL 共同构成提交单元（0:45）

## 本页核心结论

写事务不是简单地“修改一条记录”，而是同时改变逻辑版本、物理表、索引和日志。性能优化必须让这些状态协同更新，而不能只加速其中一个模块。

## PPT 可直接放置的文字

**事务逻辑状态**

> 事务层维护 start timestamp、可见版本、写意向、私有写入和提交状态，决定其它事务在什么时候能够看到新值。

**物理存储状态**

> Heap 保存记录主体，B+Tree 保存键到 RID 的访问路径，Buffer Pool 管理缓存页、dirty、pin 和 page LSN。UPDATE 可能同时改变记录内容和多个索引项。

**持久化状态**

> WAL 记录 before/after image 和事务状态，COMMIT LSN 决定返回前必须持久化到哪个位置；恢复模块依靠日志重建 committed 事务并撤销未完成事务。

页面中心放一句：

> **一次提交 = 逻辑版本完成 + Heap/Index 完整应用 + COMMIT WAL 持久化**

## 排版设计

- 使用三角形构图，三个顶点分别是“事务逻辑状态、物理存储状态、持久化状态”；
- 三角形中心放“Commit Unit”；
- 顶点之间使用双向细线，不画普通横向流程；
- 左下角放一个 UPDATE 示例：记录值变化、索引键变化和 WAL before/after image；
- 页面底部以一行话引出性能问题：旧架构在语句执行阶段交错修改三类状态，导致冲突回滚和锁范围过大。

## 讲解参考

“事务、存储和 WAL 是一个提交单元。旧系统的问题，是每条语句执行时就交错修改版本、Heap、索引和日志，冲突越晚，回滚越重。后面的架构重构就是重新安排这三类状态在什么阶段发生变化。”

# 第 8 页｜旧版本在高并发下为什么无法扩展（0:50）

## 左侧主数据：并发负扩展

| 客户端 | NewOrder tpmC | 提交率 |
| ---: | ---: | ---: |
| 1 | 约 4497 | 100% |
| 4 | 约 2427 | 20.7% |
| 8 | 约 1095 | 5.8% |
| 16 | 约 891 | 约 2% |
| 32 | 约 418 | 小于 1% |

结论：

> 单事务执行并不慢，但客户端增加后成功提交率快速下降。大量事务完成解析、索引访问和部分物理写入后，最终在热点 district、stock 或唯一键上冲突并 abort。

## 右侧只讲四个重点原因

**冲突发现太晚**

> DML 先修改 Heap 和 Index，提交阶段才发现写冲突，失败事务已经消耗大量 CPU、页面和索引工作。

**全局准入和粗粒度协调**

> SI=1 能减少回滚并取得 OJ AC 947，但所有客户端最终排成一条队；Parser、Buffer 页表和 commit-apply 等共享结构也产生明显等待。

**逐记录物理操作**

> 同一页面和索引叶上的多条写仍重复 pin、锁、bitmap 解析和根到叶遍历，固定成本随事务写入条数重复发生。

**逐事务日志同步**

> 每个事务独立 write/fsync，普通 abort 也可能执行重型刷盘；吞吐增加后同步 I/O 成为新的串行点。

## 排版设计

- 左侧 55% 使用客户端数—tpmC 折线图，曲线从 4497 降到 418；
- 右侧 45% 沿旧架构剖面标记四个红色热区；
- 只讲四个重点原因，不再列出大量失败实验；
- 页面底部放一句：`旧系统优化的是单次操作，新架构需要优化并发事务的整体成本。`

## 讲解参考

“旧版本最大的特征是负扩展：单客户端 4497，32 客户端只剩 418。根因不是基本 SQL 能力，而是冲突太晚、物理回滚太重、全局协调和逐事务 fsync。接下来重点讲我们如何改变这些结构。”

# 第 10 页｜性能重构总览：五种结构性变化（0:45）

## PPT 可直接放置的文字

**重复解析 → 计划复用与数据收敛**

> Prepared、typed parameter、EXEC_BATCH 和复合索引前缀减少请求、解析、网络往返及扫描行数。

**立即物理写 → 事务私有逻辑写批**

> INSERT、UPDATE、DELETE 先进入 TransactionWriteBatch，同一记录的多次修改可以合并，失败事务不再回滚已经修改的页面。

**全局等待 → 分片 intent 与局部锁**

> MVCC 使用 256 shards，Buffer page table 使用 64 shards，B+Tree 使用局部 crabbing，只让真正共享记录、页面或树分支的事务互相协调。

**逐行提交 → Heap Page/B+Tree Leaf Batch**

> 有序写集按页面和索引叶分组，一页或一叶只获取一次 guard，减少重复 bitmap 解析、pin 和树遍历。

**逐事务同步 → WAL Batch/Group Commit**

> row WAL 批量进入日志缓冲，多个事务共享一次 write/fsync，但每个事务仍等待自己的 COMMIT LSN durable。

## 排版设计

- 使用五条从左上到右下逐渐展开的斜切色带；
- 每条色带左侧放旧模式，右侧放新模式和一整句收益；
- 中间三条使用最深蓝，突出事务、分片和页批是主要突破；
- 底部放总纲：`少做无效工作｜冲突提前｜物理操作批量化｜协调范围局部化｜同步成本共享`。

## 讲解参考

“整体重构可以归纳为五个变化。最关键的不是 prepared 或某个锁本身，而是中间三项：写入先私有暂存，冲突在分片 intent 中提前处理，成功事务再按 page 和 leaf 批量提交。”

# 第 11 页｜TransactionWriteBatch 与分片 intent（1:30）

## 本页核心结论

TransactionWriteBatch 解决“写入太早、回滚太重”，256-shard intent 解决“热点冲突拖住所有连接”。

## 左侧：事务私有写批

> SI 下的 INSERT、UPDATE、DELETE 不再立即修改 Heap 和 Index，而是登记 table、file id、RID/TempRowId、before-image 和 after-image。自己的读取通过 overlay 看到最新写，其它事务无法访问这份私有状态。

写合并规则：

- 连续 UPDATE：保留最初 before 与最终 after；
- UPDATE 后 DELETE：合并为一次 DELETE；
- INSERT 后 UPDATE：直接修改临时 after-image；
- INSERT 后 DELETE：逻辑写直接消去。

示例：

```text
stock#17：60 → 55 → 48
最终物理 mutation：60 → 48
```

## 右侧：256-shard intent

> MvccStore 将版本链、record intent、unique key intent 和 GC dirty key 划分为 256 个 shard。事务已经持有 intent 时幂等成功；旧 owner 已结束时可以接管；其它活跃事务持有时立即返回冲突。

重点说明：

- 热点 district 或 stock 冲突时 fail-fast；
- 不同 RID、不同唯一键和不同 shard 可以继续并发；
- 最终排名路径不设置 SI 全局 admission；
- 物理 Phase-2 apply 默认最多 16 个并发事务，避免页面、索引与 WAL 同时过载。

## 为什么更快

> 旧模型中，失败事务已经完成查询、索引和部分物理写；新模型中，冲突发生在物理修改之前。普通 abort 只丢弃 WriteBatch、pending version 和 intent，不需要撤销数据页和索引。

## 排版设计

- 左侧 55% 放 WriteBatch 容器、写合并规则和 stock 示例；
- 右侧 45% 放 256 格 shard 抽象图，少数热点格为红色，其余为蓝色；
- 页面下方用对比标尺：`SI=1 全局排队` → `无全局 admission + Phase-2 16 并发`；
- WriteBatch 和 fail-fast 用琥珀色强调。

## 讲解参考

“WriteBatch 把写入留在事务内部，并合并同一行的多次变化。随后 256-shard intent 只让真正竞争同一对象的事务冲突，热点事务尽早失败，不相关事务继续运行。相比 SI=1 把所有连接串行化，这才是真正的并发扩展。”

# 第 12 页｜Page/Leaf Batch 与局部存储并发（1:15）

## 左半页：Heap Page Batch

> `StorageCommitExecutor` 将冻结写批分组为 `HeapPageKey(fd, page_no) → HeapMutation[]`。同一页内按 slot 排序，`apply_page_batch()` 在一个 WritePageGuard 中连续应用多条 INSERT、UPDATE 和 DELETE。

对比：

```text
旧：8 条修改 = 8 次 fetch/pin + 8 次锁 + 8 次 bitmap 处理
新：8 条修改 = 1 次 page guard + 连续应用 8 个 mutation
```

## 右半页：B+Tree Leaf Batch

> Index mutation 按 index fd 和 key 排序。定位叶页并取得写 guard 后，重新验证 frame generation、叶类型、键范围和兄弟关系；安全时在同一叶页完成一组 INSERT/DELETE，条件不满足时 restart 并进入 parent-before-child crabbing 结构路径。

对比：

- 旧：每个 key 都从根重新遍历，全局 split 锁限制结构修改；
- 新：同叶批次复用定位和 guard，根锁只用于替换 root page id。

## 底部：Buffer Pool 并发底座

> page table 划分为 64 个 shard，每个 frame 使用独立 metadata latch 和 content shared_mutex。PageGuard 统一管理 pin、dirty、page LSN 和 generation，不同页面可以真正并发访问。

## 为什么更快

> WriteBatch 减少物理写次数，Page/Leaf Batch 降低每次物理写的固定成本，分片 Buffer Pool 与局部 B+Tree 缩小事务之间的锁冲突范围。

## 排版设计

- 左右各使用一个大型 Heap Page、B+Tree Leaf 剖面；
- 底部使用 64 个小块表现 Buffer page table；
- 蓝色轨迹表示批量 mutation，琥珀色表示 page/leaf guard；
- 红色只表示校验失败后的 restart，不画横贯全页的长链路。

## 讲解参考

“WriteBatch 提供有序写集，StorageCommitExecutor 再按页面和索引叶消费。同一 Heap 页只拿一次 guard，同一安全叶页完成一组索引修改；Buffer Pool 分片后，不同页面也不再争用同一页表锁。”

# 第 13 页｜上游减负与 WAL 共享同步（0:55）

## 上半页：减少事务自身工作量

> PREPARE_SET 保存计划与输出 schema，执行时只绑定 INT32、FLOAT32 和 CHAR 等真实参数；EXEC_BATCH 减少请求、DML ACK 和网络往返。Planner 对谓词规范化、去重和等值传播，并以“连续 EQ 前缀 + 最多一个 RANGE”评价复合索引。

页面旁注：

> 少解析、少往返、少扫描，也意味着更短的快照和 intent 持有时间。

## 下半页：共享日志同步成本

> row WAL 通过 `add_logs_to_buffer()` 批量进入缓冲。第一个 `force_flush_up_to()` 等待者成为 group leader，默认等待约 1 ms，让同时完成的事务加入同一次 write + fsync；每个事务仍等待自己的 commit LSN 被 durable watermark 覆盖。

时间轴：

```text
Txn A ┐
Txn B ├─ 1 ms 聚合窗口 ─ 一次 write/fsync ─ 分别返回
Txn C ┘
```

## 持续运行优化

> 普通 staged-write abort 没有物理副作用，不再执行全库 checkpoint 和单独 fsync；LogRecordScanner 顺序缓冲读取 WAL；安全水位 GC 每 256 次 MVCC commit 增量清理一个 shard，避免版本和 TxnControl 持续增长。

## 排版设计

- 上半页使用 prepared 计划复用图和候选集漏斗；
- 下半页使用 WAL 时间轴；
- Scanner 与 GC 只放两个小型线稿，不抢占主视觉；
- 本页不再重复事务提交流程。

## 讲解参考

“Prepared 和索引前缀让事务少做工作，缩短持有共享资源的时间；WAL batch 和 group commit 让多个成功事务共享 fsync。轻量 abort、scanner 和 GC 让高吞吐可以持续运行，而不是只得到短时峰值。”

# 第 16 页｜新架构为什么更好、正确性与剩余瓶颈（0:30）

## 四条总结

**冲突更早。**

> WriteBatch 和 intent 让失败事务在物理修改前结束，不再浪费页面和索引工作。

**提交更批量。**

> 有序写集按 Heap Page 和 B+Tree Leaf 聚合，减少重复 guard、bitmap 和树遍历。

**并发更局部。**

> MVCC 256 shards、Buffer 64 shards 和局部 crabbing 让不相关事务不再全局排队。

**同步可共享。**

> Prepared 减少固定请求成本，Group Commit 让多个事务共享 write/fsync。

## 正确性只带过一句

> Heap、Index 和 WAL 完整稳定后才发布版本；快速路径校验失败时回退到正确慢路径。

## 剩余瓶颈

> abandoned 约 25.06%；fsync 占所选 syscall 时间约 87.4%；Delivery p99 为 441.698 ms；三轮吞吐波动明显，说明热点冲突、I/O 同步和尾延迟仍有优化空间。

## 最终结论

> 从 418 到 30,741.2 的本质，是将“全局等待、晚冲突、逐行写入”改造成“分片并发、早冲突、事务级批提交”。

## 排版设计

- 左侧 68% 放四条由浅到深的蓝色宽色带；
- 右侧 32% 放正确性一句话和剩余瓶颈；
- 底部用大字放最终结论；
- 讲完直接进入提问，不增加纯“谢谢”页。

### 备份页 C｜高频性能问题

**为什么取消 SI=1？**

SI=1 能降低冲突，但所有事务排队执行，形成硬性串行上限。最终使用分片 intent，只让真正竞争同一对象的事务冲突。

**为什么物理 apply 仍限制为 16 个并发？**

逻辑事务不设置全局 admission，但物理提交同时修改页面、索引和 WAL。默认 16 个 Phase-2 apply 用于控制页面锁、内存和日志竞争。

**为什么不能把全部提升归因于 WriteBatch？**

WriteBatch 是架构基础，但最终结果还依赖 256-shard intent、索引前缀、Page/Leaf Batch、分片 Buffer Pool、轻量 abort 和 group commit。缺少任何一层，瓶颈都会移动到下一层。
