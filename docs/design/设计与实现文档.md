# 数据库系统设计文档

**RMDB —— 关系型数据库管理系统**

得特贝斯队 · 2026 年 8 月

---

## 摘要

本设计文档描述了我们从零实现的关系型数据库内核 RMDB 的设计与实现。系统以 C++17 编写，遵循「页面式存储 + B+Tree 索引 + WAL 日志」的经典体系，并在此基础上实现了多版本并发控制（MVCC）与三种隔离级别（READ COMMITTED / SNAPSHOT ISOLATION / SERIALIZABLE），对外通过 Wire v3 协议提供服务，能够稳定运行 TPC-C 饱和负载。系统的设计目标为高效存储、并发一致与可扩展性；架构上坚持模块化（存储、执行、事务分离），并把性能优化落在「计划 → 暂存写 → 页级批提交 → 分片冲突检测 → 局部闩锁 → 便宜 abort → 快速恢复」这条通用机制链上，而非对特定 SQL 做特判。在决赛性能评测（32 客户端、多轮测量窗口取 NewOrder/min 中位数）中，最终排名吞吐为 **30,741.2 NewOrder/min**，较旧架构基线提升约 **73.5×**，同时通过功能、持久化、压测后一致性与崩溃恢复全部校验。

## 1 设计思路

### 1.1 系统目标

- **高效存储**：以 4KB 页为粒度的 Heap 存储与 B+Tree 索引，配合分片缓冲池与批写，降低 I/O 与闩锁开销。
- **并发一致**：以 MVCC 快照 + 提交校验支撑 SNAPSHOT ISOLATION，以 SSI 依赖检测支撑 SERIALIZABLE，兼顾读并发与可串行化。
- **可扩展性**：存储、执行、事务分层解耦，预留代价模型、增量检查点与分布式方向的空间。

### 1.2 设计原则

- **模块化**：存储（磁盘 / 缓冲池 / 记录 / 索引）、执行（计划 / 算子）、事务（并发 / MVCC / 日志）三层职责分离，通过明确的接口衔接。
- **通用机制而非特例快路径**：优化作用于查询计划、批提交、分片冲突检测等通用环节，禁止对表名、列名、statement_id 或客户端数做特判。
- **正确性优先**：一切性能改动以「功能、一致性、`kill -9` 崩溃恢复」门禁为前提，破坏正确性的候选整体撤回。
- **持久性边界清晰**：COMMIT ACK 前必须 `durable_lsn >= commit_lsn`；未持久化的事务绝不对其他事务可见（durable-before-visible）。

### 1.3 总体架构

内核按请求处理路径分层，一条 SQL 依次经过网络层、SQL 前端、优化与计划、执行引擎、事务并发、记录与索引、缓冲与磁盘、日志与恢复：

```text
客户端 → 网络层(Wire v3) → parser(词法/语法) → analyze(语义分析)
       → optimizer/planner(计划生成) → portal(执行器树)
       → executor(算子执行) → transaction(MVCC/提交) → record/index
       → buffer_pool(64 分片) → disk_manager → WAL/恢复
```

| 层 | 主要职责 | 关键组件 |
|------|----------|----------|
| 网络 / 协议 | 连接管理、Wire v3 报文解析与序列化 | `DBStorageEngine`、`network/` |
| SQL 前端 | 词法 / 语法 / 语义分析 | `parser/`、`analyze/` |
| 优化与计划 | 逻辑优化、谓词下推、索引选择、连接排序 | `optimizer/`、`planner.cpp` |
| 执行引擎 | 算子执行、批扫描、聚合 | `execution/`、`portal.cpp` |
| 事务 / 并发 | 隔离级别、MVCC、写批、提交发布 | `transaction/`、`MvccStore`、`TxnRegistry` |
| 记录 / 索引 | Heap 记录、B+Tree、批写 | `record/`、`index/` |
| 缓冲 / 磁盘 | 4KB 页、分片缓冲池、页面守卫 | `storage/`、`replacer/` |
| 日志 / 恢复 | WAL、组提交、检查点、redo/undo | `recovery/`、`log_manager` |

## 2 系统框架

### 2.1 存储管理

#### 2.1.1 磁盘管理

职责：以页为单位进行文件 I/O。主要能力：

1. 文件生命周期：创建 / 打开 / 关闭 / 销毁；
2. 页 I/O：按页读写、写回对齐、错误处理与返回码；
3. 与缓冲池协同：仅支持页粒度接口，保障一致性。

#### 2.1.2 缓冲池管理

目标：热数据命中与 I/O 次数最小化。核心设计：

1. **64 分片页表**（`PageTableShard`）：把全局页表锁竞争拆散到独立分片，按页号哈希定位分片。
2. **RAII 页面守卫**（`PageGuard`，含 `Basic` / `Read` / `Write` 变体）：析构时自动 unpin，杜绝泄漏与漏解锁。
3. **淘汰策略**：采用 LRU-K 变体（History / Candidates 两区），过滤一次性顺序扫描带来的缓存污染。
4. **脏页管理**：修改置脏、触发回写、全量刷盘；缓冲池大小按物理内存估算并带上下限，可与评测 RSS 上限对齐。

#### 2.1.3 记录管理与遍历

1. 行级操作：插入 / 删除 / 更新 / 读取，记录由 `RID = (page_no, slot_no)` 定位，页内空闲槽位由 bitmap 管理。
2. 游标遍历：提供全表扫描接口，支撑选择 / 投影 / 连接等算子。
3. 空闲页维护：维护空闲槽候选队列，插入优先复用，减少页分裂。

### 2.2 索引管理

B+Tree 索引支持聚簇 / 非聚簇两种形态，核心能力：

1. **定位**：大于等于给定键、严格大于给定键的叶子节点；
2. **维护**：键的插入 / 删除与节点分裂 / 合并 / 重分配；
3. **乐观叶插入**：仅在叶页有空间时本地插入，避免整棵树加锁；
4. **latch crabbing**：结构修改按页局部加锁，取代索引级大锁；分裂涉及当前页与兄弟页时按物理页号排序加锁，避免死锁；
5. **惰性删除**：删除先标记，必要时再回收，降低结构修改频率；
6. **唯一性维护**：插入时若键已存在立刻中止；更新时若新键存在则拒绝（新旧相同除外，避免无效冲突）。

索引层还支持**同叶批写**（`apply_sorted_batch`）：排序后的键变更按目标叶页分组，一次写保护内完成一组插入 / 删除，是连续写复合索引时吞吐跃升的存储层基础。

### 2.3 查询执行

执行引擎遵循 Volcano 逐行拉取模型，并叠加页级批处理：

1. **DDL**：`CREATE TABLE` 初始化表文件与元数据并注册；`DROP TABLE` 关闭并删除表及相关索引。
2. **DML**：`INSERT` 构造二进制行并写表与索引；`DELETE` 检索后删行与索引键；`UPDATE` 行更新并同步索引（唯一约束先检冲突）。
3. **DQL**：提供选择（遍历 + 谓词）、投影（列裁剪）、连接（Index-Join / 嵌套循环连接）、聚合（MAX/MIN/COUNT/SUM/AVG，支持 GROUP BY）等算子。
4. **批扫描**：`batch_seq_scan` / `batch_index_scan` 整页搬运可见记录，算子交互由「逐行」变「整页」，显著减少接口调用与重复 pin/unpin。

### 2.4 查询优化

`Planner::logical_optimization()` 形成完整的查询级优化流程：

1. 谓词规范化与去重；
2. 单表谓词尽早下推；
3. 等值关系传播，扩大可用常量与连接约束；
4. 按「已连接列与本表常量条件能覆盖的最长连续索引前缀」评分候选索引；
5. 综合连接关系、索引前缀覆盖与过滤条件做通用连接排序；
6. 索引只缩小候选，**最终仍执行全部 JOIN / WHERE**，结果语义不变。

这使得 TPC-C 中涉及复合主键、仓库号、地区号与订单号的多表查询从大范围扫描转为复合索引前缀定位，尤其降低 Delivery、OrderStatus、StockLevel 与一致性关系检查的代价。

### 2.5 事务与并发控制

#### 2.5.1 三种隔离级别

| 级别 | 实现机制 | 语义 |
|------|----------|------|
| READ COMMITTED | 锁式 | 语句级读已提交版本 |
| SNAPSHOT ISOLATION | MVCC 快照 | 事务读一致快照，写偏斜由提交校验兜底 |
| SERIALIZABLE | SSI 依赖检测 | 在 SI 之上检测读写依赖环并中止，保证可串行化 |

#### 2.5.2 事务私有写批（TransactionWriteBatch）

写入不直接在语句期落到物理页，而是先 **stage** 到事务私有的逻辑写批：

- `stage_insert` / `stage_update` / `stage_delete` 只记录逻辑变更，不触碰磁盘与索引；
- 通过 overlay 保证「读己之写」——事务能看到自己尚未提交的变更；
- 冲突事务多数只需丢弃内存批，abort 成本被大幅压低。

#### 2.5.3 分片冲突检测（MvccStore）

MVCC 状态按 ResourceKey 哈希切成 **256 个分片**：

- 记录级版本链与唯一键意图（record intent / unique intent）分别分片存储；
- 写冲突在语句期 fail-fast，避免堆大量注定失败的工作；
- `TxnRegistry` 维护提交时钟与「连续可见前缀」，读者只能读到连续已发布的前缀，保证快照一致性。

#### 2.5.4 提交流程

提交分阶段进行，顺序保证「先落盘、再可见、最后 ACK」：

```text
Seal（冻结写集） → Validate（SI/SSI 冲突校验）
  → Acquire Intent（获取唯一键意图，保证并发下唯一性）
  → Phase-2 Apply（物理应用：页批写 + WAL 落盘，受并发上限约束）
  → Publish（推进可见前缀，发布提交时间戳）
```

- Phase-2 物理应用受并发上限（`RMDB_PHASE2_MAX_ACTIVE`，默认 16、上限 64）约束，防止提交风暴拖垮缓冲池与日志。
- 提交边界遵循 **durable-before-visible**：物理应用与 COMMIT 日志落盘完成后才发布可见。
- 发布失败只消费时间戳但不产生可见版本，快照不会读到不完整前缀。

### 2.6 日志与崩溃恢复

采用 WAL（写前日志）配合静态检查点，恢复遵循 ARIES 三阶段。

**日志与规则**：日志按顺序追加并带递增 LSN，页头维护 pageLSN。遵循两条 WAL 规则——数据页写盘前其对应日志必须已持久化（WAL-before-data）；事务提交前其所有日志必须已落盘。

**组提交**：提交线程在约 1ms 窗口（`RMDB_GROUP_COMMIT_US`）内聚合多个事务的日志一起 `flush`，把每事务的 fsync 摊销掉。

**检查点流程（静态）**：阻塞新事务 → 等待在途事务完成 → 刷新全部脏页 → 刷新日志并记录 `last_checkpoint_lsn` → 解除阻塞。

**恢复流程（ARIES 三阶段）**：

1. **分析（Analysis）**：自 `last_checkpoint_lsn` 向后扫描，识别需重做的更新与需撤销的事务集合；
2. **重做（Redo，重复历史）**：按 LSN 顺序重放，仅当页 pageLSN 小于日志 LSN 时才应用并更新 pageLSN（幂等）；
3. **撤销（Undo）**：对未提交事务按逆序撤销，处理 active loser 与 committed winner 的唯一键冲突。

恢复阶段用固定缓冲顺序扫描 WAL（`log_record_scanner`），替代逐条 `pread`，同一份约 35MiB WAL 的恢复系统调用从约 63.5 万次降到约 3,312 次，显著缩短崩溃后就绪时间。

### 2.7 网络协议与批执行

对外采用 **Wire v3** 协议，核心控制点：

- `EXEC_STREAM`：常规语句执行与结果流返回；
- `PREPARE_SET`：预准备 / 复用 prepared 语句集合（计划缓存复用）；
- `EXEC_BATCH`：批执行同构语句（一次往返携带多条同 SQL 参数，1..=256 条），摊薄网络与解析成本；
- `AUTO_ABORT`：连接异常时自动中止未决事务。

协议层不依赖客户端特判；批执行与计划复用共同放大单连接吞吐。

## 3 实现重点（性能优化）

优化把「计划 → 暂存写 → 页级批提交 → 分片 MVCC → 局部索引闩 → 便宜 abort → 快速恢复」串成一条通用链，各环节对应结构变化如下（完整历程见 [../performance/xin优化历程.md](../performance/xin优化历程.md)）：

| 环节 | 做法 | 解决的问题 |
|------|------|----------|
| 计划 | 谓词下推、索引前缀评分、通用连接排序 | 少扫、多用索引 |
| 暂存写 | TransactionWriteBatch 私有写批 | 语句期不做急切写盘 |
| 批提交 | 堆页 / B+Tree 叶批写 + Phase-2 并发上限 | 降低页访问与锁开销 |
| 冲突检测 | 256 分片 MVCC + fail-fast | 拆散全局闩锁 |
| 索引并发 | B+Tree latch crabbing | 结构修改局部加锁 |
| 便宜 abort | 无物理副作用的 abort 走轻量路径 | 避免全库 checkpoint/fsync |
| 持久化 | WAL 组提交 + durable-before-visible | 摊销 fsync |
| 恢复 | 顺序扫描 + 检查点复用 | 缩短崩溃后就绪时间 |

### 3.1 评测结果

在决赛性能评测（32 客户端、三个有效测量窗口取 NewOrder/min 中位数）中，最终三轮中位数分别为 **23,943.2 / 42,520.4 / 30,741.2 NewOrder/min**，取中位数 **30,741.2 NewOrder/min**，较旧架构基线（约 418 NewOrder/min）提升约 **73.5×**；P50 延迟约 **13.218ms**、P99 约 **69.372ms**；峰值 RSS 约 **5.32 GiB**，未触及内存上限。功能、持久化、压测后一致性、崩溃恢复均 PASS。

## 4 正确性保障

我们维护以下关键不变量，并在每次改动后回归验证：

- **持久性**：`durable_lsn >= commit_lsn` 恒成立，COMMIT ACK 前日志已落盘。
- **可见性**：未持久化事务不对其他事务可见；读者只能读到连续已发布前缀。
- **唯一性**：唯一键意图在提交前落锁（Acquire Intent），并发下不重复。
- **可串行化**：SSI 依赖检测覆盖 SI 的写偏斜窗口，SERIALIZABLE 下保证可串行化。
- **恢复幂等**：redo 幂等，undo 处理 winner/loser 唯一键冲突；恢复后数据与崩溃前已提交状态一致。
- **无特判**：任何优化不依赖表名、列名、statement_id 或客户端数。

## 5 存在的问题

- **优化器缺乏代价模型**：索引选择与连接排序采用启发式（索引前缀覆盖 + 过滤条件评分），尚未引入基于统计信息的代价估算，对偏斜数据可能不是最优计划。
- **静态检查点**：检查点需阻塞新事务并等待在途事务结束，长事务下会拉长检查点窗口；尚未实现增量 / 模糊检查点。
- **MVCC 垃圾回收**：版本链回收依赖可见前缀推进，长时间快照会推迟旧版本回收；GC 的精细度仍有优化空间。
- **内存与吞吐权衡**：最终吞吐伴随更高内存占用（峰值 RSS 约 5.32 GiB），缓冲池上限需与评测内存约束做折中。

---

## 6 总结与展望

**已实现**：页面式存储与分片缓冲池、B+Tree 索引与同叶批写、逻辑优化器、MVCC（RC / SI / SSI）与事务私有写批、WAL 组提交与 ARIES 崩溃恢复、Wire v3 批执行，以及把它们串成通用执行链的性能优化；最终排名吞吐 30,741.2 NewOrder/min，通过全部正确性校验。

**展望**：

- 基于代价的查询优化器（引入统计信息与代价模型，替代纯启发式）；
- 增量 / 模糊检查点，消除静态检查点的阻塞窗口；
- 更精细的 MVCC 版本垃圾回收；
- 分布式事务与数据分片（Sharding）方向的扩展。
