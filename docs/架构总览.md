# RMDB 架构总览


## 1. 总体调用链

```text
TCP client
  -> src/rmdb.cpp（每个连接一个 pthread）
  -> parser / analyze / planner / optimizer
  -> Portal（逻辑计划转物理执行器）
  -> executor（scan / DML / join / aggregate ...）
  -> record + index + transaction + recovery
  -> buffer pool + disk files
```

`src/rmdb.cpp` 在进程内创建 `DiskManager`、`BufferPoolManager`、`RmManager`、`IxManager`、`SmManager`、`LockManager`、`TransactionManager`、`LogManager` 与 `RecoveryManager`。`SmManager` 持有表文件句柄 `fhs_`、索引句柄 `ihs_` 和数据库元数据，是 DDL、索引创建、回滚辅助与 checkpoint 刷盘的汇合点。

## 2. 执行、表与缓存层

`parser -> Analyze -> Planner -> Optimizer -> Portal` 生成并实例化扫描、过滤、投影、DML、嵌套循环连接、聚合、排序和 Union 执行器。`Portal` 对 Update/Delete 先通过子执行器收集 RID，再交给 DML 执行器处理；因此扫描、可见性和锁的成本会直接放大到写事务。

表使用定长记录页：页头、bitmap 和 slot 区组成，`Rid(page_no, slot_no)` 定位记录。`RmFileHandle` 每表有 `insert_latch_`（插入/分配页槽位）和 `logical_update_latch_`（带索引表的逻辑写串行保护）。

缓冲池为 32,768 个 4 KiB 页，约 128 MiB，替换器是 LRU。`page_table_` 使用共享互斥锁，命中读取和 unpin 走共享路径；每个 frame 另有互斥锁。新页、淘汰、删除与全量 flush 取得缓冲池全局独占锁。脏页落盘前调用 WAL 刷盘。

## 3. 索引实现

索引是唯一 B+ 树，`IxIndexHandle` 管理一个索引文件，叶节点保存 key -> RID，内部节点按 key 导航。优化器可选择 `IndexScanExecutor`，索引扫描再回表读取并完成残余谓词过滤与 MVCC 可见性判断。

- `get_value`、`lower_bound`、`upper_bound` 对 `root_latch_` 取共享锁；多个查找可并发。
- `insert_entry` 与 `delete_entry` 对同一索引的 `root_latch_` 取独占锁，分裂、合并和根调整都在这个范围内完成。
- Insert/Update/Delete 维护所有受影响索引；Update 仅当索引列的 key 真正变化时更新索引。唯一性既依赖 B+ 树中已落盘 key，也要检查 MVCC 中尚未落盘的冲突候选。

这意味着读多写少的索引负载可并发，但同一索引上的写入目前仍是粗粒度串行路径。

## 4. 并发控制与锁

系统并存两条路径：READ COMMITTED 使用 2PL 锁管理器；SNAPSHOT ISOLATION / SERIALIZABLE 使用 MVCC。

### READ COMMITTED / 2PL

`LockManager` 支持表级 IS、IX、S、X、SIX 和记录级 S、X。全局 `lock_table_` 由一个 `latch_` 保护，每个锁对象有请求队列和条件变量；不兼容请求等待，最长 5 秒后以 `DEADLOCK_PREVENTION` abort。事务把已授予锁记入 `lock_set_`，在 commit/abort 时统一释放。

### SI / Serializable MVCC

MVCC 版本表以 `(mvcc_file_id, Rid)` 为 key，值是版本向量。事务开始时取得 `start_ts`；读取选择 `commit_ts <= start_ts` 的最新版本，并优先读取本事务自己的 pending 版本。初始 load 数据没有版本链时补成 `commit_ts = 0` 的 baseline，避免旧行因无版本而对快照不可见。

Update/Delete 先在版本表写 pending 版本，冲突检查比较快照后的提交版本和其他事务 pending writer；短暂等待后仍冲突则 abort。SI commit 先在 `commit_mvcc()` 中把版本应用到物理表和索引，再写 COMMIT 日志。SERIALIZABLE 额外登记表谓词/记录读集及读写依赖，检测危险结构。

## 5. 当前关键闩锁与性能含义

| 位置 | 当前粒度 | 作用与风险 |
|---|---|---|
| `TransactionManager::commit_apply_latch_` | 全局 `std::mutex` | MVCC 物理提交、GC、checkpoint 物理应用取得它；带 `Context` 的 `RmFileHandle::get_record()` 也取得它。当前会把这类记录读取与提交应用串行化，是优先检查的吞吐瓶颈。 |
| `TransactionManager::mvcc_latch_` | 全局 `std::mutex` | 保护 `record_versions_`、MVCC 事务状态和冲突判断；高并发下可形成版本可见性与冲突检查热点。代码约束其为叶子锁，持有时不能进入文件或索引层。 |
| `LockManager::latch_` | 全局 `std::mutex` | 所有 2PL 加锁、解锁、兼容性扫描共用；锁对象越多、队列越长，竞争越明显。 |
| `RmFileHandle` 两把 mutex | 每表 | `insert_latch_` 保护物理插入，`logical_update_latch_` 串行带索引表的逻辑写操作。 |
| `IxIndexHandle::root_latch_` | 每索引 `shared_mutex` | 查找可共享；插入、删除和结构调整独占整棵树。 |
| Buffer pool | 全局页表锁 + 每 frame 锁 | 命中路径可共享；淘汰、分配、flush 会取得全局独占锁。 |

锁顺序被明确约束为两条关系：`commit_apply_latch_ -> 文件/索引闩锁`，以及 `commit_apply_latch_ -> mvcc_latch_`。`mvcc_latch_` 是叶子锁，持有时不可回调文件或索引层，否则会与“文件插入闩锁 -> MVCC 闩锁”的路径形成 ABBA 死锁。

## 6. 日志、检查点与恢复

每个事务维护 `prev_lsn` 和写集合。commit 写入 COMMIT 日志并调用 `flush_log_to_disk()`；缓冲池刷脏页前也确保 WAL 已落盘。恢复流程为分析日志、REDO 已记录 DML、对未完成事务逆序 UNDO，最后重建受影响表的空闲页链，并在缺少有效 checkpoint 索引快照时重建索引。

静态 checkpoint 会阻止新语句并等待活跃事务结束，然后处理已提交 MVCC delete 的物理回收、刷页、写 checkpoint 与索引快照。性能优化不能改变“物理更新/回滚、日志持久化、checkpoint”之间的先后关系。

## 7. 给导师的优化审查问题

1. `get_record()` 是否必须在整个“取物理记录 + MVCC 可见性判断”期间持有全局 `commit_apply_latch_`？若不必，可否证明性地拆分为共享读或版本化发布协议。
2. `mvcc_latch_` 能否按 record/file 分片，或缩短临界区，且不破坏 pending writer 等待、GC watermark 和提交顺序。
3. B+ 树写路径能否从整树独占锁演进为页级 latch coupling；这属于高风险改动，需并发 insert/delete 与恢复回归测试。
4. 2PL 的全局锁表 latch、每表逻辑更新锁，以及每次 commit 的日志 flush，分别在官方压测中占多少时间；先用 `perf` 与 `RMDB_PERF_DIAG` 定量，再决定优化顺序。
5. 任何缩短锁持有时间、批量提交、组提交或缓存优化，都必须保持：无脏读、SI 冲突语义、NewOrder 全有或全无、索引/表一致，以及 `kill -9` 后恢复正确。

- B+ 树：`src/index/ix_index_handle.{h,cpp}`

- 缓冲池：`src/storage/buffer_pool_manager.{h,cpp}`
- WAL 与恢复：`src/recovery/log_manager.{h,cpp}`、`src/recovery/log_recovery.{h,cpp}`
