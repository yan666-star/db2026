# 性能测试实现与正确性要点


##题目

本题要求参赛队伍在系统运行正确的基础上，对查询执行、存取管理、事务处理进行优化，使系统在 TPCC 负载下的吞吐率更高。


### 2.1 load 指令

在完成性能测试之前，参赛队伍需要完成 `load` 指令，把表的数据插入到系统中。

指令格式如下：

```sql
load file_name into table_name;
```

示例：

```sql
load ../../src/test/performance_test/table_data/warehouse.csv into warehouse;
```

其中，`file_name` 为数据文件相对于数据库文件夹的相对路径。测试时，数据文件存放于 `src/test/performance_test/table_data` 文件夹下。

测试脚本会通过 `./bin/rmdb` 启动服务器，因此数据库文件夹位于 `build` 文件夹下。

`load_data` 指令不需要包含建表操作。

### 2.2 关闭输出文件

为了减少将结果写入文件带来的时间开销，参赛队伍需要在接收到如下命令后，停止向 `output.txt` 中写入输出结果：

```sql
set output_file off
```

注意：`set output_file off` 命令没有分号。

在未接收到该命令时，默认需要开启向 `output.txt` 中写入结果的功能。

### 2.3 聚合函数

聚合函数测试中需要考虑字符串的 `MIN` 和 `MAX`。

## 3. TPCC 测试表

测试程序中包含如下九张表：

| 表名 | 说明 | 数据规模 |
| --- | --- | --- |
| `warehouse` | 记录仓库相关信息 | `W` 条记录 |
| `item` | 记录商品信息 | 100000 条记录 |
| `stock` | 记录每个仓库的商品库存数据 | `W * 100000` 条记录 |
| `district` | 记录每个仓库提供服务的地区 | `W * 10` 条记录 |
| `customer` | 记录每个地区的客户信息 | `W * 10 * 3000` 条记录 |
| `history` | 记录客户的交易历史 | `W * 10 * 3000` 条记录 |
| `orders` | 记录每个地区的订单数据 | `W * 10 * 3000` 条记录 |
| `new_orders` | 记录新订单信息，`orders` 表中每个地区的最后 900 条订单会被添加到该表中 | 每地区 900 条 |
| `order_line` | 每个订单随机生成 5-15 条订单明细记录 | 约 `orders * 5-15` 条记录 |

## 4. TPCC 测试事务

测试程序包含如下五种事务：

| 事务 | 说明 |
| --- | --- |
| `NewOrder` | 新订单的生成 |
| `Payment` | 订单付款 |
| `OrderStatus` | 最近订单查询 |
| `Delivery` | 配送 |
| `StockLevel` | 库存缺货状态分析 |

测试程序会对每张表的主键建立索引。测试事务中包含主键字段上的单点查询、范围查询，以及非主键字段上的单点查询、范围查询。
## 6. 正确性检查

在参与性能排名前，系统必须通过以下正确性检查：

1. 功能测试全部通过；
2. 数据加载结果与标准输出一致；
3. 压测结束后，数据库表数据满足一致性检查；
4. 模拟 `kill -9` 崩溃后重启，已提交事务的数据必须能够正确恢复。

若任一正确性检查失败，则性能测试不参与排名，得分为 0。

若全部检查通过，则性能测试得分为 100，并根据 `tpmC` 参与排行榜排名；`tpmC` 越高，排名越靠前。

## 7. 优化思路

可以根据大赛提供的优化思路对系统进行性能优化，也可以在系统中加入其他优化。优化思路包括：

1. 完善系统的查询优化功能，生成更优的查询计划；
2. 增加新的算子；
3. 提高索引的并发度；
4. 在日志管理器中增加线程池，实现日志的异步刷盘。

## 8. 违规说明

针对评测中的固定表名、字段结构或 SQL 文本编写专用匹配逻辑，并绕过通用解析、优化或执行流程以提升跑分，属于面向评测用例的硬编码优化，不具备通用性，将认定为违规。

所有优化均应落实在通用的索引、执行器、事务、缓存及 WAL 等机制中，不得改变 SQL 原有语义，也不得产生 SQL 未声明的额外副作用。

如引入了此类实现，请立即移除并调整优化方向。初赛截止后如仍发现相关违规行为，经核实后可能直接取消参赛资格。
## 性能测试流程

性能题分为几个阶段：

1. 功能测试
   - 验证前十题相关 SQL 能力。

2. Load Data
   - 通过 `load file into table` 导入 TPC-C 数据。
   - 这条路径在 `src/rmdb.cpp` 中特殊处理。

3. 建索引
   - 官方会对各表主键建立索引。
   - 后续事务大量依赖主键点查、范围查和部分非主键谓词。

4. 关闭输出
   - 官方发送：

```sql
set output_file off
```

   - 该命令没有分号。
   - 关闭 `output.txt` 写入是性能优化要求。
   - 该命令不应改变后续新 worker 连接的事务隔离级别；隔离级别应由显式配置决定。

5. 预热和正式压测
   - 先预热 30 秒。
   - 再正式测量 360 秒。
   - 共 3 轮，取成功提交 NewOrder 的 tpmC 中位数。

6. 压测后一致性检查
   - 检查 district/order/stock/customer/history 等 TPC-C 守恒关系。

7. 崩溃恢复检查
   - 模拟 `kill -9` 后重启。
   - 已提交事务必须恢复正确。

## 性能测试关键事务

性能题必须先通过通用正确性门槛，再比较吞吐量。不能在数据库实现中识别固定表名、字段、SQL 文本或评测事务后走专用路径。可接受的优化必须位于通用索引、优化器、执行器、事务、缓存、WAL 和恢复机制中，并对任意等价 SQL 保持原语义。

### 合规边界

1. 禁止针对固定表名、字段结构或 SQL 文本做专用匹配。
2. 禁止绕过通用解析、分析、优化和执行流程来提升评测跑分。
3. 优化只能落实在通用机制中，包括索引、执行器、事务、缓存和 WAL。
4. 优化不能改变 SQL 原有语义，也不能产生 SQL 未声明的副作用。
5. 已存在此类评测硬编码必须立即移除；初赛截止后核实可能取消资格。

、可以使用 TPC-C 表和官方事务形状模拟负载，但数据库服务端不能识别并特殊处理这些名字或 SQL。还应使用随机表名、不同常量、不同语句顺序和不同隔离级别做反向验证。

### 索引信息

性能查询会带 `ol_w_id`。官方不会额外建立 `(ol_o_id, ol_d_id)` 二级索引，只建立以下 `order_line` 复合索引：

```sql
CREATE INDEX order_line(ol_w_id, ol_d_id, ol_o_id, ol_number);
```

### 正确性门槛

检查重点为 ACID 和并发正确性：

- 成功提交的数据必须持久化。
- 未提交数据不能被其他事务读到。
- abort 后插入、删除、更新以及索引项必须全部回滚。
- 同一行的并发写必须按隔离级别串行化或让冲突事务 abort。
- 需要关注幻读；在 SI/SSI/串行化模式下，同一事务内的快照范围读应保持一致。
- 表记录、索引、MVCC 版本链、WAL 和恢复后的状态必须一致。

隔离级别未被严格限定为 RC、RR、SI 或 SSI 中的某一个。官方回复给出的底线是通常不低于 Read Committed。不能把 `set output_file off` 偷偷绑定为隔离级别开关；隔离级别应显式设置。

### 性能负载与计分

事务比例总计 23 份：

| 事务 | 比例 |
| --- | ---: |
| NewOrder | 10/23 |
| Payment | 10/23 |
| OrderStatus | 1/23 |
| Delivery | 1/23 |
| StockLevel | 1/23 |

每一轮先预热 30 秒，预热吞吐不计分；随后正式测量 360 秒。共运行 3 轮，以三轮成功提交 NewOrder 的 tpmC 中位数作为最终指标，不取最高值，也不取平均值。

请求量充足且并发较高，公开信息约为 16–32 个客户端；已有澄清明确提到 16 个并发线程。本地应至少分别测试 16 和 32 客户端。测试 scale 小于 50、warehouse 数较低，热点 district、warehouse 和 stock 行的锁/MVCC 冲突会显著影响吞吐。

事务 `abort`/`commit` 没有隐藏的特殊埋点，公开回复只说明性能环境数据量更大。因此本地小数据通过不代表大数据和长时间并发一定通过。

### 评分闸门

以下项目全部通过后才进入性能排名：

1. 功能测试。
2. 数据加载结果检查。
3. 压测后的 TPC-C 数据一致性检查。
4. `kill -9` 后的崩溃恢复检查。

任一项失败，性能成绩为 0；全部通过后性能测试得分为 100，再按 tpmC 排名。

### NewOrder

NewOrder 是性能得分核心，tpmC 只统计成功提交的新订单。

关键链路：

1. 读取 `customer`、`warehouse`。
2. 读取并更新 `district.d_next_o_id`。
3. 插入 `orders`。
4. 插入 `new_orders`。
5. 多次读取 `item`。
6. 多次读取并更新 `stock`。
7. 插入多条 `order_line`。

一致性要求：

- `district.d_next_o_id` 必须等于初始值加成功 NewOrder 数。
- 每个订单应有完整的 `orders/new_orders/order_line` 关系。
- `stock.s_quantity/s_ytd/s_order_cnt/s_remote_cnt` 要和已提交订单一致。
- abort 后不能留下订单、订单行或库存变化。

优化重点：

- 主键索引点查。
- district 和 stock 热点更新。
- MVCC 写冲突检测成本。
- 多条 order_line 插入和索引维护成本。

### Payment

Payment 更新付款相关字段并插入 history。

关键链路：

- 更新 `warehouse.w_ytd`。
- 更新 `district.d_ytd`。
- 更新 `customer.c_balance/c_ytd_payment/c_payment_cnt`。
- 插入 `history`。

优化重点：

- warehouse/district/customer 的点查和点更新。
- history 追加插入。
- float 字段更新和输出格式保持稳定。

### Delivery

Delivery 处理待配送订单。

关键链路：

- 从 `new_orders` 找到待配送订单。
- 删除对应 `new_orders`。
- 更新 `orders.o_carrier_id`。
- 更新 `order_line.ol_delivery_d`。
- 更新 customer 的余额和配送计数。

优化重点：

- `new_orders` 的范围/最小值查找。
- 删除时表和索引一致。
- MVCC delete 的物理记录、版本链和索引项同步。

### OrderStatus

OrderStatus 偏读，通常查询客户最近订单和订单行。

优化重点：

- customer 点查或按 last name 查询。
- orders 最近订单查找。
- order_line 范围读取。
- 保持 SI 快照读一致。

### StockLevel

StockLevel 偏聚合和范围查询。

优化重点：

- 最近订单范围。
- order_line 和 stock 的连接/过滤。
- 聚合计数。
- 索引选择和中间结果规模控制。

## 性能正确性的关键实现点

### 1. 性能 worker 的隔离级别不能低于 READ COMMITTED

当前做法：

- 普通连接默认仍是 `READ_COMMITTED`。
- `set output_file off` 只关闭 `output.txt` 写入，不再改变默认隔离级别。
- 如需运行 SI 或 SERIALIZABLE，应通过显式隔离级别配置进入对应路径。

这样避免输出开关产生 SQL 语义副作用，同时保留按不同隔离级别评估吞吐的空间。

### 2. 初始 load 数据按 `ts=0` 可见

load 进来的 stock、district、customer 等行没有 MVCC 版本链，但它们是已提交初始数据。

当前做法：

- MVCC 读取无版本链物理行时，为其建立 baseline 版本。
- baseline 的 `commit_ts = 0`。

这保证老数据不会因为别的事务提交而从快照里消失。

### 3. MVCC UPDATE 空结果需要 abort

TPC-C 的 UPDATE 目标为空通常不是正常情况，而是可见性、冲突或索引路径出错。

当前做法：

- MVCC `UpdateExecutor` 如果待更新 RID 为空，直接 abort。
- 如果扫描得到 RID 但实际读取不可见，也 abort。

这避免半个 NewOrder 提交。

### 4. COMMIT 顺序必须先应用数据，再写提交日志

当前做法：

- MVCC 事务先执行 `commit_mvcc()`。
- 物理记录和索引更新成功后，再写 COMMIT log。
- 如果物理应用失败，回滚已应用部分并 abort。

这个顺序同时服务于性能测试的 post-run consistency 和 kill -9 recovery。

### 5. 表、索引、版本链必须同步

性能测试检查可能通过 scan，也可能通过 index 谓词。后续优化不能只让其中一条路径正确。

需要保持：

- 物理表记录正确。
- 索引项正确。
- MVCC 版本链正确。
- tombstone 和物理删除时机正确。
- abort 后三者都回到事务前状态。



## 修改代码时的注意点

1. 不要写死 TPC-C 表名、字段名或 SQL 文本。
2. 不要破坏默认 RC 功能测试。
3. 不要绕过 parser/analyze/optimizer/executor 主流程。
4. 改索引时同时验证 Insert/Update/Delete/Abort/Recovery。
5. 改 MVCC 时同时验证 SI、SER、性能压测和 crash recovery。
6. 改日志时必须验证第十题和性能题 kill -9 阶段。
7. 改输出路径时注意 `set output_file off` 无分号。
8. 改 float 计算和输出时注意 Payment、history、聚合测试。
