# 本轮修改关键要素

> 基线：finals-wire-ssi worktree  
> 测评时间：2026-08-11  
> 测评结果：所有正确性门禁 PASS，NewOrder 30/min（中位数）

---

## 一、修改总览

本轮围绕三个独立方向修改了 12 个源文件，均为通用机制内优化，不涉及硬编码表名/SQL/绕过通用路径。

### 提交 1：复合 JOIN 全绑定（复合索引查找）

**问题**：`NestedLoopJoinExecutor` 每次只传一个跨表 EQ 条件给内表索引扫描，无法利用 `(ol_w_id, ol_d_id, ol_o_id, ol_number)` 等多列复合索引的前缀一次性定位。

**修改文件**：
| 文件 | 改动 |
|------|------|
| `executor_abstract.h` | 新增 `IndexLookupBinding` 结构体 + 多绑定虚函数 |
| `executor_nestedloop_join.h` | 收集全部跨表等值绑定，先单键回退再尝试多键 |
| `executor_filter.h` | 多绑定代理 |
| `executor_projection.h` | 多绑定代理 |
| `executor_index_scan.h` | 动态绑定 + 常量等值 → 最长连续前缀键（全键→等值查；部分键→零扩展范围下界） |
| `planner.cpp` | 复合索引评分：join列 ∪ 常量EQ 覆盖的最长前缀，同分选列数少者 |

**关键性**：复合索引前缀扫描是 TPC-C `order_line` 五表 JOIN、Delivery 范围查等路径的基数削减核心。单列绑定迫使扫描大量无关记录。

---

### 提交 2：Active Loser 恢复修复

**问题**：REDO 阶段对活跃 loser（崩溃时未提交事务）仍执行物理重放。若 loser 与已提交 winner 暂持相同唯一索引键，REDO 抛唯一键冲突导致恢复失败。

**修改文件**：
| 文件 | 改动 |
|------|------|
| `log_recovery.h` | 声明 `index_key_changed()` |
| `log_recovery.cpp:redo()` | 记录 loser offset，跳过物理 REDO |
| `log_recovery.cpp:install_record()` | `keys_changed` 守卫索引删除+插入；旧记录存在且键列不变时跳过索引 churn |
| `log_recovery.cpp:index_key_changed()` | 逐索引逐列 `memcmp` 比较新旧记录键列 |

**关键性**：直接决定 crash recovery 能否通过。32 客户端 SI 下 loser 事务数显著增加，修复前大概率恢复失败。

---

### 提交 3：正式规模恢复就绪 + 监听器

**问题**：
1. `finish_recovery()` 无条件全页扫描重建空闲列表（O(n) 遍历）
2. 全量 `flush_for_checkpoint()` 刷所有索引至恢复关键路径
3. 索引快照复制用 iostream 逐字节读写
4. `SIGKILL` 后内核延迟释放端口 → `bind()` 直接失败退出

**修改文件**：
| 文件 | 改动 |
|------|------|
| `sm_manager.h` | 声明 `flush_touched_for_recovery()` |
| `sm_manager.cpp` | 定向 flush 实现 + `std::filesystem::copy_file` 替代 iostream |
| `log_recovery.cpp:finish_recovery()` | 有检查点时跳过 free-list 重建；调用 `flush_touched_for_recovery()` |
| `rmdb.cpp:create_listener()` | EADDRINUSE 重试循环（5 次 × 200ms） |

**关键性**：恢复就绪时间直接影响 90s 恢复预算。定向 flush 避免全量索引扫描阻塞恢复完成。

---

## 二、这些修改与 30 NewOrder/min 的关系

坦率说：**本轮提交对吞吐几乎无影响**。原因如下：

1. **复合 JOIN**（提交 1）：Delivery/StockLevel 本身占比低（各 1/23），且这两类事务在原始基线中完成率已达 100%，不是吞吐瓶颈。
2. **恢复修复**（提交 2）：纯正确性修复。恢复失败 = 得分 0，但通过后对吞吐零贡献。
3. **恢复就绪**（提交 3）：缩短恢复时间，不影响吞吐测量窗口。

**真正的性能瓶颈不在此处**——30 NewOrder/min 的成因见《激进性能优化方案》。

---

## 三、关键教训

1. **正确性门禁是入场券，不是加分项**。通过全部门禁只保证"有资格被排名"，不保证"排名靠前"。
2. **瓶颈诊断必须先于代码修改**。本轮提交的设计文档聚焦于 JOIN 正确性和恢复正确性，未触及吞吐的核心约束。
3. **吞吐瓶颈的本质**：NewOrder p50 延迟 27 秒、p99 延迟 81 秒，远非"索引扫描多读了几页"可以解释。这是一个全局串行化问题。
