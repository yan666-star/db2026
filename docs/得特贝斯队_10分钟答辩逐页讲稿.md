# 得特贝斯队 RMDB 10 分钟答辩逐页讲稿

> 统一主线：**三万级吞吐不是因为某一个函数变快，而是系统不再让所有客户端围绕少数全局锁、热点记录和 fsync 排队。**

## 第 1 页｜封面（0:00—0:10，10 秒）

各位评委老师好，我们是得特贝斯队。下面重点汇报 RMDB 的系统架构，以及我们如何在保证事务正确性和崩溃恢复的前提下，把高并发性能提升到三万级 NewOrder 每分钟。

汇报分为四部分：首先用三页建立系统地图；然后解释旧架构为什么随并发增加反而退化；第三部分重点讲事务私有写批、分片冲突检测和页、叶批提交；最后用 OJ、本地 A/B 和正式三轮数据说明优化效果与剩余瓶颈。

## 第 3 页｜系统架构与运行链路（0:30—0:35，5 秒）

先从一次数据库请求经过哪些模块开始。

## 第 4 页｜六大板块构成完整 RMDB（0:35—1:15，40 秒）

RMDB 不是一条简单的 SQL 流水线。接入层处理 Wire v3、Prepared 和批请求；查询层完成解析、语义检查和规划；执行器把计划变成 Scan、Join、聚合或 DML。真正决定系统能否扩展的是下面三块：事务层负责 MVCC、隔离级别、写意向和提交状态；存储层负责 Heap、B+Tree 与 Buffer Pool；日志恢复层用 WAL 约束提交顺序并支持 redo、undo。也就是说，上面三层决定“做什么”，下面三层共同决定“能不能并发、能不能持久、崩溃后能不能恢复”。后面的优化主要发生在这三个模块的交界处。

## 第 5 页｜请求从 SQL 到数据页的运行链路（1:15—1:50，35 秒）

一条请求先由协议层解码，Prepared 请求直接复用已有计划，普通请求则经过 Parser、Analyzer 和 Planner。到执行器后，读写开始分流：读取通过索引缩小候选 RID，再按快照选择可见版本；写入除了生成 DML，还必须登记事务私有变化和冲突 intent，提交时统一修改 Heap、Index 并写 WAL。这里的关键是，同一条 SQL 的成本不只在执行器，解析复用、冲突发生时机、页访问次数和日志同步都会进入端到端延迟。

## 第 6 页｜事务、存储和 WAL 共同构成提交单元（1:50—2:30，40 秒）

写事务不是“改完一行就结束”。它同时改变三类状态：事务层的版本、intent 和提交状态，存储层的 Heap、Index、Buffer Page，以及持久化层的 Row WAL 和 COMMIT LSN。我们的正确性边界是：物理修改完整应用、COMMIT 日志稳定之后，版本才对新快照可见；返回 COMMIT 成功前，还必须满足 durable LSN 已覆盖本事务的 commit LSN。这个顺序非常重要，因为如果先发布版本，其他事务可能看见尚未持久化的状态；如果只优化其中一层，瓶颈也会立刻转移到另外两层。

## 第 7 页｜并发瓶颈与性能障碍（2:30—2:35，5 秒）

明确提交边界后，再看旧版本为什么无法扩展。

## 第 8 页｜旧版本在高并发下为什么无法扩展（2:35—3:25，50 秒）

左图最能说明问题：单客户端约 4497，增加到 32 客户端后只剩 418，只有单客户端的约 9.3%。这不是硬件饱和，而是负扩展。第一，冲突发现太晚，事务已经完成查询、页访问甚至部分物理写，最后才在热点 district、stock 或唯一键上失败；第二，用 SI admission 等于 1 虽能把 OJ 做到 947，但本质是把 32 个客户端排成一队，只减少冲突、没有并行度；第三，同页多条记录和同叶多个 key 仍逐条 fetch、pin、加锁和从根下降；第四，每事务独立 write、fsync，把日志同步变成串行点。因此旧系统优化的是“单次操作”，我们需要优化的是“并发事务的整体成本”。

## 第 9 页｜并发和存储性能优化（3:25—3:30，5 秒）

所以我们没有继续微调旧锁，而是重排事务从准备、冲突到持久化的整个过程。

## 第 10 页｜性能重构总览（3:30—4:15，45 秒）

重构可以概括为五个变化。请求入口用 Prepared 和 EXEC_BATCH 减少重复解析、网络往返和逐条 ACK；事务写入从立即修改 Heap、Index，改为 TransactionWriteBatch 私有暂存；并发控制从全局 admission 改为 256 分片 intent，并把 Buffer 页表拆成 64 个 shard；物理提交从逐记录操作改为 Heap Page Batch 和 B+Tree Leaf Batch；日志从逐事务同步改为 WAL batch 与 group commit。这里最核心的是中间三项：失败事务先在逻辑层结束，成功事务才进入有界的物理提交，并把固定成本按页、按叶摊薄。

## 第 11 页｜TransactionWriteBatch 与分片 intent（4:15—5:40，85 秒）

这一页是整个架构的核心。左侧的 TransactionWriteBatch 把 INSERT、UPDATE、DELETE 先保存在事务私有状态中，自己的读取通过 overlay 看见最新值，其他事务看不见未提交状态。同一记录的连续 UPDATE 会保留最初 before image 和最终 after image，例如库存 60 到 55 再到 48，最终只产生一次 60 到 48 的物理 mutation；INSERT 后 DELETE 甚至可以直接消去。因此普通冲突 abort 只需要丢弃 batch、pending version 和 intent，不再对数据页和索引执行重型回滚。

中间是提交顺序：先 Seal 和 Validate，再获取 intent，最后才进入 Phase-2 物理 Apply。右侧把 record intent 和 unique-key intent 按 ResourceKey 哈希到 256 个 shard。若同一事务已持有则幂等成功，旧 owner 已结束可以接管，其他活跃事务持有则 fail-fast。这样，热点只影响竞争同一对象的事务，不相关 RID 和唯一键仍可并发。

我们取消了排名路径上的 SI 全局 admission，但没有让物理写无限并发：Phase-2 默认最多 16 个事务同时修改 Heap、Index 和 WAL。这个设计把“事务并发度”和“存储承载能力”分开：前者不再全局排队，后者通过有界并发避免页面、内存和日志被同时压垮。

## 第 12 页｜Heap Page Batch（5:40—6:40，60 秒）

WriteBatch 给了我们一个冻结、有序的写集，StorageCommitExecutor 再按 PageId 聚合。旧路径中，同一页 8 条修改会重复 8 次 fetch、pin、写锁、bitmap 解析和 dirty 标记；新路径只取得一次 WritePageGuard，在 guard 内按 slot 连续校验 RID 与 before image、应用 mutation，并统一更新 page LSN。它减少的不只是函数调用，更重要的是锁切换和 cache line 竞争。

页间并发由 64-shard Buffer Pool 承担：PageId 先落到不同页表 shard，frame 还有独立 metadata latch 和 content latch，PageGuard 统一管理 pin、dirty、generation 与 page LSN。因此“页内批处理”摊薄固定成本，“页间分片”保留并行度。脏页真正写出前仍要保证 WAL durable 到该页的 page LSN，性能优化没有破坏 WAL-before-data。

## 第 13 页｜B+Tree Leaf Batch（6:40—7:30，50 秒）

B+Tree 的问题类似，但还多了结构变化。旧路径每个 key 都从 root 下降到 leaf，即使 8 个连续 key 落在同一叶，也会重复定位、比较和加锁。新路径先按 index 和 key 排序，定位叶页并取得 WriteGuard 后，重新校验 frame generation、叶类型、键范围和兄弟关系；条件安全时，一次下降服务一组 key，在同一叶连续应用 mutation。

如果 key 越界、叶分裂或父分隔键需要更新，我们不会强行走快路径，而是立即释放局部 guard，restart 到 parent-before-child 的 local crabbing 慢路径。也就是说，快路径靠可验证前置条件提速，失败时回退保证 B+Tree 不变量。右下角 852 到 891 的局部 A/B 只证明减少热路径固定成本的方向有效，不能把全部架构收益单独归因于这一项。

## 第 14 页｜评测数据与结论（7:30—7:35，5 秒）

最后看这些结构变化是否真正转化为稳定吞吐。

## 第 15 页｜评测数据（7:35—8:50，75 秒）

数据要分三个口径看。第一，旧架构从 1 客户端 4497 下降到 32 客户端 418，证明核心问题是并发退化；SI 等于 1 的 OJ 结果 947 说明全局串行只能止损，不能扩展。第二，605 到 785、829 到 867、852 到 891 是不同阶段、同环境的局部 A/B，它们只能验证轻量 abort、Buffer 并发和 B+Tree 热路径这些方向有效，不能简单相加。

第三才是最终端到端结果：阶段提交达到约 15,621，最终正式三轮分别是 23,943.2、42,520.4 和 30,741.2，按赛题规定取中位数 30,741.2 NewOrder 每分钟。相对旧 32 客户端 418，约提升 73.5 倍；成功 NewOrder 的 p50 为 13.218 毫秒，p99 为 69.372 毫秒。我们没有把 42,520.4 的单轮峰值包装成稳定吞吐，也不把后半段差异归因于某一个提交，因为数量级提升来自整条提交链路共同消除结构性串行。

## 第 16 页｜为什么更好、正确性与剩余瓶颈（8:50—9:55，65 秒）

总结起来，新架构有四个本质变化：冲突更早，失败事务在物理修改前结束；提交更批量，有序写集按 Heap Page 和 B+Tree Leaf 聚合；并发更局部，MVCC 256 shards、Buffer 64 shards 和局部 crabbing 让不相关事务不再全局排队；同步可共享，Prepared 减少固定请求成本，group commit 让多个事务共享 write 和 fsync。

但共享 fsync 不等于提前返回。第一个等待者作为 group leader 聚合同时完成的事务，每个 follower 仍要等 durable watermark 覆盖自己的 commit LSN；Heap、Index 和 WAL 全部稳定后才发布版本，快速路径校验失败就回退到正确慢路径。这是我们坚持的正确性底线。

剩余问题也很明确：abandoned 约 25.06%，fsync 占所选 syscall 时间约 87.4%，Delivery p99 达 441.698 毫秒，而且三轮吞吐仍有波动。下一步会继续减少热点事务冲突前的无效工作、WAL 与索引写放大，并重点优化 Delivery 尾延迟。

## 彩排时只记住的 6 个锚点

1. **418 → 30,741.2 的本质**：全局等待、晚冲突、逐行写入，变为分片并发、早冲突、事务级批提交。
2. **正确性顺序**：Validate → Intent → WAL/Heap/Index Apply → COMMIT durable → Publish visibility。
3. **WriteBatch 的价值**：不仅是批量，更是把冲突移到物理修改之前，并合并同一记录的净变化。
4. **256 与 64 的区别**：256 shards 管 MVCC/intent；64 shards 管 Buffer page table；Phase-2 默认最多 16 个并发提交。
5. **Group commit 的底线**：共享 fsync，但每个事务都等待自己的 `commit_lsn` 被 `durable_lsn` 覆盖。
6. **数据口径**：局部 A/B 不相加；正式成绩取三轮中位数 30,741.2；42,520.4 只是峰值。
